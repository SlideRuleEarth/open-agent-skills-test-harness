# Design: MCP Server Support in the Agent-Skills Test Harness

**Status: draft for discussion** · CLI versions verified against: claude 2.1.113 · codex 0.140.0 · copilot 1.0.64 · agy 1.1.1

## 1. Context and goals

We are developing a custom MCP server (SlideRule data access). The harness needs to:

1. **Let scenarios exercise MCP servers** — declare a server (local stdio process or remote HTTP/SSE endpoint), have the agent under test call its tools, and assert on that usage.
2. **Control access** — MCP stays hermetically OFF by default; only scenarios that explicitly declare servers get them, optionally restricted to specific tools. Credentials (API keys, bearer tokens) come from environment variables at run time and never appear in scenario YAML or archived artifacts. "Off by default" is enforced by *prevention* everywhere except a residual window on copilot **and codex**, where the CLI re-reads its own discovery state after launch and the harness cannot freeze that state; there the guarantee is narrowed to **no run reported clean had its hermeticity premise broken** — and on **codex that narrowed guarantee is itself qualified**: a server that started and was removed before the post-run check, without the model calling it, is undetectable (see the update below). §4 states what the copilot case does and does not cover.

> **Update — codex's launch window is now NARROWED, and one case stays open.** The Phase 0 text below describes codex's `_verify_all_mcp_disabled` as a "post-verify". That name is misleading: it runs from `build_argv`, so it is post-*enumeration* and pre-*launch*. A server added to config between argv construction and codex reading its config at startup was never named on the disable set, loaded live, and nothing checked afterwards. `CodexAdapter.verify_post_run` now re-enumerates after the run and fails closed on any server configured but not disabled on the launched argv, and additionally reads the run's own stream for `mcp_tool_call` items.
>
> **Residual undetectable gap (codex only).** A server added after argv was built, started by codex, and removed again before the post-run enumeration is invisible to *both* checks whenever the model never calls one of its tools — the stream is silent because codex emits nothing when a server starts, and re-enumeration sees the restored configuration. Because it is precisely the *idle* server that escapes, and a server need not be called to act (the sentinel received `initialize`/`tools/list` and ran as the agent for the whole session), this is a real hole rather than a technicality. **For codex, a clean verification means "no leak was detected", not "no server ran".** An earlier draft of this section claimed the two checks covered each other's blind spots; that holds for copilot, whose witness names every server it brought up, and is false for codex — review caught the over-claim.
>
> Closing it requires *prevention*: a materialized private configuration for the child, so no file an outside writer can reach is consulted mid-run. That is a real change to codex's isolation story — `$CODEX_HOME` currently mirrors the user's, which is what keeps auth working — and is not attempted here. Tracked in `TODO_Version_Provenance.md`.
>
> **codex's stream evidence is much weaker than copilot's, and the asymmetry is load-bearing.** Verified live against a sentinel stdio MCP server: codex emits **no event when it starts a server** — the sentinel was launched and exchanged `initialize`/`tools/list` while the stream showed its usual four events. The only MCP trace is an `mcp_tool_call` item, emitted only if the model actually calls a tool. So for codex, presence proves a leak but absence proves nothing, and the re-enumeration half carries the argument — the reverse of copilot, whose `session.mcp_servers_loaded` positively witnesses a clean run.
>
> **`--ask-for-approval never` is not an MCP control.** The same test showed it cancelling the sentinel's tool *call* ("user cancelled MCP tool call") while the server process ran as the agent for the entire session. Only the `-c mcp_servers.<name>.enabled=false` overrides stop the process starting (verified: with them applied, the sentinel never ran at all).

All four adapters (claude, codex, copilot, antigravity) are in scope, with a phased rollout grounded in what each CLI can actually do.

### 1.1 Pre-Phase-0 state — a hermeticity bug (historical; fixed below)

MCP was intentionally disabled from the start, but before Phase 0 only the Claude adapter actually enforced it (line references are to the pre-Phase-0 code):

- **claude** — was already hermetic. `--strict-mcp-config` sat in `_HERMETIC` (`adapters/claude.py:63-68`) with no `--mcp-config`, so no servers loaded.
- **codex** — **leaked**. The isolated HOME symlinked `~/.codex` wholesale (`isolation.py:130-149`), so any `[mcp_servers.*]` in the user's real `config.toml` loaded in every run.
- **copilot** — **leaked**. `--disable-builtin-mcps` (`adapters/copilot.py:73`) only disabled the bundled GitHub server; the user's real `~/.copilot/mcp-config.json` still loaded through the symlinked HOME.
- **antigravity** — **leaked** (latently). `<iso_home>/.gemini/config/mcp_config.json` was a symlink to the real file; benign at the time only because that file happened to be empty.

Fixing this was Phase 0, worth doing regardless of the rest of this design.

**Update: Phase 0 does not support Windows, and refuses to run there.** The design below
works out copilot's Windows ODR gate, WOW64 views and `%USERPROFILE%` resolution in
detail, and all of that stands — but it is downstream of a guarantee the harness cannot
currently make on that platform at all. Every hermeticity claim here rests on being able
to kill the whole process tree the agent creates, and on Windows the only mechanism for
that (a Job Object) can be assigned only *after* `CreateProcess` returns, while the OS
associates a member's **future** children only. A grandchild spawned in that window —
an MCP server started as the first thing the agent does — is permanently outside the job.
Job-at-creation via `PROC_THREAD_ATTRIBUTE_JOB_LIST` is unreachable through stdlib
`Popen` (CPython honours `lpAttributeList` for `handle_list` and nothing else), so
closing it needs a bespoke `CreateProcess` or a launcher shim, plus a Windows host to
verify on — neither of which exists yet. Rather than ship a guarantee that is silently
unsound on one platform, `exec.run_captured` refuses win32 **before it spawns anything**
(`UnsupportedPlatform`, an `OSError` subclass so existing callers fail closed on it
unchanged). Refusing after the `Popen` would refuse nothing — the grandchild being
guarded against starts in the child's first instants, so a check that runs once the child
exists has already let it happen. The Job Object
code stays in place, correct and tested against a stubbed kernel32, because it is still
the right sweep for the child that did start and because the follow-up that adds
job-at-creation should change one predicate rather than start from nothing.

**Update: Phase 0 is implemented** (revised across several review rounds — see §8 for the mechanics). Findings from implementation that corrected this design, all verified against the installed CLIs: codex's `-c mcp_servers={}` does **not** clear the persisted table (deep-merge), disabling a name codex doesn't load *breaks* the run, its plugins are a separate MCP channel, and its effective server set depends on the run's **cwd and env** (trusted-project `.codex/config.toml`, `$CODEX_HOME`) — so enumeration must run in the child's exact context; copilot/agy each have additional channels beyond the single user config file (plugins — including copilot's `config.json` `cache_path` records and agy's `plugins.json` — workspace configs across agy's *four* customization roots, `COPILOT_HOME`, and copilot's Windows ODR registry, which is a **fail-closed gate** — copilot executes the registry-advertised command itself, so a populated gate can't be soundly pre-enumerated and instead fails the run closed), and copilot rejects `{}` as an MCP config (§2).

## 2. Per-CLI MCP capability survey

Everything marked **(verified)** was checked against the installed CLI's help output or embedded docs; **(inferred)** items are documented behavior not confirmable from `--help` and carry a verification task (§9).

### claude 2.1.113
- `--mcp-config <configs...>` — loads servers from JSON files or inline strings (verified). Paired with the already-passed `--strict-mcp-config` ("only use MCP servers from --mcp-config"), declared servers become the *only* servers — hermetic opt-in for free.
- Tool gating: MCP tools are named `mcp__<server>__<tool>` (**verified** live against the echo fixture, 2.1.113 — §6-C2). `--disallowedTools` is the mechanism that bites: it removes tools from the advertised surface, accepts wildcards (`mcp__<server>__*`), and **beats** `--allowedTools` when both name the same tool (all verified). `--allowedTools` gates nothing under the flags this harness passes (§6-C2). The bare `mcp__<server>` whole-server prefix form was **not** exercised — the harness emits explicit names and `*` wildcards only, so it stays unverified rather than assumed.
- Transports in the `mcpServers` JSON: stdio `{"command":…, "args":[…]}` — **verified** end-to-end against the echo fixture, server reported `connected` in the init event and its tool executed; remote (`"type": "http"|"sse"`, `url`, `headers`) still **inferred** (§9.1).
- The harness runs with `--dangerously-skip-permissions` (`adapters/claude.py:100-101`), under which `--allowedTools` is not "likely moot" but **entirely inert** for MCP tools: the unlisted tool stays advertised, the model calls it, it executes (**measured** 2026-07-22, not inferred — §6-C2). The one flag that makes an allowlist bite, `--permission-mode dontAsk`, makes it bite on *every* tool including built-ins — rejected on comparability grounds, not on strength (§6-C2).

### codex 0.140.0
- No MCP flag on `exec`; the mechanism is `-c key=value` dotted-path TOML overrides, valid on `exec` (verified).
- **`-c` deep-merges with the persisted config — it cannot clear a table** (verified 0.140.0: with `[mcp_servers.review_fixture]` in config.toml, `-c mcp_servers={}` leaves the server enabled in `codex mcp list --json`). Per-server `-c mcp_servers.<name>.enabled=false` *does* disable it (verified) — so hermetic-off requires enumerating configured names, and Phase 1's "declared servers only" likewise means disabling every user server not in the declared set.
- **Enumeration must match codex's effective view exactly**: a `-c …enabled=false` for a name codex does NOT load creates an incomplete top-level entry and the run dies with "invalid transport" (verified). The **only** enumerator is codex itself (`codex --disable plugins mcp list --json`) — there is no offline config parse: a hand-parsed subset of one config.toml misses codex's system/managed layers, and a later successful main invocation could then launch an un-disabled server, so any failure of the CLI enumeration **fails closed**. Profiles don't contribute: the legacy `profile = "x"` config key is rejected outright by 0.140.0 ("no longer supported; use `--profile`"), the harness never passes `--profile`, and inactive `[profiles.*]` tables are ignored (all verified).
- **The effective view depends on the run's cwd and env** (verified 0.140.0): a *trusted* project contributes its `<git root>/.codex/config.toml` servers (untrusted projects don't; the root is resolved via git, so a subdir cwd inside a trusted repo still loads it), and `$CODEX_HOME` moves the global config. So enumeration runs `mcp list` with the **child's exact cwd and env** (exec.execute() computes the subprocess env *before* argv and hands it to the adapter via `RunOptions.effective_env`; probes get their own fresh workspace + env). Its JSON (an array of objects with a string `name`) is validated strictly — `null`, `{"servers": […]}` or any other drifted shape **fails closed** rather than reading as "no servers". Results are **not cached**: the effective view depends on the full execution context (resolved binary/PATH, git-root state, system/managed config), more than any home+cwd+mtime key could capture, so a stale entry could disable the wrong set.
- **Managed/MDM config can outrank the kill-switch, so the overrides are post-verified**: a higher-precedence configuration layer can override a `-c …enabled=false` (and `--disable plugins`). After building the disable overrides the adapter re-runs codex's own enumeration **with the overrides applied**, in the same cwd/env, and confirms every server is reported disabled (an entry counts as enabled unless it carries `"enabled": false`). Any server still enabled — or any failure to obtain that post-override view — **fails closed**.
- **Plugins are an MCP channel of their own**: a codex plugin can ship `.mcp.json` servers that never appear in config.toml, and disabling them by name would hit the incomplete-entry failure above. `plugins` is a stable feature flag; `--disable plugins` (valid at top level, verified) removes the channel wholesale — plugin-provided skills go with it.
- Server names are restricted to `[A-Za-z0-9_-]` by `codex mcp add` (verified), i.e. always TOML-bare-key-safe in a `-c` dotted path. The `-c` parser cannot address *quoted* key segments (verified: it errors with "failed to load configuration"), so a hand-edited exotic name fails closed rather than loading.
- **`RunOptions.extra_args` are a config channel of their own**: appended after the kill-switch overrides, a `-c`/`--config` token there outranks them (verified 0.140.0: the later of two duplicate `-c mcp_servers.<n>.enabled=` overrides wins), and `--profile`/`-p`, `--cd`/`-C`, or `--enable` switches which configuration codex resolves — all after the post-verify has run. `build_argv` fails closed on every spelling of those flags (standard runner cells never populate `extra_args`; only the programmatic API can).
- No feature-level kill-switch: `codex features list` has no `mcp` entry (verified).
- Config vocabulary (verified via `codex mcp add --help` and binary strings): stdio `command`/`args`/`env`; remote `url` (streamable HTTP) with `bearer_token_env_var`, `http_headers`, `env_http_headers` (header value taken from a named env var); `enabled_tools`/`disabled_tools`; `startup_timeout_sec`/`tool_timeout_sec`.
- `bearer_token_env_var` is notable: the secret never appears in argv or on disk — only the env-var *name* does.
- Gap: no legacy SSE support surfaced anywhere (inferred gap).
- The harness parser already normalizes `mcp_tool_call` items into TOOL_CALL events (`adapters/codex.py:168-195`).

### copilot 1.0.64
- `--additional-mcp-config <json>` — JSON string or `@file`, repeatable, augments `~/.copilot/mcp-config.json` for the session (verified).
- Per-server vocabulary via `copilot mcp add`: `--transport stdio|http|sse` (all three), `--env`, `--header`, `--timeout`, and per-server `--tools "*"|list|""` filter (verified).
- Also useful: `--secret-env-vars <names>` redacts those env values from output (verified); `COPILOT_HOME` overrides `~/.copilot` (verified); `--disable-mcp-server <name>`, `--allow-tool`/`--deny-tool` with `MyMCP(tool)` syntax (verified).
- No "ignore user mcp-config" flag exists — hermeticity must come from masking the file in the isolated HOME.
- **Server sources beyond `~/.copilot/mcp-config.json`** (verified in the 1.0.64 bundle): workspace configs — copilot reads `.mcp.json` / `.github/mcp.json` (the **first existing candidate per directory**, walking cwd→git root; a repo-less run reads the cwd only), `.vscode/mcp.json` having been **removed in 1.0.64**; the **built-in / feature-gated in-process servers** (`github-mcp-server`, `playwright`, `bluebird`, and the staff-gated `computer-use`, the last switchable on via `config.json` `enabledMcpServers` — `--disable-builtin-mcps` documents only `github-mcp-server`); and installed plugins, whose definitions can declare `mcpServers`. The harness's workspace walk is a deliberate **conservative superset**, not CLI parity: it checks all three candidates (the removed `.vscode/mcp.json` and legacy `"servers"` spelling included) in the cwd and *every* ancestor, because over-enumerating only adds harmless disables (`--disable-mcp-server` tolerates names copilot never loads) while under-enumerating would leave a server live. The built-in names are disabled unconditionally by name, and the user `mcp-config.json` is parsed as JSONC (below). All of these must be neutralized for hermetic-off, and `COPILOT_HOME` redirects the home-based ones wholesale.
- **Plugin loading doesn't go through `installed-plugins/` alone**: plugin records live in `config.json` (`installedPlugins`, each with an absolute `cache_path` the loader follows even when `installed-plugins/` is empty — verified live). `config.json` also holds auth tokens and is **full JSONC** (line, inline, *and* block comments plus trailing commas — the same live-verified grammar as the user `mcp-config.json`, not just full-line `//`), so it must be *sanitized* (drop `installedPlugins`/`enabledPlugins` and `enabledMcpServers` — the feature-gated built-in switch — keep the rest), not replaced. An unparseable file fails closed to the neutral-but-hermetic shape.
- **The user `mcp-config.json` is JSONC too, the workspace ones are strict JSON** (live-verified via `copilot mcp list`, 1.0.64): `$COPILOT_HOME/mcp-config.json` accepts comments and trailing commas, so the enumerator parses it as JSONC and **fails closed** on an existing-but-unparseable file (copilot itself errors out on such a file); a workspace `.mcp.json` with a trailing comma is silently *ignored* by copilot, so those stay strict `json.load` (invalid → empty, matching copilot's warn-and-skip).
- **The empty mcp-config shape is `{"mcpServers": {}}`** — a bare `{}` fails validation with "mcpServers: Required" (verified 1.0.64) and kills the session before execution.
- **Custom agents are an MCP channel `--disable-mcp-server` cannot be *aimed at*** (verified in the 1.0.64 bundle + installed CLI help): agent definitions come from `**/*.md` under `$COPILOT_HOME/agents`, under the `.github/agents` / `.claude/agents` convention dirs walked up from the cwd to a boundary that is the git root when git discovery finds a repo and the OS home *only when it does not* (an either/or, not the nearer of the two — so a home nested **inside** a repo is walked straight past), from installed plugins, and — for a git-repo cwd with a GitHub remote and auth — from a *remote* org/enterprise listing fetched off the Copilot API; local frontmatter (`mcp-servers`) and remote entries alike can declare MCP servers. A selected agent's servers *are* started through `startServerOnce`, which **does** consult the session `disabledMcpServers` set — but that buys the harness nothing here, because the **names are unenumerable**: they live inside agent frontmatter and, worse, inside *remote* org/enterprise listings the harness cannot read at all, so there is nothing reliable to put on `--disable-mcp-server` (parsing local frontmatter would still miss every remote entry). Disabling by name therefore cannot cover this channel, and no flag disables custom agents (`--no-custom-instructions` does not). The only off-switch that exists is the documented config setting `customAgents.defaultLocalOnly`, which short-circuits the loader before the remote listing. That setting lives in **two** files, not one: 1.0.64 migrates user settings between `config.json` and `settings.json` at startup (verified live — an opt-out written into `config.json` was applied for that run and then moved into a `settings.json` copilot created, value intact). So the harness reads the opt-out from either file (a *disagreement* between them fails closed: which wins is decided inside a native module, not readable JS) and masks **both** under isolation with the same sanitizer — otherwise a key stripped from one rides back in through the other, which the overlay symlinks wholesale unless it is declared a mask. Reading only `config.json`, as an earlier revision did, also made the opt-out *evaporate*: copilot relocates the key, so the next run finds it missing and fails closed telling a non-isolated user to set the key they already set. One ordering detail matters for the harness: copilot **executes** `git rev-parse` (child PATH) to pick that boundary *before* it globs the agent dirs, so anything that runs as `git` there acts inside the harness's preflight-to-launch window (§4). So: isolation masks `agents/` to an empty dir and *forces* `defaultLocalOnly` into the sanitized `config.json`; the argv layer **fails closed** on any discoverable local agent file, and on *any* run whose enumerable config doesn't provably carry the opt-out. That gate is **unconditional** — not "in a git repo" — because deciding it would mean *executing git*, which copilot then executes again at launch; §4 explains why that two-execution gap is refused here exactly as it is for the ODR command (non-isolated runs need the opt-out set in the real `config.json`; the error says exactly that).
- **`extra_args` can reopen configuration channels after enumeration**: 1.0.64 accepts `--additional-mcp-config` (merges more servers for the session), `--agent` (selects a custom agent whose mcp-server *names* are unenumerable, see above), `--plugin-dir` (loads a plugin from any dir), the hidden `--config-dir` (repoints the whole config home), the hidden `--prefer-version` (runs a *different* cached CLI build, voiding every 1.0.64 fact this design rests on), and `-C` (changes copilot's cwd *before* discovery, invalidating the enumeration's walk). `build_argv` rejects these tokens — exact, `--flag=value`, attached `-C<dir>`, **and combined short-option clusters carrying the flag** (`-sC/tmp` == `-s -C /tmp`, which a leading-`-C` rule would miss) — before spending the enumeration, mirroring the codex vet.
- **Windows ODR registry is a fail-closed gate, not enumerated** (1.0.64 bundle, "ODR load/convert" pipeline): the registry value `Command` under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Mcp` names a command line; copilot executes `<that command> mcp list`, parses the JSON `servers` array, and registers each named server. No flag/env/setting disables the mechanism and nothing lets the harness intercept copilot's load. An earlier revision executed the command *itself* and pre-disabled the resolved names, but the two executions are **independent**: a stateful or time-varying command can hand the harness listing `A` and copilot listing `B`, leaving `B`'s servers enabled — matching cwd/env/bitness cannot close a two-execution gap. So a **populated gate fails the whole invocation closed** (cell, probe, judge alike); only an absent/blank gate lets a run proceed. What must still match copilot is the gate **detection**: the value is read with `KEY_QUERY_VALUE | KEY_WOW64_64KEY` — the QUERY-ONLY access copilot's `RegGetValueW` uses (not the broader `KEY_READ`, which a query-only ACL would deny, making the harness reject a host copilot reads fine) plus the 64-bit view flag matching copilot's read (a 32-bit process's *default* view is the redirected WOW6432Node one, where an absent key would fake the gate "off") and judged blank-vs-populated with copilot's own **ECMAScript** `value?.trim()` + falsy test (U+FEFF is JS-space, so a lone-BOM value reads gate-off exactly as copilot sees it; U+001C–U+001F/U+0085 are not, so a value of only those reads gate-on). A 32-bit harness process on win32 fails closed outright regardless — WOW64 file-system redirection (System32 → SysWOW64) desyncs the config FILES it reads from 64-bit copilot's view (the ODR command is copilot's to launch, not the harness's).

### antigravity (agy) 1.1.1
- No MCP flags at all (verified absence). Discovery is purely file-based: `~/.gemini/config/mcp_config.json` — `{"mcpServers": {name: {command, args, env}}}` for stdio, `serverUrl` (SSE) or `url` for remote (verified via embedded docs + changelog).
- Plugins are a second file-based channel: "MCP Servers defined in `plugins/<name>/mcp_config.json`" (verified via embedded plugin docs) — hermetic-off must mask that file inside every installed plugin too. `~/.gemini/config/plugins.json` can additionally register *external* plugin directories by absolute path (their MCP configs live outside every masked tree), so that registration file is masked as well.
- The **run workspace** is a third channel (verified 1.1.1 with sentinel stdio servers launched at session start): `--add-dir` exposes it, and agy recognizes **four** customization roots — `.agents/`, `.agent/`, `_agents/`, `_agent/` — loading, per root, `mcp_config.json`, every `plugins/<name>/mcp_config.json`, and `plugins.json` (the entries/inherits registration schema from the embedded json_configs.md — an *external* plugin dir registered from a workspace `plugins.json` had its MCP server launched, verified). Ancestors of the workspace are NOT scanned (verified). A seeded scenario file could re-enable MCP, so the runner neutralizes all sixteen patterns after seeding (`workspace_config_masks` — per root: `mcp_config.json`, `plugins/*/mcp_config.json` plus its dot-inclusive companion `plugins/.*/mcp_config.json` (glob's `*` skips hidden names, and agy loads dot-prefixed plugin dirs too, verified), and `plugins.json`), and model probes anchor `--add-dir` to a fresh private 0700 temp dir instead of the shared system temp root (whose planted `.agents/` would load — `/tmp` is world-writable on Linux).
- **No tool-allowlist mechanism** (verified absence) — documented gap.
- Transcript tool names look like `mcp_<server>_<tool>` with single underscores (inferred from binary strings).

## 3. Scenario schema extension

New optional top-level field on evals and scenarios. Absent ⇒ MCP hermetically off (the default today, post-Phase-0 for all adapters).

```yaml
mcp_servers:                              # dict[str, server]; key = server name = tool namespace
  sliderule:                              # → tools surface as mcp__sliderule__<tool>
    command: python3                      # stdio transport (XOR with url); bare names stay PATH-resolved
    args: [fixtures/sliderule_mcp.py]     # entries naming files under the scenario dir are absolutized
    env:
      SLIDERULE_DOMAIN: slideruleearth.io
      SLIDERULE_API_KEY: ${SLIDERULE_MCP_TOKEN}    # interpolated from harness process env
    tools: [atl06p, atl03x]               # optional allowlist; omit ⇒ all tools

  sliderule-remote:
    url: https://sliderule.example.com/mcp     # remote transport (XOR with command)
    transport: sse                        # http (default) | sse
    headers:
      Authorization: Bearer ${SLIDERULE_MCP_TOKEN}
```

Validation rules (added to `validate_spec`, `spec.py:237-395`, so misconfiguration fails before any tokens are spent):
- Exactly one of `command` / `url` per server; unknown keys → error.
- `${VAR}` interpolation in `env` values, `headers` values, and `url`, resolved from the harness process environment at load time; unresolvable → error naming the variable.
- Every interpolated value is registered in a per-run **secrets set** (used for artifact redaction, §5.3).
- Path absolutization is selective, resolving against the spec's `base_dir()` (same convention as `files:`, `spec.py:159-182`) — the agent runs in a tempdir workspace, so scenario-relative paths would otherwise break. `command` is absolutized only when it contains a path separator *and* names an existing file under `base_dir()`; a bare executable name (`python3`) is left for PATH lookup. Each `args` entry is absolutized only when it names an existing file or directory under `base_dir()`; flags and other non-path arguments pass through verbatim.
- The **CLI-native filter spellings** — `allowedTools`, `enabledTools`, `enabled_tools`, `disabled_tools` — are **rejected** on a server. `tools:` (above) is the harness's portable field; the native spellings are what claude accepts and then **silently ignores** (measured, §6-C2), so passing one through would write a key that does nothing quietly. The error names `tools:` as the replacement.
- `tools:` on an antigravity target → warning ("advisory only").
- **`mcp_servers:` with no isolated HOME → error, where the adapter's MCP-off guarantee is a mask in the overlay** (`Adapter.mcp_off_depends_on_isolation`: copilot, antigravity — implemented 2026-07-28). Declaring servers states what the run's tool surface *is*; without the overlay the user's real MCP configuration loads beside them, so the declared set is a **subset** of what ran and the scenario grades an experiment nobody described. The rule is a property of where the **kill-switch lives**, not of isolation: claude (`--strict-mcp-config`) and codex (per-server disables) hold whatever HOME the child is handed and are left alone — a blanket "`mcp_servers` + `isolated: false` → error" would have refused the one configuration that works today for no safety gain. The classifier is `Adapter.mcp_off_mechanism`, a **declared tri-state**: `CLI` (claude, codex), `OVERLAY_MASKS` (copilot, antigravity), or `None` for *not determined*. Two earlier cuts were wrong in instructive ways. Deriving it as `bool(isolation_config_masks or plugin_registry_config_masks)` answers "does this adapter *have* a mask" — a different question from "does it *depend* on one" — and refused a complete CLI kill-switch backed by a redundant mask, a shape already in use here (copilot carries masks beside its argv disables). Replacing it with a **boolean** then made `False` mean both *uses overlay masks* and *nobody has ever determined how this adapter keeps MCP off*, so an unclassified adapter was cleared the moment a run had any isolated HOME — by an overlay that materializes nothing for an adapter declaring no masks. Both found in review. `None` is the same not-mapped-is-not-a-claim distinction `contained_home_subpaths` draws, and it fails closed in **both** directions, isolated or not. An `OVERLAY_MASKS` declaration is additionally checked against the masks it names, and against whether those masks have anywhere to *act*: naming the overlay while declaring no masks is a mechanism that does not exist, and so is declaring `plugin_registry_config_masks` with no `global_plugin_registry_subpaths` root to materialize them in — checked **per channel**, not in aggregate, because plugins are a server-discovery channel of their own and a working direct mask covering a *different* channel would otherwise launder an orphaned plugin mask beside it (antigravity declares both kinds, so dropping its registry root was cleared by an aggregate test) — `build_mcp_masked_home` derives its registry list from exactly that field and returns `(None, {})` when it is empty, so the overlay being relied on is never built (found in review). Declaring a mask and the mask having somewhere to act are different claims — and "somewhere" includes the directory the child is actually repointed at: a rooted plugin mask is **not** carried into a custom config home's mirror (both builders forward only rerooted direct masks), so that combination is refused too, pending the routing fix tracked in `TODO_Contained_HOME.md` §6.

  The two `CLI` declarations are **reviewed assertions**, not verified ones, and the code says so. `VersionProvenance` is an audit trail plus a drift warning: an unaudited claude build warns and still runs, and its own witness text states that an empty server list cannot distinguish "the flag worked" from "a newer build grew a server source outside the flag's reach". codex has less than that — `_VERSION_UNREADABLE` records that it cannot identify the build it just executed at all, so its only check is an out-of-band `codex --version`. Nothing in the harness would catch a wrong `CLI`; what the machinery buys is that an unaudited build is visible and that re-establishing the claim has a documented procedure. Note this is unreachable through a shipped adapter: the mask-dependent adapters are exactly the ones that cannot inject, so `validate_mcp_support` refuses them one line earlier. It arms itself the day copilot or agy gains injection. It also closes a hole in the overlay-build guard (§4), whose fail-closed message names `isolated: false` as the documented opt-out — correct for a run that says nothing about MCP, and an escape hatch from the guarantee in the same breath as declaring the surface being guaranteed once one does.
- **`tools:` must never be accepted where it is not enforced.** Each adapter either compiles it to a real filter or the spec fails validation naming the adapter — an accepted-and-ignored allowlist is the exact failure mode claude's own config has, and reproducing it in the harness's schema would be worse, since the scenario author has no way to notice. Where enforcement is snapshot-prevention plus detection rather than hard prevention (claude, §6-C2), that is a documented property of the field, not a reason to reject it.

### Isolation-layer generalization (implemented, Phase 0)

`build_isolated_home` (`isolation.py`) gained a third leaf type — a **config mask**: adapter-declared HOME-relative paths materialized instead of symlinked, as a real file with supplied content (each CLI's accepted empty shape — copilot rejects a bare `{}`, §2), a callable that *sanitizes* the real file, or, with content `None`, an empty real directory. E.g. `isolation_config_masks = {".copilot/mcp-config.json": '{"mcpServers": {}}', ".copilot/installed-plugins": None, ".copilot/config.json": <sanitizer>, ".copilot/settings.json": <the same sanitizer>}`, `{".gemini/config/mcp_config.json": '{"mcpServers": {}}'}`. Two paths can share one sanitizer, and copilot's settings pair must: an unmasked file is symlinked to the real one, so masking only `config.json` leaves `settings.json` — which copilot's startup migration moves the same user settings into — free to supply the very keys the sanitizer strips. `plugin_registry_config_masks` applies the same idea inside every plugin of a registry (agy's `plugins/<name>/mcp_config.json`). Mask paths are validated (relative, no `..`, no drive prefixes, not empty/dot-only). `isolation_config_homes` entries carry the HOME subdir the env var stands in for, so masks re-root into mirrored custom homes (`$COPILOT_HOME/mcp-config.json`). A shared `build_mcp_masked_home` builds a mask-only overlay (skills untouched) for model probes and judge runs, which otherwise execute against the real HOME. One mechanism serves the Phase 0 hermeticity fix and the copilot/agy injection path (Phases 2–3).

## 5. Access control

### 5.1 Opt-in (server level)
Default stays hermetic via the kill-switch column in §4. When `mcp_servers` is declared, only those servers are reachable: claude's `--strict-mcp-config`; codex's per-name `enabled=false` disables for every user server outside the declared set (a full-table `-c mcp_servers={}` override was disproven — it deep-merges, §2) plus `--disable plugins`; copilot/agy's masked user config.

### 5.2 Tool gating (tool level)
Per-server `tools:` compiles to each CLI's native filter — codex `enabled_tools` and copilot per-server `tools` are hard filters (verified). Claude: `--allowedTools` does **nothing at all** to MCP tools under `--dangerously-skip-permissions` — not a soft filter, not advice; the tool stays advertised and executes (measured, not inferred — §6-C2). The mechanism is `--disallowedTools` on the *complement*, which removes tools from the advertised surface entirely, paired with a fail-closed post-run subset check against the run's own init event. That pairing is **prevention for the enumerated snapshot plus fail-closed detection of drift** — not hard prevention against a server that answers the enumerator and claude differently (§6-C2; C3 is the mechanism that would be). agy: no mechanism; validation warns.

### 5.3 Credentials
- `${VAR}` interpolation from the harness process env only; fail-fast at validation; values never committed in YAML.
- Prefer CLI-native env-var **indirection** where it exists (codex `bearer_token_env_var`, `env_http_headers`) — the value then never touches disk or argv at all.
- Scratch config files created `0600`, outside the workspace, deleted post-run.
- **Redaction pass**: every interpolated secret value is scrubbed from `stdout.jsonl`, `stderr.txt`, `events.json`, `result.json` (including recorded `argv`), `report.md`, the archived `workspace/`, and the run-level `summary.json` / `summary.md`. This also covers the case no CLI flag can: a tool *result* echoing a token back into the transcript. Three properties are load-bearing, each of them a defect found in review of the first implementation:
  - **Every spelling, not just the one the author typed.** Matching the raw value against serialized JSON misses the escaped form, and nearly every artifact here is JSON: `a"b` is stored `a\"b`, `ö` is stored `ö`. Structured artifacts are now scrubbed *before* serialization (no encoder in the path); text artifacts match the escaped forms too, since a CLI's own JSONL stream carries them. Not exotic for a credential — base64 contains `/` and `+`.
  - **Copied artifacts, not just written ones.** Redacting at the writers covers only what the harness authors. The agent's `workspace/` is *moved* into the artifact tree wholesale, so a token an MCP result echoed back and the agent saved to a file survived there. Scrubbed on bytes (binary-safe), after grading (never changing what was graded), names as well as contents, and not *through* symlinks.
  - **Run scope as well as cell scope.** `_secrets` is cleared per cell by design; the summaries are written after the last cell and *aggregate* cells, and `RunResult.error` carries a tail of child output — so they scrub against the run-scoped union.
- **The workspace scrub establishes completion or fails the cell** (second review round; the three properties above were each still true and each still incomplete). A traversal is only as good as what it can *see* and what it treats as an object:
  - **Write-and-rename, never in place.** A hardlink shares its inode with every other name pointing at it, so an in-place rewrite reached out of the artifact tree and overwrote an external file with `«redacted»`. The replacement is written beside the original and renamed over it: new inode for the archive, the agent's link target untouched. Refusing to follow *symlinks* never covered this — a hardlink has no target to refuse.
  - **A symlink's target string is archived even though its contents are not.** `readlink` reads it straight back, so a blandly named link pointing at `/tmp/<token>` published the credential as plainly as a file containing it. The target is redacted in place; traversal is still refused.
  - **`os.walk` reports an unreadable directory to `onerror` and then yields nothing for it** — indistinguishable from an empty one, so a `chmod 000` subtree was skipped in silence while the scrub reported success. Owner permissions are repaired before the walk (the harness owns this tree), and anything still unreadable is removed rather than published unchecked.
  - **Names are checked as assembled paths.** A secret containing a separator (`tenant/key`, a URL with credentials) spells itself out across a directory and its child while every individual component looks clean. The component that *completes* the secret is renamed; the prefix, not being a secret on its own, is left alone.
  - **The scrub returns what it could not certify**, and each such path is deleted and named in `RunResult.error`, failing the cell. A scrub that cannot prove a tree is clean must not report success over it — and a silent deletion would be worse than either outcome it is choosing between.
- **The scrub does not trust the shape of its own root, its entries, or its answers** (third review round; each of the five properties above survived, and each was still reachable around). The remaining leaks were all *identity* — what an object is, and whether the tree it lives in is the tree we think:
  - **`os.path.isdir` follows symlinks, so the root itself was a way in.** An agent that replaced its workspace with a link aimed the entire scrub at an external directory and had every file under it rewritten to `«redacted»`. The root is now classified with `lstat`; anything that is not a real directory is dropped whole and replaced with an empty one.
  - **The permission repair wrote through a hardlink.** Reading a `000`-mode file needs a `chmod`, and a `chmod` changes the *inode* — which is exactly what the previous round established a hardlink shares. Write-and-rename fixed the bytes and left the mode as an unguarded second channel to the same object. A multiply-linked file that cannot be read is now quarantined instead: dropping our name for it leaves every other name alone.
  - **"Not a directory" is not the same claim as "a readable regular file."** The dispatch treated every non-directory as one, so a FIFO made `open(...).read()` wait for a writer that never came and hung the run rather than failing it. Entries are classified with `lstat`; FIFOs, sockets and devices hold no archivable bytes and are removed and named.
  - **Not all of a file's bytes are in the file.** `xattr -w com.example.token <secret> note.txt` parks a credential in metadata that `cat` never prints, `cp -p`/`ditto`/`rsync -X`/zip all preserve, and a scrub reading contents reports `lost == []` over. Attribute names *and* values are scrubbed, on files, directories and symlinks (`xattrs.py`; CPython exposes the `os.*xattr` family on Linux only, so darwin goes through libc).
  - **A quarantine that cannot delete was reporting a deletion.** `chflags uchg` makes a file unremovable; the old code swallowed the `unlink` failure and returned the path as *lost*, which promises the artifact is gone. Removal now escalates outward-in — parent directory first (inside the tree, never hardlinkable elsewhere), then the entry's own flags — and the result is the answer to `lexists`, not the absence of an exception. What still cannot be removed raises `ScrubFailed`, whose sentence says the secret is **still on disk** rather than claiming a removal.
  - **A symlink is not an unshareable object.** `os.link(src, dst, follow_symlinks=False)` works on macOS, so an external symlink hardlinked into the workspace shares its inode with the archived name and an in-place `setxattr` rewrote the outside one's metadata. Symlinks are now replaced on a fresh inode like regular files (`_scrub_link`) — target and attributes rebuilt, renamed over — rather than edited.
  - **One pass of assembled-path reasoning can create the leak it just removed.** With `secretA` and `tailpart/childsecret` both declared, renaming `secretAtailpart` to clear the first spelled out the second across the new parent and a child the bottom-up walk had already gone by. Per-component scrubbing and assembled-path scrubbing are now separate phases, and the second runs **to a fixed point** — shallowest offender first, since renaming one component cleans every path beneath it — with a bounded round count that falls back to deletion rather than looping.
- **The scrub's reach is the archived tree, so the agent must never have a path into it** (fourth review round). Two of that round's three findings were still the scrub's; the third was upstream of it and larger: `exec_ws` — the directory the agent actually runs in — was relocated to a detached tempdir **only under `self.isolated`**. A `--no-isolated` cell therefore ran with its cwd at `cell_dir/workspace`, and `../agent-created.txt` published the raw secret in `cell_dir`, which `_scrub_tree` never examines because only `workspace` is archived. A cwd is a place the agent can *write*, not only one it can `list_dir`; `--no-isolated` means "see my real HOME and installed skills" and never meant "run inside the results directory". The relocation is now unconditional, and `exec_ws` is nested one level inside the harness's own tempdir so that `..` reaches a directory that is deleted whole rather than published. HOME isolation and execution-directory isolation answer different questions and no longer share a flag.
  - **A credential directory is deleted when it is gone, not when the call returns** (fifth review round). Both tempdirs that carry secrets — the agent's `exec_root` and the MCP `mcp_scratch`, whose `mcp.json` holds the interpolated `${VAR}` values in the clear — were removed with `shutil.rmtree(..., ignore_errors=True)`. An agent that `chmod 000`-ed its own execution directory left both secret-bearing files on disk, and the cell said nothing. Both now go through `_purge`, the same verified outward-in removal the workspace quarantine uses, whose result is `lexists`; a directory that genuinely cannot go **fails the cell** with the path named, before `_secrets` is cleared. `result.json` is re-written at that point too: it is serialized at step 6, long before the workspace is moved, so a note appended afterwards had been reaching `report.md` and nothing else.
  - **Absence and refusal are different answers.** `_scrub_tree` opened with `except OSError: return []`, so a cell directory at mode `000` produced a clean bill of health over a workspace still holding the secret. Only `ENOENT` is clean now; anything else repairs through the parent (`cell_dir`, which the harness created and owns) once, and raises `ScrubFailed` if that is not enough.
  - **A finding held in a frame the exception unwinds is a finding nobody reads** (sixth review round). The verified removal was right; where its answer *lived* was not. The scratch-dir failure was collected into a `purge_notes` local of `_run_cell_body`, and every path out of that function that is not a `return` discards it: `execute()` raising transfers straight to `_failed_cell`, which had no way to name a directory the body had created. Review made both happen at once and got a cell reporting `RuntimeError` and nothing about the `mcp.json` still on disk; the same loss followed any raise between the agent exiting and the notes being applied. Ownership now sits in `_CellCleanup`, held by `_run_cell` — the frame with the `try/except/finally`, the one an exception in the body cannot unwind. The body *registers* directories and purges each at the moment that suits it; `_failed_cell` sweeps whatever is left and drains the accumulated notes onto the crashed cell's own result; the outer `finally` warns about anything no result was written for. The guard also now starts where the directory does rather than at `execute`: resolving `${VAR}`s and building `RunOptions` sit inside the same `try`, because a raise from either used to leak the scratch dir and the isolated home outright.
    - **Reading a finding must not destroy it either** (seventh review round). The first version of that handoff drained on read, which put the note back in a local — one frame later than the bug it replaced, and just as lossy: review made the `result.json` rewrite raise between the read and the write, and the scratch failure vanished from a cell that then reported only the write error. `pending()` is now non-destructive and `acknowledge()` is called *after* the artifact writes return, so a note is forgotten when it reaches a reader rather than when it is handed to something that intends to carry it. The distinction is load-bearing one write further out too: acknowledging after `result.json` but before `report.md` looks safe because the note is on disk, right up until the crash path rewrites `result.json` from a rebuilt result that no longer has it. Whatever is still held when `_run_cell`'s finally runs is exactly what no artifact recorded, and gets echoed there.
    - **The isolated HOME is a resource on the same terms.** It was built at step 4 and removed by a guard that began at step 5, so anything raising in between — the overlay build, a progress update, the effort resolution — left `ase-home-*` behind and unnamed. It is now registered the moment `mkdtemp` returns, including on the build-failure paths, and its severity travels with the registration.
    - **What a directory contains is not decided when the harness creates it** (eighth review round). That severity was first written as `fatal=False` — the isolated HOME holds config masks and symlinks — which described its *initial* contents. It is `$HOME` for a child that can write: review's agent copied the resolved token into it, the removal then failed, and the cell passed while its warning stated that no credentials were present. A cell that resolved a `${VAR}` has handed the agent somewhere to put it, so from that point the HOME is registered exactly like the scratch dir. Re-registering a path replaces its severity, which is the mechanism rather than a convenience; the sentence claims *reach* ("could have written") rather than asserting contents the harness stopped controlling at launch.
    - **The last safe moment to forget is the one with nothing left to go wrong.** Acknowledging after the artifact writes was still early: the judge artifacts and `progress.done()` come after them, and a raise there lands in `_failed_cell`, which *rewrites* `result.json` from a rebuilt result — so an early acknowledgement erases the finding rather than merely omitting it. `acknowledge()` is now the last statement before the return.
    - **The overlay bounds what the model can read, and never bounded what it can write** (ninth review round). The severity fix above was still reasoning about the overlay as a container. It is not one: `_overlay` passes every unmasked real-HOME entry through as a symlink, so `$HOME/.cache/x` *is* `~/.cache/x`. Review wrote a token through one and watched the overlay's removal succeed while the token sat in the real home — outside every directory this runner deletes and outside the workspace it scrubs. Deleting a symlink certifies nothing about its target, and the harness will not go hunting through a user's home afterwards, so neither "run it and scrub" nor "run it and delete the overlay" is available. A cell that interpolates a `${VAR}` is therefore **refused** when `home_write_escapes()` finds any symlink leading out — *any*, because the first version of that check filtered on target type, reasoning that a file symlink can be clobbered but not used to plant a new file. Clobbering is the leak: review symlinked a `state.json`, the gate reported nothing, and writing through it replaced the real file's contents with the token. A dangling symlink is worse, having no target to classify while a write creates one. The question is whether a name leads out of the tree the harness can account for, and that has one answer for all three. Both sides of that comparison are canonicalized (`realpath` + `normcase`, not `abspath`): on macOS `/var` is a symlink to `/private/var`, so a link pointing inside its own overlay was reported as an escape — a safe error direction that would nonetheless have made the structural lifting condition unreachable, since a materialized HOME is where safe internal links start appearing — and refused when there is no overlay at all, since `isolated: false` hands over the real home outright. The check is structural rather than a blanket ban, so materializing the HOME's writable state lifts it without this code being removed; that materialization is the follow-up that re-enables credential-bearing runs.
    - **Declaring a server is not handling a secret.** The same round: the severity upgrade was gated on `spec.mcp_servers` being present, so a cell declaring `{"echo": {"command": "/bin/echo"}}` — nothing interpolated, no credential anywhere — failed on a stubborn HOME while claiming the agent could have written "resolved credentials". Gating now reads `interpolated_refs()`, a syntactic `${VAR}` check on the *declaration*. Deliberately not `bool(secrets)`: the redaction set omits values under `MIN_REDACTABLE_LEN` because rewriting a three-character string would corrupt unrelated text, and a short credential is still a credential. "What can be scrubbed" and "does this cell handle secrets" are different questions that had been sharing one answer.
    - **A finding that cannot be recomputed must not be recomputable-in-theory either.** The scrub's verdict stayed a body local because it reads like a value any caller can re-derive. It is not: the scrub *deletes* what it could not certify, so a raise after it ran reached a `_failed_cell` that rescanned a tree which was clean by then, and the evidence deletion went unrecorded. It travels through `cleanup.note()` on the same protocol as the purge failures; the rescan in `_failed_cell` still happens (the body may have raised before scrubbing) but adds rather than replaces.
- **Post-run warnings are recorded, not just printed** (`notices.py`). `execute()` archives the *child's* stderr; the harness process's own was written to a terminal and nowhere else, so a warning explaining an inexplicable result was itself unreadable afterwards — the claude server-health message said assertions would "fail for a reason the results will not show" while being that reason. Warnings now land on `RunResult.warnings` → `cell.json`, `report.md`, `summary.json`. The sink is **thread-local**: cells run in parallel and `sys.stderr` is process-global, so a `redirect_stderr` at the call site would file one cell's findings on another's result. Terminal rate-limiting (drift warnings, once per version) governs the *echo* only — every affected cell records it, or a matrix would show cell 1 carrying a finding that applies equally to cells 2..n.

## 6. Decision points

**A. Config delivery for claude/copilot: inline argv JSON vs scratch file vs workspace `.mcp.json`.**
Inline JSON leaks resolved secrets into `result.json` (argv is archived) and needs shell-safe quoting. Workspace files are archived and inlined into `report.md`; claude ignores workspace `.mcp.json` under `--strict-mcp-config` anyway. → **Scratch file** in the per-cell tempdir, deleted post-run.

**B. Codex delivery: `-c` overrides vs materialized `$CODEX_HOME/config.toml`.**
`-c` needs no isolation surgery, keeps HTTP secrets env-indirect natively, and its one exposure (stdio env literals in argv) is covered by redaction. A materialized config home means converting `.codex` from a wholesale symlink into a masked dir with a merged TOML (preserving auth) — heavier and riskier. → **`-c` overrides**, with config-home materialization as the fallback if TOML array/inline-table `-c` values prove unreliable (verification task).

**C1. Allowlist shape: flat top-level `allowed_tools: [mcp__sliderule__*]` vs per-server `tools:`.**
Flat matches claude's flag but forces claude's naming onto codex/copilot (whose native filters take bare tool names per server) and repeats server names. → **Per-server `tools:`**; adapters compile to their native form. A flat form can be added later without breakage.

**C2. Claude gating strength: advisory vs hard.** — **resolved by measurement (2026-07-22, claude 2.1.113), and the answer inverted the ranking.** All three options were run against the `fixtures/echo_mcp_server.py` stdio server (tools `echo` + `add`), allowing `echo` and instructing the model to call `add`:

| option | result |
| --- | --- |
| (a) `--dangerously-skip-permissions` + `--allowedTools mcp__echo__echo` | **No gating whatsoever.** `mcp__echo__add` stayed in the init `tools` list, was called, returned `42`. Advisory is not even advisory here — nothing carries the preference to the model. |
| (b) `--permission-mode dontAsk` + `--allowedTools mcp__echo__echo` | **Hard, at call time.** The tool is still advertised, the model still attempts it, and the *call* is refused (`is_error: true`, "running in don't ask mode"). But the allowlist governs **every** tool: with only the MCP tool listed, `Write` and `Bash` were both denied and the file never written. Enumerating the whole built-in surface is version-brittle, and it changes the agent's capabilities — which makes a gated cell non-comparable with an ungated one, the exact axis `Runner._consistency` exists to protect. |
| (c) `--dangerously-skip-permissions` + `--disallowedTools mcp__echo__add` | **Hard, at advertisement time** — strictly the cleanest. The denied tool is **absent from the init `tools` list**; the model never learns it exists and reports the server "only exposes an `echo` tool". Built-ins are untouched. |

Two further measured facts shape the mapping: `--disallowedTools` accepts wildcards (`mcp__echo__*`), and **deny beats allow** — `--disallowedTools "mcp__echo__*" --allowedTools "mcp__echo__echo"` removed *both* tools. So the tempting "deny the namespace, re-admit the allowlist" is not expressible. And `--mcp-config` has no native per-server filter: `tools`, `allowedTools`, and `enabledTools` in a server object are all **silently ignored** (accepted, not rejected — so a plausible-looking key in a hand-written config does nothing quietly, which is worth a validation error on the harness's own schema).

→ **(c)**, with the deny set computed as the *complement* of `tools:` — and with the strength of that guarantee stated in two parts, because the original objection to (c) is **not** fully closed. An earlier revision of this section said it was "closed the same way every other Phase 0 gap was". That cited the precedent while dropping the qualifier that made the precedent honest: those gaps were *classified* as detection, not closed (§8's copilot audit says so in as many words), and the same classification is owed here.

Computing a complement requires the server's full tool list, which is not statically available at argv-build time. The harness gets it by starting the server and calling `tools/list` itself — a **second, independent server instance** from the one claude launches. That is precisely the two-execution gap the Windows ODR registry gate and copilot's `git rev-parse` window are refused on: a stateful or time-varying server can advertise `[echo]` to the enumerator and `[echo, add]` to claude, and `add` — never having entered the complement — is advertised and callable. The post-run init check *detects* exactly that, and detects it exactly (denied tools are absent from init's `tools` list, measured above; claude advertises its full surface unconditionally, so there is no idle-object equivalent of codex's ABA hole). But it detects it after the call may already have had effects, under `--dangerously-skip-permissions`. Full init visibility closes an evidence gap, not an enforcement window.

So:
- **Prevention** for the tool set observed at enumeration — hard, advertisement-time removal, not advice.
- **Detection, fail-closed**, for anything appearing afterward: any advertised `mcp__<server>__*` outside the declared allowlist fails the cell.

The harness therefore cannot promise an off-list tool was never *callable*. It promises that no run **reported clean** had an off-list tool advertised to its model — deliberately the same shape, and the same words, as copilot's `verify_post_run` guarantee (§4). Two consequences worth naming: enumeration **starts the declared server an extra time**, so a server with startup side effects performs them twice and a remote one is contacted twice with the scenario's credentials; and the gap exists only for scenarios that actually use `tools:` — omit it and there is no complement, no enumeration, and no second instance.

Hard prevention against a server the scenario author does not control needs the filtering proxy in **C3**. `tools:` on claude is not a security boundary against a hostile server, and neither the schema docs nor the error messages may imply it is.

**C3. A harness-owned filtering proxy — designed, probed, and now BUILT (#94–#96, #98, #100–#103); the only mechanism that is both hard and uniform.**
Rather than compiling `tools:` to four different native filters, the harness could launch its own stdio shim as the `command` the CLI actually starts; the shim spawns the declared server, filters `tools/list` responses down to the allowlist, and refuses off-list `tools/call` at the wire. That closes C2's drift window outright — there is exactly **one** server instance and the harness sits inside the connection, so there is no second execution to disagree with — and it is the only thing that would give **antigravity** tool gating at all (§2: no native filter exists there; today the schema can only warn). It would also produce wire-level MCP telemetry that no CLI reports uniformly, which is the same reason `--output-format json` became load-bearing for copilot.

Deferred out of Phase 1 for two reasons: it puts harness-authored code in the request path of every gated run, where a bug is a silently wrong eval rather than a loud failure; and remote servers need it to be a transport *bridge* (stdio in, HTTP/SSE out), which is materially more than a pipe pump. → **Phase 1 ships C2's native mechanism with C2's stated guarantee.** Revisit before any scenario points `tools:` at a server its author does not control, and revisit for agy regardless — that adapter has no other path to tool gating. **The mechanism is now designed in §10** (stdio only in the first cut; remote `tools:` stays refused), and both gating probes are answered: **C3-0** and **C3-1** in §9. Neither deferral reason has gone away — the first is exactly why §10.5 makes the proxy fail loud rather than degrade — but they became constraints on how it was built rather than reasons not to. **The build is done**: the dual-era fixture (#98), the decision layer (#100), the ending model (#101), the audit types and their verdict (#102), and the I/O half with its guardian and its wire-level driver (#103). **The adapter integration has now landed for claude**: a server declaring `tools:` is replaced in the CLI's MCP config by `mcp_proxy_io.py`, which is handed the real command in its own 0600 config, and `verify_post_run` calls `mcp_audit.log_verdict()` on the audit log the proxy wrote. `mcp_tool_filter` on claude is therefore `"proxy"` rather than `"unbuilt"`, and a gated STDIO server runs today. A gated REMOTE server still does not — that is the transport bridge, and it is untouched by this.

**D. Where secrets interpolate: harness at load time vs CLI-native expansion.**
CLI-native keeps values off disk but is inconsistent (copilot/agy have nothing). → **Hybrid**: harness interpolation as the uniform contract + fail-fast validation; adapters use native indirection where available (codex); redaction pass regardless.

## 8. Phasing

- **Phase 0 — hermetic hardening** (no schema change; fixes today's leaks). **Implemented**, revised across several review rounds: codex passes `--disable plugins` and disables each configured server by name on argv, enumerated via `codex mcp list --json` run with the child's exact cwd/env (trusted-project configs, `$CODEX_HOME` — §2), strictly validated, uncached, with **no offline fallback** (any enumeration failure fails closed), a **post-verify** that re-runs codex's own view with the overrides applied and fails closed if a managed/MDM layer keeps any server enabled, and a hard reject of config-channel `extra_args` (`-c`/`--config`, `--profile`/`-p`, `--cd`/`-C`, `--enable`) that would reach past the verified state (§2); copilot masks `mcp-config.json` (valid empty shape) + `installed-plugins/` + sanitized `config.json` **and** `settings.json` under isolation, mirrors `COPILOT_HOME` (resolving the home from `%USERPROFILE%` on win32, `$HOME` elsewhere), and disables enumerable servers by name on argv — user config (child's env — a relative `COPILOT_HOME` anchored to the child's cwd where copilot itself resolves it, a POSIX set-but-empty `HOME` preserved so `<child cwd>/.copilot` is enumerated as copilot's Node `homedir()` behaves, an empty `COPILOT_HOME` treated as unset like copilot treats it, all verified 1.0.64; win32 home resolution via a fully-qualified predicate rather than `ntpath.isabs`, so driveless-rooted homes anchor to the child cwd's drive, complete UNC roots (the extended `\\?\UNC\server\share` form included) and device-namespace paths whose `ntpath.join` provably opens the same FILE as copilot's Node join — byte-identical under an exact-literal already-canonical `\\?\` (incl. a volume-GUID root, one trailing `\` allowed; its open skips normalization), reconverged by Windows' open-time normalization under `\\.\` forms outside the shared rejections — are accepted, and drive-relative homes, bare drive-letter device drives (their joins drop the separator), bare or incomplete namespace roots (`\\?\`, `\\?\UNC\server\` — joins on some Pythons double the separator vs Node's; where they coincide the rejection is conservative), incomplete ordinary-UNC roots (`\\`, `\\server\` — Node resolves a bare `\\` from the child drive's root while the harness's join names nothing), terminal-colon roots (`\\?\foo:`, `\\srv\share:` — `ntpath.join` glues the child name on where Node inserts the separator;   The set and the HEALTH are two axes, not one, and the reason is the whole design. Review's first pass found the single-axis version manufacturing both of the states it exists to prevent: two cells whose witness named `echo` with no status compared equal and reported `verified`, while a `connected` beside an unstated one reported `drift` — agreement and difference invented out of the same silence. Unstated health is neither.

  What makes a two-axis split work rather than just relocating the problem is a **third** state, and it is a property of the *source*:

  | source | names | health |
  |---|---|---|
  | witness (`system`/`init`) | servers the run HOSTED | stated per server; any one missing ⇒ the cell's health is **unknown** |
  | argv (`mcp_servers_seen`) | servers the invocation DISABLED | **nothing to state** — they never ran, so there is no health to be unknown about |

  Collapsing those last two is the tempting mistake in each direction: treat argv as unknown health and every codex and copilot matrix parks at `unverified` forever over a question that cannot be asked about a server that was never started; treat unstated witness health as known and the silence gets a vote.

  Two axes means **two verdicts**, published separately and combined only in `comparability`. A first cut had `mcp_server_set_verified` require both, which silently narrowed a field consumers already read as a statement about the SET: a matrix reported `mcp_server_sets: [["echo"]]` and `mcp_server_set_unknown_cells: 0` beside `set_verified: false`, when the set was never in doubt — what nobody stated was whether those servers worked (found in review). `summary.json` therefore carries the set (`mcp_server_sets`, `mcp_server_set_unknown_cells`, `mcp_server_set_verified`) and the health (`mcp_server_states`, `mcp_server_health_unknown_cells`, `mcp_server_health_verified`) side by side.

  Health is a claim **about** a server set, so it is only compared within a uniform one — in both directions. Health values must carry the names they belong to, or `echo failed, other connected` would compare equal to its mirror; that makes a difference in the *set* propagate into this axis, so `echo(connected)` beside `other(connected)` announced health drift as well, asserting a difference in whether servers worked when only their identity changed (also found in review). The agreement side needs the same gate for the same reason: two cells that each disabled a different server both have nothing outstanding and so compare equal, and a green `health_verified` there would stand in for a comparison whose two cells share no server at all.

  Three further things the implementation had to get right:

  - **`None` is not `()`.** A run that crashed before its init event, or whose event was reshaped, reports `None` — "did not say" — not the empty set. Collapsing them lets a cell that established nothing contribute agreement. The distinction survives into `result.json` via `witness_json`, where `null` and `[]` mean the same two different things.
  - **Named is not usable.** Two cells both listing `echo`, one `connected` and one `failed`, did not run against the same tool surface — the distinction the per-cell witness already draws, now at matrix scale, and reported on its own drift line rather than as `varied: [echo]; [echo]`.
  - **Per-cell, not only aggregate.** `RunResult.to_dict()` records `mcp_servers_witnessed` and `cli_version`; the aggregate lists the distinct states a matrix contained, but without the per-cell record a reader who saw two of them had to re-parse raw stdout to learn which cell produced which — the exact re-derivation the aggregate exists to spare them.

  And one that is about the reporting path rather than the answer: **a finished matrix must stay reportable.** Adapters build the witness value themselves, so entries can arrive as lists, dicts or bare scalars — and `_spread` deduped through `set()`, which is not merely unordered on those but undefined, raising `TypeError: unhashable` while describing a run that had already finished. Entries are normalized to plain scalar tuples at ingestion *and* `_spread` dedupes by `repr`; either alone suffices, which is why the mutation covering it has to remove both.

  This is comparability reporting and never a safety decision: hermeticity is still decided by `verify_post_run` reading the same event, which keeps the standing rule (a fact learned from the run may *warn*, only the runtime contract may *pass*) intact. Malformed telemetry is therefore an unknown here rather than a failure — `parse` must not raise — while the identical reshape still fails the run in `verify_post_run`.

C3-2 says no shipped CLI would be refused, which turns that from a gamble into a priced trade: nothing in the fleet pays for it today, and the day one of them pipelines the answer is the defer action.

   Side confirmations from the same runs, all consistent with C3-0/C3-1 under the **new** read path: agy opens `server/discover` → `subscriptions/listen` → `tools/list`, copilot enumerates `tools/list` twice (progressToken 0 then 1), codex and copilot shut down with `SIGTERM`, and agy's graceful-closure write lands on a departed peer (`broken_pipe`).

8. **C3-3 — does any CLI REUSE a request id on one connection?** — **open, and it costs nothing extra.** §10.4 spends an id for the connection once it has reached the server, which refuses a client behaviour the specification permits: "the request ID MUST NOT match the ID of any other request the sender has issued and **not yet received a response for**" leaves reuse *after* a response legal. §10.5's rule cuts both ways, so a strictness that fails a conforming CLI is a defect, not caution — and the belief that every id allocator is a monotonic counter is an assumption about the fleet, exactly the kind C3-0 and C3-2 both overturned when measured.

   `tools/probe_mcp_pipelining.py` carries the reading: the shim logs a **structured, canonicalized request id** for every request it parses, so the id sequence comes out of the C3-2 run rather than a second one. Two details that are the difference between a measurement and a decoration, both found in review:

   - **The ids are compared as the PROXY identifies them** — `mcp_proxy.request_id_key`, exported for exactly this. Deduplicating on `repr` calls `1` and `1.0` distinct, and `0` and `-0.0` distinct, which are precisely the pairs §10.4 treats as one id: a CLI whose reuse the proxy would refuse was reported as not reusing at all. The shim cannot import the proxy (CLIs spawn it with only the stdlib reachable), so it keeps a copy of the rule and `verify_mcp_fixtures.py` asserts the two agree on the cases that distinguish them.
   - **The id is logged from the parsed message, not recovered from the `rx` diagnostic**, which truncates at 4096 characters. Reparsing that dropped any longer request entirely, and a measurement that silently omits requests cannot answer a question about reuse. E15 drives a 9 KB request and asserts both that its id is recorded and that the `raw` record really was truncated, so the case is exercised rather than assumed.
   - **A REPEATED ID IS NOT AUTOMATICALLY THE BEHAVIOUR BEING PRICED**, and this is the subtlest of the three. An id repeated while the first request is still *unanswered* is a live duplicate, which JSON-RPC forbids outright and the proxy refuses as `duplicate_request_id`; only a repeat *after* the response prices §10.4's stricter rule. Counting any repeat reported a client that pipelined `ping(1)` behind a held `initialize(1)` as proof that §10.4 "refuses a client behaviour the spec permits" — when the spec forbids that client's behaviour and the proxy refuses it on separate grounds (review, sixth round on PR #100).

     Telling them apart is a question about **wire order**, which is the only order a proxy in the stream can see — and which, it turned out, this instrument cannot establish at all. Three attempts got closer without getting there, and all three are worth recording:

     1. *Log arrivals from the main loop.* That is **processing** order, and a pipelined request lands in the buffer before the response is written but is processed after it — so the live duplicate read as post-response reuse.
     2. *Log arrivals from `_fill`, the read helper.* Better, but `_fill` is still called **on demand**: outside the held-`initialize` window the shim answers the current request before asking for more input, so two requests that both crossed the wire before the response was written were still logged `req, resp, req`. **Nothing that reads on demand can observe when bytes it has not asked for arrived** (review, seventh round on PR #100).
     3. *Drain continuously.* A daemon reader thread owns the only buffer, announces each line as it lands, and the main loop consumes from the queue it fills. `_send` logs the response id **after** the write succeeds — C3-1 established that agy is gone by the time the graceful closure is written, so logging first recorded an answer no client ever received.

     Attempt 3 is what ships, and it is still not wire order: the reader thread and the main thread log independently, so a request can sit unread in the pipe while the response goes out. That is why the reading concludes nothing — see the paragraph above. E15 drives all of it live: the held window, the ordinary case with no window (which is where attempt 2 failed and which the earlier E15 could not reach, because `_measure_pipelining` happens to drain continuously), a departed reader, batches, malformed notifications and malformed ids.
   - **Only ids the proxy would correlate on enter the timeline.** `_announce` accepted any non-null method and id, while the proxy accepts a valid `RequestId` inside a valid envelope. A list id is unhashable and crashed the reader; `true` followed by `1` manufactured a reuse out of nothing, because Python aliases them and JSON-RPC does not. Malformed traffic is logged as its own event — a finding about the client, not an input to the price. Admission is the proxy's ENTIRE envelope taxonomy, not the request branch alone: a batch and a malformed notification are equally fatal to the proxy and were producing no marker at all. `_envelope_shape` and `_valid_request_id` are both checked against `mcp_proxy.classify_envelope` and `valid_request_id`, the same anti-drift device as `_id_key`.
   - **Classification stops at the first live duplicate, because the proxy does.** `Fail` is terminal (§10.5): the connection is torn down, so a later reuse never reaches the rule being priced. Counting it anyway reported that §10.4 "causes failure" using traffic that would never arrive.

   **THIS RUN CONCLUDES NOTHING, IN EITHER DIRECTION, AND CANNOT BE MADE TO.** That took three rounds to arrive at, each removing one more thing the reading was thought to establish:

   - *The negative was never usable.* Pipelining is exercised exactly once per connection — the `initialize` window either has traffic in it or it does not — so one clean run per CLI settles C3-2. Allocation is not like that: a run that sends ids 0 and 1 says nothing about the fourth request, and a scenario cell runs far longer than a probe. An earlier version treated two distinct ids as a completed answer and concluded the rule "costs the fleet nothing", which is a claim about sessions it never observed (fifth round).
   - *The positive is not usable either.* Classifying a repeat requires knowing whether an arrival preceded a response, and **no observer inside the server can establish that**. The reader thread and the main thread log independently; bytes can sit unread in the kernel pipe while the main thread writes a response. Continuous draining makes the favourable interleaving likely, not certain — stopping the process, writing a second request on a live id, and resuming produced `req, resp, req` in 1 run of 20, a live duplicate reported as legal reuse (seventh round).

   So the probe **reports and does not conclude**: it prints the sample, surfaces repeats as `UNCLASSIFIED` for a human to look at, and says why neither direction follows. Continuous draining stays — it removed a systematic error and E15 pins it — but "usually correct" is not what a price is made of.

   **Pricing needs the sequential stress workload**: a driver that waits for each response before sending the next request, so the ordering is a property of the client's behaviour rather than of the server's scheduling, over enough requests to exercise an allocator at cell length. That probe is still to write. **Until it exists the spent-id rule is a deliberate strictness, not a priced trade**, recorded here rather than in a comment claiming otherwise. What bounds the risk is that the refusal is a named anomaly (`spent_id_reuse`), so a CLI that reuses ids fails loudly on the first run against the real fleet instead of quietly.

   Two further admission rules, both from the same round:

   - **The whole envelope, not just the id.** A JSON-RPC 1.0 `ping(1)` carries a perfectly good id, so id-only validation admitted it — while the proxy terminates on that frame as `MALFORMED` and never reaches an id rule. Worse, the shim *answers* the bad frame, as a conformant server should, and recording that response marked the id answered with no matching arrival: a repeat manufactured out of a single request. A malformed frame now enters the timeline in position as a terminal marker, a response is recorded only for an id that was admitted, and malformed traffic reaches the probe's result and its exit status instead of dying in a temp log.
   - **A failed read is not a closed stdin.** `_reader` swallowed every `OSError` into an empty chunk, so the main loop logged `stdin_eof` and a clean terminator — C3-1 would have published an instrument failure as "this CLI shut the server down cleanly", which is precisely the conclusion that probe exists to draw.

9. **C3-4 — does the SlideRule server issue a session, and will it terminate one on request?** — **open, and it blocks a decision rather than an implementation.** §10.10 makes a retained session anomalous, so a conformant server that simply does not offer client-driven termination would fail every gated run against it. That is either a correct refusal or a self-inflicted outage, and which one it is depends on a fact about real servers that no amount of reading this document establishes. **The alternative is not "be lenient" but "record it and call it clean"**, which certifies a live credential-bearing session as cleaned up — so the two candidate answers sit on opposite sides of §10.5's never-degrade rule, and picking without measuring is picking blind.

   **Ask everything answerable in one visit, because the access is the expensive part.** Probe #1 got two findings free from one set of receipts; the same applies here, and one of these questions is larger than the one this probe was named for.

   1. **Which protocol version and transport binding does the server speak?** Nothing in this repo has measured the SlideRule server at all — probe #1 measured *claude against our fixture*, not anything against theirs. §10.2's allowlist is `{2025-06-18, 2025-11-25, 2026-07-28}` and §10.10 serves Streamable HTTP under the legacy revisions only. If the answer is modern `2026-07-28`, the session machinery this probe is about **does not apply**, because modern removed protocol-level sessions — and the bridge as designed does not serve the motivating case. That is a design finding rather than a parameter, so it is asked first even though the probe is named for the third question.
   2. **Does it issue `Mcp-Session-Id`?** If not, `session_released` is `not_applicable` for this server and the rest of the probe is moot for it — though not for the design, which must still handle servers that do.
   3. **Does it accept a client-driven termination, and does it answer the same way across a stated sample?** Not "every time" — that is a universal, and no finite probe establishes one. The measurement is **N sessions terminated under stated conditions**, and the finding it licenses is "N of N answered alike", which is a statement about the sample. Any disagreement inside the sample is the interesting result and settles the design question immediately: a server that refuses only *some* sessions is one where the verdict needs a per-run record rather than a constant.
   4. **How long does an idle session survive an observation window W?** Not "how long does it live" — a session still alive at W establishes **`lifetime > W`, censored**, and never "it does not expire". Choosing W is the whole design of this question: set it from the longest eval this harness would actually run, so the useful answer is a bound against a decision rather than a duration. Report it as censored **in those words**; "no expiry observed" read as "no expiry" is the C3-3 mistake, and it is cheaper to write the reporting rule now than to discover it in review a third time.

   **These two are why this entry states its measurement semantics before the measurement.** §4 already carries the lesson twice — absence of a positive result is not a negative result, and a count is an observation of one run — and both times it arrived after a probe had published a claim wider than its evidence. A probe whose *wording* is a universal produces a reading nobody can weaken later without looking like they are explaining away a result.

   **Not answerable from the fixture, and that is the point.** `fixtures/http_mcp_server.py` implements no sessions and advertises none, deliberately — "what is not conformant is issuing one and ignoring it". So the fixture can drive the bridge's *handling* of both answers once they are known, and can prove the bridge does the right thing under each, but it cannot say which one the world produces. This probe wants the real endpoint, which makes it the first C3 probe whose subject is the **server** rather than a CLI, and the first that cannot be run offline.

   **Cost and ordering.** It needs the SlideRule endpoint and a token, so it is gated on access rather than on effort, and it is worth ordering *before* §10.10's slice 1 rather than after: the ending model is where the answer lands, and building `session_released`'s verdict twice is the avoidable version of this. If the endpoint is not reachable when the bridge is built, the fallback is to implement both dispositions behind one named predicate and leave the choice recorded as unmeasured — which is worse than measuring, and much better than a constant nobody can find later.

## 10. C3 — the harness-owned filtering proxy (design)

Decision recorded in §6-C3; this is the mechanism. **Scope of the first cut: stdio servers only.** A remote (`url:`) server with `tools:` is a validation error — the transport bridge is a separate piece of work and nothing should read "C3 landed" as "`tools:` works everywhere".

**That refusal is now enforced by something that names the transport, which it was not when this scope note was written.** For a while the sentence above was true only by accident: `mcp_tool_filter` read `"unbuilt"` on claude, so `validate_mcp_support` refused *every* gated server and the remote case fell inside a blanket. The adapter integration flipped that constant to `"proxy"` for the stdio case it was built for, and the remote case lost the only thing refusing it — the scope note stayed in this document and stopped describing the code. What restored it is `Adapter.tool_filter_for(server)`: the mechanism is asked **per server**, because `proxy` filtering is a program *the harness launches*, so whether it applies depends on a transport the server owns rather than on anything about the CLI. `native` and `complement` remain per-adapter answers and the default hook returns exactly that. The claude adapter's config writer re-asserts the same rule at the layer nothing routes around, since a validator is skippable by any caller that builds argv directly (PR #107).

**`tools: []` is a legal state and it starts.** The schema admits an empty allowlist with a warning that the server stays reachable and unusable, and the proxy honours it: every advertised tool stripped, every call refused, the server still reachable for everything that is not a tool call. An empty allowlist is a filter, not the absence of one — what C3 has no mode for is a **missing** allowlist, which is the case that could quietly become "pass everything", and `load_config` refuses that. The two were one condition until review found the documented state passing every preflight and then failing at launch (PR #107).

**And the motivating use case is on the far side of that line (confirmed 2026-08-06).** The SlideRule server will be **remote**, and §8's documented pattern for it is exactly `url` + a bearer token + a `tools:` allowlist — the one combination this scope excludes. So the bridge is not a completeness item to be picked up whenever; it is what stands between the harness and the thing it was built for. It was tracked nowhere until this date, which is the more useful half of the observation: the scope note above was correct and had been read as a limitation of an edge case rather than of the main case.

**The bridge is not "the same proxy with an HTTP client", and that is what makes it a design round rather than a port.** Almost every guarantee §10.5 and §10.5.1 make is stated over a **child process**: six shutdown steps that close its stdin, drain its stdout, signal its group and reap it; a `spawn_failed` partition that says no server ran; and a guardian whose whole purpose is to hold a pid unreaped so a process-group id provably still names the group this instance created. **A remote connection has no pid, no process group, and nothing to reap.**

The completion facts show the split exactly. Of the five, **four name the child** — `child_stdin_closed`, `drain_ended`, `child_reaped`, `group_terminated` — and have no counterpart in a socket. The fifth, `intake_closed`, is about the *client* half and generalizes unchanged, because the CLI still speaks stdio to the proxy no matter what the proxy speaks upstream. That asymmetry is the shape of the whole problem: the bridge keeps §10's entire client-facing story and has to re-derive its server-facing one.

What has to be re-derived, not ported:

- **What "this instance ended cleanly" means** when the resource is a socket. A connection left open is the honest analogue of a leaked child — a credential-bearing session the run no longer accounts for — but "closed" is a weaker claim than "reaped": the peer may hold it, a proxy in between may hold it, and `close()` returning says nothing about the far end. The pin argument that makes the stdio case sound has no counterpart here, so the limit should be stated the way §10.6 states the `setsid` one rather than papered over.
- **Where the credential lives.** For stdio it is the child's environment, contained by the child's lifetime. For remote it is an `Authorization` header on every request, held in the proxy's own memory for the life of the connection, and travelling to a host the harness does not control. That is a different exposure with a different scrub story, and §5.3's rules were written for the first one.
- **What the audit record says.** The five completion facts are a closed set checked in both directions by `mcp_audit.validate()`, so the reader cannot simply be handed a record about a socket. Either the facts generalize — which needs an argument, not an edit — or remote instances are a different record shape with their own validator, and the verdict function has to be total over both.

Sequence it behind the stdio integration regardless. The proxy has never faced a client that was not our own driver, and meeting a real CLI for the first time while also growing a network client means a failure has two candidate causes instead of one.

### 10.1 What it is

For a stdio server that declares `tools:`, the harness does not write the server's own `command` into the CLI's MCP config. It writes **its own shim**, which then spawns the declared server:

```
  agent CLI ──stdio──> agentskill_evals.mcp_proxy ──stdio──> the declared server
```

One server instance, with the harness inside the connection. That is the whole point, and it is what C2 cannot offer: C2 computes a deny-list from a **second** enumeration run, so a stateful server can advertise one tool set to the enumerator and another to the CLI (§6-C2). Here there is no second execution to disagree with, because the bytes the model sees are the bytes the proxy passed.

It is also the only tool-gating mechanism that will ever exist for **antigravity**, which has no native filter at all (§2), and it is adapter-independent by construction: the proxy is just a command, so any adapter that can inject a stdio server gets filtering for free. `mcp_tool_filter` gains a fifth value, `"proxy"`.

### 10.2 Protocol era — what the proxy speaks

MCP revision **`2026-07-28`** is a breaking change, and an earlier draft of this section was written against the era it replaced:

- There is **no `initialize` handshake**. Protocol version, client identity and client capabilities ride on *every request* in `_meta.io.modelcontextprotocol/*`.
- Servers **MUST** implement `server/discover`. A dual-era stdio client probes with it and falls back to `initialize` on any non-modern error *or a timeout* — the fallback is deliberately not keyed to one error code.
- Servers **MUST NOT** write JSON-RPC *requests* to stdout. Server→client interactions (sampling, elicitation, roots) are carried inside `InputRequiredResult` **responses**, and the client retries the original request as a new request with a **different `id`** (the MRTR pattern). `inputRequests` is a **map, not an array** — "keys are server-assigned string identifiers; values are request objects" — so code that iterates it walks the *keys*, sees a string where it expected a request, and skips every entry. The first implementation of §10.6's sampling check did exactly that and its arm agreed with it by building an array; both were wrong together (review, PR #100).

Three consequences, each of which changes a rule stated elsewhere in this section:

1. **Era is observed, never assumed — and it is decided by metadata, not by method name.** `server/discover` is *optional for clients*: a modern client may open with an ordinary `tools/list` carrying the required modern `_meta`, and that connection is modern, not unknown. So the test is **valid `_meta.io.modelcontextprotocol/protocolVersion` on any request ⟹ modern; `initialize` ⟹ legacy**, applied *per request*. **Modern is stateless; legacy retains the state its `initialize` established.** Modern carries nothing across requests, so "the connection is modern" is not a state the proxy may hold. Legacy is the opposite: an accepted `initialize` selects legacy semantics **for the stdio process**, and what it selects is not a fact that a boolean can carry. Later legacy messages contain no metadata whatsoever, so the **negotiated version** is the only thing that says which legacy revision to read them under — and the fleet spans two of them (§9), so a proxy that recorded merely "legacy is on" could not interpret the traffic that follows. Store the negotiated version and capabilities, and treat a second `initialize` as a lifecycle violation rather than a renegotiation: accepting one would retroactively move every message already exchanged to a revision it was not read under.

   **The negotiated version is the SERVER's answer, not the client's proposal, and the handshake is therefore two-phase.** "If the server supports the requested protocol version, it **MUST** respond with the same version. Otherwise, the server **MUST** respond with another protocol version it supports" — so a client proposing `2025-11-25` and served `2025-06-18` has a `2025-06-18` connection, and the implemented-version gate belongs on the **response**. Gating the proposal as well would fail a negotiation that was about to succeed, which is the false failure this whole section is trying to avoid. Between request and response there is a real state — *initialization in flight* — and it is load-bearing rather than bookkeeping: a proxy holding only an accepted version cannot refuse a second `initialize` sent before the first is answered, because at that moment nothing has been accepted. Both halves were wrong in the first implementation (review, PR #100).

Keeping one flag for both roles also makes dispatch order-dependent — a modern request followed by an accepted `initialize` would leave legacy disabled and refuse every bare request after it — which is why protocol state and era *telemetry* must be separate things.

The corollary is that **the method must match the request, not the reverse.** `initialize` carrying modern `_meta` is an unknown method, and a **modern-only method** arriving with no modern metadata is unknown to the legacy semantics in force — answering either on the strength of its familiar name is reading the era off the method, the exact inversion this section forbids. Modern-only is a **category, not a special case**: `server/discover` and `subscriptions/listen` both belong to it, the latter because `2026-07-28` introduced it as the replacement for legacy `resources/subscribe`. An implementation that names one method rather than the set will let the other through — which is precisely what happened to the probe shim, where a bare `subscriptions/listen` was answered with an acknowledgment and a graceful closure under legacy semantics that have no such method. Keying era off "which of `server/discover` or `initialize` arrived first" would misclassify every modern client that skips the probe — which the spec explicitly permits. A proxy that assumed `initialize` would hang a modern client at its first request.
   The version in that `_meta` is then checked against the versions the proxy **explicitly implements**; an unimplemented version is an anomaly (§10.6), not something to forward on the strength of being "modern". **The version is not the only required field.** `_meta` must carry both `io.modelcontextprotocol/protocolVersion` *and* `io.modelcontextprotocol/clientCapabilities` on every modern request — the spec says a request missing either "is malformed; the server **MUST** reject it with `-32602`" — and a proxy that policed only the version would forward malformed traffic that a conforming server is obliged to refuse. `clientInfo` and `logLevel` are optional and carry no such obligation.

   **An era must be ESTABLISHED, not merely unclaimed.** Absence of modern metadata makes a request legacy-*eligible*; it does not make it legacy. Until an `initialize` has been **sent** there is no negotiated version and none is coming, so nothing says which revision's rules the request is read under and §10.6's defined locations are undefined for it. Forwarding it anyway is the version gate defeated by simply never handshaking — no malice and no exotic client required, since a peer that sends neither modern `_meta` nor `initialize` would have every request waved through on the strength of an absence (review, PR #100). `initialize` and `ping` pass regardless, which the lifecycle sanctions explicitly: "the client **SHOULD NOT** send requests other than pings before the server has responded to the `initialize` request". The *method*-against-era check runs first, because a bare `subscriptions/listen` is a modern-only method offered under non-modern metadata whether or not a handshake has happened, and that is the more specific diagnosis.

   **A handshake still IN FLIGHT does NOT count, and the round trip to that answer is worth recording.** Pipelining ordinary requests behind `initialize` is a **SHOULD NOT**, not a prohibition, and a proxy is structurally more exposed to it than the server it fronts: the proxy reads lines serially while the server *answers* them, so a pipelined request reaches this check with the negotiation still in flight. An earlier revision let it through for that reason — and opened the gate exactly where §10.6 needs it shut. **A pending negotiation cannot govern traffic.** The pipelined request's *response* may arrive **before** the `initialize` response, and is then read under no version at all: a modern `InputRequiredResult` carrying tool definitions is forwarded unrecognised, because there is no version with which to recognise the channel (review, PR #100). Tolerating pipelining safely needs a **defer-and-replay** action — the request held, released when the negotiation completes — which is a materially larger contract for `decide` than forward/filter/refuse/drop/fail.

   Probe **C3-2** (§9) is what makes refusing the right trade rather than a gamble: **no shipped CLI pipelines.** All three legacy CLIs wait for the response, and agy sends no `initialize` at all. So the refusal costs the fleet nothing today, and the day one of them starts, the answer is the defer action rather than a hole here.

   **A REFUSED handshake clears rather than stranding the connection.** An errored `initialize` negotiated nothing, so leaving it pending forever leaves the connection neither negotiated nor open to a fresh attempt — and version negotiation is precisely where an error is expected, since the lifecycle's own worked example is a server rejecting a proposed version and naming what it supports. Clearing it lets the client propose again; bare requests stay shut throughout.

   **Validation applies to the opening request too, and per request rather than per session.** Modern is stateless — "servers **MUST NOT** rely on prior requests over the same connection to establish context ... every request supplies this metadata" — so there is no negotiated state for a later request to be checked against, and an opener that escaped validation would set the very terms it should have been judged by. Legacy is the exception the spec carves out: a dual-era server takes `initialize` as selecting legacy semantics *for the stdio process*, which is what makes a bare later request legal at all.
2. **Correlation is direction-scoped.** Under legacy, *both* sides originate requests, so an `id` on a server→client request is not an unrequested `id` — the proxy keeps two in-flight maps, one per direction. Under modern, a server-originated request is itself an anomaly, because the spec forbids it.
3. **Every `tools/call` retry is re-checked.** MRTR retries carry a new `id`, which the allowlist check handles for free by keying on `params.name` per request rather than on position in the stream.

**Probe C3-0 (§9) is resolved, and the fleet is split.** claude and copilot speak `2025-11-25`, codex speaks `2025-06-18`, and agy speaks the modern `2026-07-28` — so the allowlist this section gates on is `{2025-06-18, 2025-11-25, 2026-07-28}`, and dual-era support is a day-one requirement rather than a hedge. Note that the three legacy CLIs do not agree with each other either: "legacy" is two implementations, not one. Anything outside that set is an anomaly.

The unit of support is a **protocol version, not an era**. "Modern" is a category that future revisions will keep joining, and a revision that adds a new way to convey tool definitions would be waved through by any rule phrased at the level of era. §10.6 depends on knowing exactly where tool definitions live in a given version, which is knowable only for versions someone has actually read.

### 10.3 Launch and configuration

The proxy reads a JSON config from a **file**, whose path is its sole argument, and the file lives in the per-cell `ase-mcp-` scratch dir: mode `0600`, outside the archived workspace, deleted on every exit path. It carries the real `command`/`args`/`env` plus the allowlist, so it carries **interpolated credentials** and gets exactly the handling the CLI's own MCP config gets, for the reason mutation M10 exists — argv is recorded in `result.json` and is readable by any local user through `ps`, and a secret must not be in either.

The interpreter is `sys.executable`: the harness's own, the only one guaranteed to import `agentskill_evals`, and an absolute path outside HOME so a contained or masked home does not affect it.

**And that settles which Python runs, not whether the package is importable.** The proxy is launched by absolute *script path* — `sys.executable /abs/.../agentskill_evals/mcp_proxy_io.py <config>` — which puts the file's own directory on `sys.path` rather than the package's parent, so the module bootstraps from `__file__` when `__package__` is empty. The alternative is a `PYTHONPATH` that has to survive four different CLIs' handling of an MCP server's `env` map, and a proxy that fails to import is indistinguishable from a server that would not start — which is the ten-day silent failure Phase 1b already paid for once (§4). Nothing else is read from the environment except the wire driver's test-only variables (§10.9), and those are stripped from the child's environment before the declared server sees them — as a **declared set** (`CONTROL_ENV`) rather than a list repeated at the strip site, because this sentence was already true of the design while the code named four of the five that existed and handed the fifth to the server (review, PR #109).

**The guardian is launched the same way and briefed down a pipe.** It runs the same file with `--guardian <fd>` and reads the launch order — command, args, `env`, cwd, and the descriptor numbers it is to hand on — from an inherited descriptor. Not from `argv`, and not from its own environment: the order carries the interpolated `env`, and both of those are readable through `ps`. That is the same rule the config file above obeys, applied to the one process that has to be told the same secrets.

**That argv has a second reader, so it is built in one place.** §10.9's survivor check finds live guardians in the process table and its whole content is an *absence*, which makes it satisfied by a recogniser that looks for a shape nobody launches. `guardian_argv` builds the command line and `is_guardian_command` matches it, both from `os.path.abspath(__file__)`, so the launcher and the recogniser cannot drift — §4's duplicated-rule rule, satisfied by there being one rule. The path term is load-bearing rather than decorative: `mutate_mcp.py --jobs N` runs N copies of the tree at once, and a recogniser matching the bare module name would put a concurrent worker's guardian into this worker's before/during/after window, where it is genuinely absent before the case and genuinely present during it. Nothing in the argv is a secret — it is this file's path, a flag and a descriptor number — which is why the recogniser may read it from `ps` at all.

### 10.4 What is intercepted

Newline-delimited JSON-RPC 2.0, one message per line, as the stdio binding specifies.

**Parseable JSON is not a valid MCP message**, and the difference is load-bearing. Before any routing decision, each line must validate as an envelope: a JSON **object** (not an array); `"jsonrpc": "2.0"`; and *exactly one* of a request (`method` + `id`), a notification (`method`, no `id`), a result response (`id` + `result`), or an error response (`error`, `id` **optional** — the schema declares `id?: RequestId`). A `tools/call` must additionally carry a string `params.name`. Anything else is an anomaly.

Classifying by "it has no `id`" alone would be the bug this rule exists to prevent: a **malformed response that lost its `id`** would match the notification test and be forwarded verbatim down the never-answer path, unfiltered and unrecorded.

**FRAMING IS PART OF VALIDATION, and every way a line can fail to be one is an anomaly.** The stdio binding says each message is a single request, notification or response, so an **empty line** is not a message; bytes that are not **UTF-8** are not a message; and a **partial line left in the frame buffer when the stream ends** is a message that was never framed at all. All three were once waved through — the first by a `strip()` test, the second by decoding with `errors="replace"`, which silently rewrote a peer's bytes into different bytes and forwarded them, and the third by an EOF path that discarded the residue — and each produced a clean verdict for a stream that had gone wrong (review, PR #103). The residue is latched *before* the EOF trigger, so the record names the framing fault rather than the ordinary close that followed it. **`NaN` and `Infinity` are refused at the decoder**, via `parse_constant`, rather than at whichever field happened to look: Python's JSON decoder accepts all three as a documented extension, and the rule previously held only because `valid_request_id` rejects a NaN id — nothing checked one anywhere else in a message. A rule enforced at one field is a rule about that field.

**Positive validation means the *typed* fields too**, not just which keys are present. `RequestId` is a string or a **number** and never `null`; `params` and `result` are objects; an `error` carries an integer `code` and a string `message`. Three of these have consequences beyond tidiness. A **boolean** id passes `isinstance(x, int)` in Python, so it is the one illegal id that also *aliases* a legal one. A **list or object** id is unhashable, so it does not fail a correlation lookup — it raises `TypeError` inside a pump, several frames from anything that knows what to do about it, turning an anomaly the audit log could name into a crash. And a **fractional** id is *valid*: the schema is the declared source of truth and says `string | number`, while JSON-RPC only says fractions **SHOULD NOT** be used, so refusing `1.5` fails a conforming client over style — the prose on the basic page says "integer" and following it was over-strict (review, PR #100). `NaN`/`Infinity` stay refused, being outside JSON entirely and, in the `NaN` case, never equal to themselves and so never retirable.

An `id`-less **error** response is the case that makes the taxonomy earn its keep. It is schema-valid, so calling it a malformed envelope would be wrong — and would send whoever reads the audit log hunting a framing bug that does not exist, while hiding a genuine server-side error the server was trying to report. But the proxy forwards only validated client requests, so it can never correlate one, and forwarding it anyway would hand the client a reply to something the proxy cannot account for. It is therefore an anomaly of kind **uncorrelated**, not **malformed** — same verdict, different diagnosis, and the audit log records which.

| message | proxy behaviour |
| --- | --- |
| `tools/list` **response** | filter `result.tools` to the allowlist before forwarding |
| `tools/call` **request** | if `params.name` is off-list, do **not** forward; answer the client with a JSON-RPC error and record it |
| notification (`method`, no `id`) | forward verbatim, never answer — answering `notifications/initialized` is a protocol violation some clients treat as fatal |
| server→client **request** | legacy era: forward verbatim *unless the row below claims it*. Modern era: **anomaly** — the spec forbids it |
| `InputRequiredResult` carrying `sampling/createMessage` with `params.tools` | **anomaly** — a tool definition at a defined location outside `tools/list` (§10.6). Legacy equivalent: the server-originated `sampling/createMessage` request |
| everything else | forward verbatim: `server/discover`, `initialize`, `ping`, `resources/*`, `prompts/*`, `logging/*`, `completion/*` |

Filtering responses requires correlating them to requests, so the proxy keeps in-flight `id` → method maps — **one per direction** (§10.2). Pagination therefore needs no special case: every `tools/list` response is filtered, whichever page it is. A response arriving with an `id` never requested *in that direction* is an anomaly, not a pass-through.

**An id that is already open may not be reopened**, and this one is a filtering bypass rather than bookkeeping. Record `tools/list` on id 1, then `ping` on id 1, and a map that overwrites has relabelled the outstanding request: the server's tool advertisement correlates as a `ping`, is not recognised as a `tools/list` response, and is forwarded **unfiltered**. The spec forbids the client sending it — "the request ID **MUST NOT** match the ID of any other request the sender has issued and not yet received a response for" — and the proxy does not get to assume the client obeys, because the whole point of sitting in the connection is that the guarantee holds against what actually arrives. Reuse is legal only *after* retirement, which is what makes the subscription-id case above work (review, PR #100).

**The id is claimed before the proxy produces any message, refusals included.** An off-list `tools/call` arriving on an id that is already live must fail as a duplicate, not be answered: the synthesized error would reach the client correlated to the request that id *actually* belongs to — its outstanding `tools/list`, say — which then looks answered while its real response is still on its way. A refused call releases the id again, since nothing was forwarded and no reply will come back to correlate. Checking availability only at the point of *recording* leaves exactly this gap, because the refusal returns before it (review, PR #100).

**The correlation entry stores the governing version alongside the method**, because §10.6's defined locations are per version and a *response* carries no version of its own. Without it the reader of a legacy response applies modern `InputRequiredResult` semantics to it, and a conforming legacy result carrying an `inputRequests` key of its own meaning — legacy `Result` is open-ended — fails as a bad MRTR payload.

**Ids are keyed by DOMAIN and VALUE, not by Python type.** `1` and `"1"` are different ids and must stay apart; `1` and `1.0` are the same JSON number and must not. Keying on the type name split them, so a request on `1` answered on `1.0` read as uncorrelated and both could be live at once — a correctness bug that arrived the moment fractional ids became valid (review, PR #100).

**A request in that map may stay unanswered for a long time, and that is not a fault.** C3-0 found agy opening a `subscriptions/listen` with `notifications: {toolsListChanged: true}` — a long-lived request whose stream arrives as *notifications* correlated by `_meta.io.modelcontextprotocol/subscriptionId`, not by response `id`. An implementation that treated an unanswered request as a leak, a timeout, or an anomaly would fail every agy cell.

**But it is not resident forever, and one notification does need special handling.** A subscription ends in one of two orderly ways, and the proxy must retire the map entry on each:

- the client sends **`notifications/cancelled`** naming the `subscriptions/listen` request id; or
- the server sends the **graceful-closure response** on that same id, which *is* the subscription's terminal JSON-RPC response.

That response is **not `{}`**, and `resultType` is **required rather than defaulted** — the wording above is where both misreadings came from. The subscriptions page calls it "an empty result" in prose and then prints what it actually is: `resultType: "complete"` plus `_meta.io.modelcontextprotocol/subscriptionId`, whose value "matches the JSON-RPC `id` of the originating `subscriptions/listen` request". An implementation that required a literally empty object rejected our own `probe_era_mcp_server.py` — which has been emitting the conforming shape, and `verify_mcp_fixtures.py` asserting it, since #98 — and would have turned every clean agy shutdown into an anomaly (review, PR #100). The subscription id is checked against the response id because it is the only thing distinguishing a closure from a stray complete result. And the absent-reads-as-`complete` rule does **not** reach here: it exists for servers implementing *earlier* revisions, and no earlier revision has `subscriptions/listen` at all — it arrived in `2026-07-28` as the replacement for `resources/subscribe`. A server answering this method is by construction a modern server, where `resultType` is mandatory, so defaulting it accepts a closure that cannot exist (review, second round on PR #100).

**Which map a cancellation retires is decided by the PROTOCOL, not by looking in both.** The obvious reading — retire the sender's own direction — is wrong for the case the modern revision *mandates*: "a server **MUST** send `notifications/cancelled` referencing a `subscriptions/listen` request ID when it tears down that subscription stream ... Servers **MUST NOT** send `notifications/cancelled` for any other purpose", and that request is the **client's**. But searching both maps and taking whichever hits first is wrong too, and in *both* directions: an unknown **client** cancellation reaches into the server's map and cancels a coincidentally-numbered request there, and a **server** can retire the client's outstanding `tools/list` simply by naming its id — after which the reply that follows has lost the correlation that would have filtered it (review, PR #100). The three rules: a client cancellation names a client-issued request; under legacy a server may cancel its own; under modern a server cancellation names the client's `subscriptions/listen` and nothing else.

**The two server meanings are not mutually exclusive, and an era flag cannot choose between them.** Reading a negotiated legacy version as settling the question for the whole connection was the next mistake: modern semantics ride **per request**, in each request's `_meta`, so a client that has completed an `initialize` may still open a modern `subscriptions/listen`, and [the versioning specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) contemplates a server serving both eras concurrently. Every server cancellation then read as legacy, found nothing of that id in the server's map, and left the subscription open (review, third round on PR #100). So each meaning is tested against the traffic that would have to exist for it — a live server-originated request, or a live client `subscriptions/listen`, whose modern-only method is itself the era test — and normally exactly one is live. Matching **neither** is an invalid cancellation, ignored rather than guessed at, which is safe: the request stays live and its response is still correlated and still filtered. Matching **both** is the genuine collision, and the notification carries an id and nothing else to choose with, so it **fails loudly** rather than retiring a request on a coin-flip. An id live in neither is ignored, and so is a `requestId` that is not a valid `RequestId` — it would otherwise reach `dict.pop` through a tuple and raise `TypeError: unhashable` inside a pump, which is the envelope crash arriving by a route that skipped envelope validation. Both are what the spec asks for: "invalid cancellation notifications **SHOULD** be ignored: unknown request IDs ... malformed notifications" (review, PR #100).

**A cancelled id is remembered, not merely dropped, because the race is documented.** "Cancellation notifications may arrive after request processing has completed, and potentially after a response has already been sent", and the client "**SHOULD** ignore any response to the cancelled request that arrives afterward". Without a record of the cancellation that late response is a reply to an id nothing is waiting for — the `uncorrelated` anomaly, and a failed cell for a sequence the spec calls normal. The proxy therefore **drops** it: carrying out the client's own instruction one hop earlier, and safer than forwarding, since the correlation that would let a late `tools/list` reply be *filtered* went away with the cancellation. `Drop` is reserved for exactly this — a response on an id never issued at all stays fatal, or the escape becomes the degradation §10.5 forbids. The memory costs one entry per request genuinely cancelled.

**A REQUEST ID THAT REACHED THE SERVER IS SPENT FOR THE CONNECTION**, however it ended. This is a filtering boundary rather than bookkeeping, and it took four attempts to state at the right width — each narrower version left the same bypass reachable by a different route:

1. *Cancelled ids remembered, cleared on reuse.* Cancel `tools/list` on id 1, reuse id 1 for a `ping`, and the server's straggling tool advertisement correlates as the `ping` and is forwarded **unfiltered**. The ambiguity is real and unrecoverable, which is precisely why the id may not be reused, not why the bypass is acceptable.
2. *Quarantine lifted once a straggler was seen.* The request is over on the **client's** side; the other side is a server the scenario author does not control (§10.1), and **one observed response is no evidence about the next** — a second straggler is nonconforming, but so was the first, and only the second lands on a reopened id.
3. *Quarantine for cancellation only.* That argument never mentioned cancellation — it is about servers — so it applies verbatim to an ordinary answer and to a graceful closure. `tools/list` on id 1, its filtered answer, `ping` on id 1, a second `tools/list` result: forwarded unfiltered, with no cancellation anywhere in the sequence (review, fourth round on PR #100).

The rule that survives all three is the widest one: an id the proxy forwarded is never reopened. **The one id that does come back is one nothing was forwarded for** — an off-list `tools/call` is answered by the proxy itself, so no response can ever arrive on it, and keeping it spent would fail the client's next legitimate request and every MRTR retry.

**Same tombstone, different diagnosis.** A response after a *cancellation* is the documented race and is **dropped**: "cancellation notifications may arrive after request processing has completed, and potentially after a response has already been sent", with the client told to "ignore any response to the cancelled request that arrives afterward". A second response after an ordinary *answer* has no such licence — one request has one response — so it is an anomaly (`response_after_completion`), not a drop. Discarding it would be the proxy deciding by itself that an unexplained server message did not matter, which is the degradation §10.5 forbids. A response on an id never issued at all remains `uncorrelated`.

**This refuses something the specification permits, and that cost is not yet measured.** Reuse after a response is legal — the rule is only that an id may not match one "the sender has issued and not yet received a response for" — and §10.5 is explicit that failing a clean cell is as much a failure as forwarding a definition. Probe **C3-3** (§9) reads the id sequence out of the C3-2 run for free, and reading it is not pricing it **in either direction**: no negative from a short run can be, because allocation is not exercised once per connection the way pipelining is — and no positive can be either, because classifying a repeat needs the order of an arrival against a response, which nothing inside the server can establish. Pricing needs the sequential stress workload at cell length, which is not written. Until then this is a deliberate strictness, and what bounds the risk is that it is a *named* anomaly — a CLI that reuses ids fails loudly on the first real run rather than silently.

**The two orderly ends of a subscription differ only in that diagnosis.** The subscription id **is** the JSON-RPC request id, and neither the graceful closure nor the cancellation returns it: both are messages from the server, and the closure is no better evidence than the straggler was that nothing follows. Either way the live entry must go — one left resident forever would collide with a reused id, correlating a fresh response against stale state or reading a legitimate one as unrequested. So the earlier claim in this section that notifications need no special treatment is **wrong for `notifications/cancelled`**: it is still forwarded verbatim, as every notification is, but it must also be *observed* on the way through.

It does, however, kill any thought of caching. `toolsListChanged` means a server can prompt re-enumeration whenever it likes, and copilot independently issues `tools/list` twice per session. **Every `tools/list` response is filtered on its own merits**; there is no first-enumeration-wins shortcut, which is the same reason C2's second-enumeration model was rejected in §6-C2.

### 10.5 Failure semantics — the deferral objection, answered

C3 was deferred partly because it "puts harness-authored code in the request path of every gated run, where a bug is a silently wrong eval rather than a loud failure". That is the design constraint, not a caveat on it:

> **The proxy never degrades. Anything it cannot handle with certainty becomes a failed cell, never unfiltered traffic.**

Each of these is an **anomaly**:

- an envelope that fails validation (§10.4), including a **JSON-RPC batch** — an array is not a legal MCP message on stdio at all ("Each message is a single JSON-RPC request, notification, or response"), so refusing it is conformance, not a v1 shortcut;
- unparseable JSON in either direction;
- a response whose `id` was never requested in that direction;
- a `tools/list` result that is not shaped as expected;
- a server-originated JSON-RPC request while in the modern era;
- traffic in a protocol era the proxy was not built for (§10.2);
- a tool definition at a defined location outside `tools/list` — for `2026-07-28`, sampling's `params.tools` (§10.6);
- a request declaring a protocol version the proxy does not implement, or a modern request missing either required `_meta` field — `protocolVersion` or `clientCapabilities` (§10.2). This, not payload inspection, is what fails a future revision closed, and it applies to the **opening** request as much as any later one;
- a spawn failure of the declared server;
- **premature EOF, an unexpected child exit, or a write failure on either pipe** *while the connection is live* — see the shutdown exception below, which is scoped to step 2 of a teardown already under way and to nothing else. A child that dies mid-request must not read as a quiet end of stream — the spec tells clients to *restart* a server that exits unexpectedly, so this is the case most easily mistaken for normality, and it is not covered by the spawn-failure or terminator checks.

An anomaly is recorded and the proxy stops forwarding. It is **not** left to be inferred from the CLI's behaviour: the proxy writes an append-only audit log beside its config, and `verify_post_run` **fails the cell** unless, for every gated server, that log exists, parses, records no anomaly, and shows every proxy instance that started also terminating cleanly. Absence of a clean verdict is a failure — deliberately the same rule as copilot's, where a run that emitted its own `result` without ever emitting `session.mcp_servers_loaded` fails closed (§4).

Two refinements that the naive form of that rule gets wrong:

- **The invariant is about what was forwarded, not what was seen.** A proper-subset allowlist normally *means* the server advertises off-list tools and the proxy strips them, so "the log records no off-list advertisement" would reject exactly the case where filtering worked. The required evidence is that **no off-list advertisement was forwarded to the client**; a filtered source advertisement is an expected event and is recorded as one.
- **The client may restart the proxy.** Because unexpected exit is a spec-sanctioned restart trigger, the log is append-only across instances and every record carries an instance id. The verdict is per instance, not "the file ends with a terminator".
  **A later instance never heals an earlier one.** The cell verdict is the conjunction over every instance; one anomalous or unterminated instance fails the cell no matter how many clean instances follow it. This is the whole reason the rule is phrased per instance, and it is the form an implementation is most likely to get wrong — "find the latest verdict for this server", or a dedupe keyed on server name, would each silently let a clean restart paper over the exact failure the log exists to catch.
  That requires knowing an instance existed, so **the start record is written before the child is spawned** — and therefore before a single byte is forwarded. Then the two cases partition cleanly: an instance that logged a start must also log a terminator, and that terminator must be clean; an instance that died before logging anything spawned nothing and forwarded nothing, so its absence from the log is not a gap in the evidence.
  **The instance boundary sits before the spawn attempt, not after it**, and that is what makes `spawn_failed` (§10.5.1) an ordinary ending with a record like any other rather than a failure the log can only be silent about. A successful spawn is then recorded in its own right, carrying the child's **pid and process group id, and the guardian's pid** — facts the start record cannot hold, since it precedes the spawn. All three are **required**, because the spawn record is written only once the guardian has reported ready about itself: its presence is the readiness evidence rather than a note beside it, which is why the reader validates it like any other claim (§10.5.1). They are what lets §10.9's teardown case check the proxy's account of the group against the group a surviving process reports for itself, instead of discovering processes and deciding for itself which belonged to the run. What remains outside the boundary is narrow — a config that cannot be read, an audit log that cannot be opened — and it is closed from the other side: for a gated server, an audit log that does not exist fails the cell, because a gated server whose proxy never ran means the gating never happened, and a pass would be certifying an ungated run.

The terminator rule had an empirical dependency, recorded as **probe C3-1** in §9 and now **resolved**: claude and agy close stdin, **codex and copilot send `SIGTERM`**, and nothing observed used `SIGKILL` without grace. The rule survives — under a requirement the design had not stated:

> **The proxy MUST catch `SIGTERM`/`SIGINT` and perform a coordinated shutdown — of which writing the terminator is the *last* step, not the whole of it.**

Default signal disposition terminates a process without running any handler. A proxy that omitted these would write no terminator on *half the shipped fleet* and fail every clean codex and copilot cell — a false failure indistinguishable from the real one the rule exists to catch. That the answer was neither of the two outcomes this section anticipated (clean stdin close, or an unhandleable kill) is the case for measuring rather than reasoning: the third option is handleable, but only on purpose.

**The naive form of that requirement is worse than not having it.** Unlike the probe, the proxy has a child: the real MCP server, holding the interpolated credentials. A handler that logs a terminator and calls `os._exit(0)` neither terminates nor reaps that child, so the server can outlive the run — still holding a credential, possibly still connected to something — while the audit log certifies the instance ended cleanly. That is a *false clean verdict*, the one outcome §10.5 exists to make impossible, produced by the very mechanism meant to prevent it. The order is therefore fixed:

1. stop accepting new client traffic;
2. close the child's stdin — the portable graceful signal (§10.2) — and keep **draining the child's stdout**, forwarding what it says on the way out. The graceful-closure result for an open `subscriptions/listen` is the **server's** statement about the server's subscription, so the proxy forwards the child's real one and **never synthesizes its own**. A proxy that manufactured that response would be asserting, in the server's voice, that a subscription closed cleanly — which it cannot know, and which is the same fabrication §10.4 refuses everywhere else. Forwarding here is best-effort: C3-1 measured agy closing stdin and ceasing to read at once, so the write raises `EPIPE` against a conforming peer. Record it, swallow it, continue — an exception escaping here would skip every step below and orphan the child, which is the failure this sequence exists to prevent;
3. wait for the child, escalating `SIGTERM` → `SIGKILL` on a bounded timer;
4. **terminate the child's process group, not just the child.** A stdio server may spawn helpers, and they inherit the interpolated environment — so a surviving grandchild is a live credential the run no longer accounts for. The child is therefore started in its own process group (`start_new_session=True`) precisely so this step has a group to signal, which is a launch decision (§10.3) that exists only to make this teardown possible;
5. reap the direct child, record its exit status and the group teardown in the audit;
6. **only then** write the terminator.

**Steps 4 and 5 are carried out by the guardian, on the proxy's order** — it is the child's parent and therefore the only process here that can show the group id has not been recycled (below). The proxy keeps the sequence, the bounds and the record; what it delegates is every real signal, plus the reap that ends the pin.

A **clean** terminator therefore asserts something stronger than "the proxy reached its handler" — it asserts **the direct child was reaped and its process group terminated**. Nothing weaker would be worth checking, which is exactly why the steps that can fail to keep that promise — an unreapable child, a group teardown that errored — are recorded as cleanup outcomes that make the terminator *anomalous* (§10.5.1), rather than as details a terminator omits.

**Why the reap is last, which the numbered order states and does not explain.** The process group is named by the child's pid, and that pid stops being unique the moment the child is reaped: after `wait()` returns, `killpg(pgid, ...)` names a group the kernel is free to have reassigned. Holding the child as an **unreaped zombie through step 4** is what makes the group provably still the one this instance created — a zombie is a member, so the group cannot be recycled out from under it. That is the whole content of "step 4 before step 5", and an implementation that reaped first would look identical and be signalling an arbitrary group.

Three consequences the implementation ran into, recorded here because each of them looks like a bug in the wrong direction:

- **Step 3 cannot call `wait()`.** `os.waitid(..., WNOWAIT)` — the POSIX way to wait for an exit without consuming it — **is not available on macOS**. So step 3 bounds its wait on the child's stdout reaching EOF, which step 2's drain already establishes, and escalates on the timer when it has not. Correctness does not rest on that reading being right: step 4's group `SIGKILL` is a kernel guarantee about every live member, and step 5's bounded reap is what reports a child that outlived even it.
- **Steps 2 and 3 are ONE wait, not two bounded independently.** They ask the same question of the same descriptor — has the child finished? — and a drain with its own separate deadline reports a server that merely needed `SIGKILL` as a teardown anomaly, when §10.5.1 classifies forced termination as **clean**. That would fail a conforming cell, which this section weighs exactly as heavily as forwarding a definition.
- **`EPERM` from `killpg` is success, and this one is measured rather than reasoned.** macOS returns it for a group whose members are all zombies, where Linux returns 0 — and with the pinning member still unreaped in the group, reading it as an error reports `shutdown_group_kill_failed` on **every clean shutdown** on half the supported platforms. A group with a live member always returns 0, because the child and anything it spawned run as the proxy's own uid. Step 4 also refuses outright if the target group is the signaller's own, since that means `start_new_session=True` did not take effect and signalling would reach the proxy and everything beside it.

**`EPERM` was then read as success, and that was wrong for a reason the measurement could not reach.** macOS returning it for an all-zombie group establishes *one* cause of `EPERM`; `kill(2)` defines it as the inability to signal group members, which a sandbox restriction or a differently credentialed descendant also produces — and either would have left a live member while the branch certified success (review, PR #103). An errno with more than one cause is not evidence. So delivery and the **verdict** are now separate: step 4 delivers `SIGTERM` then `SIGKILL` while the group is provably ours and records only errors it can attribute, and the fact is settled **after step 5's reap**, when the one member the proxy was deliberately keeping alive is gone and `killpg(pgid, 0)` answering `ESRCH` is direct evidence rather than an inference. That probe **sends no signal**, which is what makes the residual pid-reuse window safe rather than merely unlikely: the worst outcome is a false `shutdown_group_kill_failed` — a failed cell — instead of a signal to a stranger.

**`start_new_session=True` is also what puts the child out of reach of every ancestor, so the proxy dying is a leak the audit can only describe.** A `SIGKILL` to the proxy leaves a credential-bearing server with nothing that will ever terminate it: the absence rule catches it and fails the cell, but **detection is not cleanup** (review, PR #103). The proxy therefore runs a **guardian** — a third process, in its own session so the group signal half the fleet sends does not take it out, holding one end of a lifeline the proxy holds the other end of.

**The guardian is the child's parent, and that is the whole design rather than an implementation choice** (review, PR #103). A guardian that is merely *started alongside* the child is wrong in three ways at once, and the first draft was wrong in all three:

- **It can be late.** A guardian spawned after the child leaves a window in which a credential-bearing server exists and nothing is watching it; a `SIGKILL` inside that window orphans it however carefully both sides are written. Making the guardian the thing that *starts* the server closes the window by construction — there is no moment at which the child exists and the guardian does not.
- **It can be absent.** "Best effort, the run continues" is not a shape a containment mechanism may have. Establishing the guardian is now part of the spawn: if it cannot be established the server never starts, and the instance ends `spawn_failed` — an ordinary anomalous ending with a record like any other, because the instance boundary already sits before the spawn attempt. **Inability to contain fails closed.**
- **It cannot prove what it is signalling.** A process group is named by the child's pid, and that number is reusable once the group's last member is reaped. `killpg` on a remembered number can therefore reach a group the kernel has since handed to somebody else, and no amount of asking first fixes it — `killpg(pgid, 0)` succeeding does not establish identity, it establishes that *something* is there. What does establish it is a **pin**, and the argument needs no kernel internals: a process group id names at most one *existing* group, our group exists for as long as it has a member, and an unreaped child is a member. So while the parent holds the child unreaped, that number cannot name anything but the group this instance created — and only a parent can hold that pin, which is the whole reason the guardian is one. **Every real signal to that group is therefore sent by the guardian**, and it stops signalling the moment it reaps: releasing the pin ends its licence to act, which is why the reap is also the last thing it does.

**Readiness is a handshake in TWO PHASES, and the split is what makes `spawn_failed` true rather than merely written.** `Popen` returning says a fork succeeded; what has to be established is that the guardian's own code ran in that process. So phase one authenticates that process and *nothing else*: it reports its own pid, the proxy checks it against the one it spawned, and the guardian does not yet hold a command. Phase two is the launch order, sent only once phase one is accepted. The spawn record is written after that, so `guardian_pid` in the log is positive evidence rather than a note, and the reader requires it (§10.5.1).

One phase was not enough, and the gap was observable. With the guardian spawning the server and reporting in a single step, a report the proxy **rejected** still left a child that had run: under the imposter injection a `/usr/bin/touch` child created its marker in 6 of 20 runs, while every audit recorded `spawn_failed`, no spawn record, and four `not_applicable` child facts (review, PR #103). **A partition the record asserts has to be a partition the code enforces**, and the enforcement is that a guardian which has not been accepted was never told what to run. Note the shape of the error rather than the case: the record was not lying about anything it could see — it was reporting a boundary that the implementation drew one step later than the document did.

**It stands down only on purpose, and a failed teardown is not a purpose.** The default at every ending — an order, an EOF — is to terminate the group. The single exception is §10.9's retention control, which is armed by a fault point *firing* and is therefore impossible in any run that could have passed. The first version instead stood down whenever the proxy's teardown had merely **run**, which meant a teardown that ran and *failed* silenced the one mechanism that existed to clean up after it: `group_terminated=fail` exited 1, recorded `shutdown_group_kill_failed`, and left the child's liveness channel open after the proxy was gone (review, PR #103). The record already preserves the evidence of the failure; **cleaning up after it does not erase that**, and the two are not alternatives.

Which is also why the reap order sweeps the group *before* it reaps. Reaping releases the pin, so anything still in the group has to be dealt with while it is still held — including the case where the proxy's own step 4 never delivered, which is exactly the failure the guardian exists to survive.

**And why the sweep signals before it says anything.** stderr is inherited from the proxy and therefore from the CLI, and a CLI may close it. The guardian's sweep announced itself first, so once that pipe was gone the `print` raised `BrokenPipeError` and the guardian exited having signalled nothing: a credential-bearing process group left alive **by its own log line** (review, PR #103). The general rule is the one worth keeping — *a diagnostic must never be able to prevent the action it describes* — and it quantifies over every stderr write in the program, not over the one that was found. All of them go through a helper that swallows the failure; the sweep additionally does its work first, so the ordering says what the helper guarantees and a reader need not take the helper on trust.

**The one ending the structure does not cover is the guardian dying mid-run**, and it gets its own trigger: `guardian_lost`. The report pipe reaching EOF is the proxy's notice that the child now has no pin and no reaper, which is terminal rather than degraded — forwarding stops.

**And then the proxy signals nothing at all.** The first attempt at that path had it ask `getpgid(child_pid)` and signal if the answer was still the recorded pgid — but that is not an identity: a reaped pid can be reused, and because `start_new_session=True` makes the child its own group leader, `getpgid(pid) == pid` degenerates to *some group leader has this number*. The check's own documentation said as much, and it authorized `SIGKILL` regardless, which is the naked-pgid hazard narrowed to one path rather than removed (review, PR #103). **A loud anomaly does not authorize signalling an uncertain identity.** So `guardian_lost` records `shutdown_group_kill_failed` and `shutdown_reap_failed`, the cell fails, and the server is left running — a leak the audit reports rather than a stranger's process group killed quietly. §10.6 carries it as a limit of the design, and §10.9 drives it as a case that asserts the survivor, exactly as the `setsid` case does. What would lift the limit is another non-reusable handle on the process — `pidfd_open` on Linux, `EVFILT_PROC` on the BSDs — and neither is portable to both supported platforms.

What step 4 promises is therefore that `SIGKILL` **reached** the group, with emptiness confirmed after the reap by a probe that sends nothing. That nothing survived is *also* checked from **outside**, by §10.9's liveness channels, which is where a claim about the proxy's own cleanup belongs anyway.

#### 10.5.1 Every way an instance can end, on two axes

An instance ends for **one latched trigger**, may record **further triggers** behind it, accumulates **zero or more cleanup outcomes** on the way out, and records **what its teardown actually completed**. Those are independent facts and one field cannot carry them: `client_eof → shutdown_write_failed → shutdown_child_killed` and `protocol_anomaly → shutdown_write_failed → shutdown_child_killed` are different endings that a single-slot reason either renders identical or renders by discarding one end of the evidence (review, PR #101). Either loss is load-bearing. Drop the trigger and a protocol anomaly reads as a clean client close. Drop the outcomes and a failed process-group teardown — a surviving grandchild holding an interpolated credential — is certified clean by the very record that was supposed to prove the opposite. The rule is therefore:

> **clean ⟺ the record is structurally valid, *and* every reason it holds is clean, *and* every step of §10.5's sequence recorded its completion** — a monotonic conjunction over everything recorded, never a lookup on the last thing that happened.

**The structural clause is first because the other two are universally quantified, and both are vacuously true of an empty record** (review, PR #101). "Every recorded reason is clean" holds of `triggers: []`, which is not a clean instance but a broken one — the instance is *defined* as having a latched first trigger, so a record without one is evidence about the writer, not about the run. `all()` over a collection nothing was put into is the same unfalsifiable assertion `CLAUDE.md` bans in test code, and it fails the same way: it passes hardest exactly when the thing it checks did not happen.

The three clauses fail differently, and all three are needed. `is_clean` is one total function over the reason enumerations below, and every consumer reads it: the terminator record, the per-instance verdict, and `verify_post_run`. No consumer re-derives cleanliness from a condition of its own. Monotonic means evidence only ever moves the verdict toward anomalous — the no-heal rule of §10.5 stated as an algebraic property rather than as a warning, and applied within one instance rather than across restarts.

The completion half exists because **every outcome is an exceptional observation, so an empty outcome list is not evidence that anything ran** (review, PR #101). An implementation that silently skipped step 4 raises nothing, records nothing, and would satisfy a verdict that read only the reasons — the failure mode being certified clean is precisely a surviving credential-bearing grandchild. This is the absence rule §10.5 already applies to the terminator, applied one level down to the steps inside it: *not observing a failure is not the same as observing a success*, and only one of the two is worth a clean verdict.

This is written down before the I/O half is built rather than after, because it is the shape of defect this work has already paid for twice (`TODO_Contained_HOME.md` §4). Both times a new fact about whether something could be trusted was added *beside* the existing reasons instead of *into* them, and the consumers that were not updated went on publishing their old conclusion. Fifteen ways to end, arriving from three directions — the client, the child, the proxy's own machinery — is precisely the setup that produces it, and the single-axis first draft of this very section is the third instance, which is the cheapest demonstration available that the enumeration needed writing down before the code and not after.

**Axis 1 — the triggers.** An ordered list, and the **first** one is the latch: the terminal event that stopped forwarding and started the teardown. Every §10.4 anomaly is terminal (§10.5), so every anomaly is a trigger rather than something that happens alongside one. Later triggers are recorded behind the latch and classified by the same `is_clean`, which is the whole reason this is a list — `client_eof` followed by `signal_term` is a CLI closing stdin and then signalling, and two individually clean triggers must not compose into a failure (review, PR #101).

| Trigger | Raised by | Verdict |
| --- | --- | --- |
| `client_eof` | client closed stdin | **clean** — C3-1: claude, agy |
| `signal_term`, `signal_int` | client signalled | **clean** — C3-1: codex, copilot |
| `spawn_failed` | the declared server would not start | anomaly — an instance with a start record and a terminator like any other, because the boundary sits before the spawn (§10.5) |
| `child_exit` | the server exited while the connection was live | anomaly — the spec tells clients to *restart* an unexpectedly exited server, which is why this is the case most easily mistaken for normality |
| `client_write_failed`, `child_write_failed` | a write during ordinary forwarding | anomaly — mid-conversation, and what it carried did not arrive |
| `read_failed` | a read error that is **not** EOF, on either pipe | anomaly — an instrument failure must never wear the clean-shutdown label |
| `guardian_lost` | the guardian died while the connection was live | anomaly — it is the child's *parent*, so its death leaves a credential-bearing server whose exit nobody will observe and whose group nothing can prove the identity of (§10.5) |
| `protocol_anomaly` | any anomaly from §10.4's closed set | anomaly — and it carries *which* one, so this axis does not fork a second copy of an enumeration the decision layer already owns and mutation-covers |

**Axis 2 — the cleanup outcomes.** An ordered list of what went *wrong* as §10.5's six steps ran; an empty list means nothing exceptional was observed, which is not the same as every step having run — that claim is the completion facts' job, below. The child's exit *status* is recorded here as data and is deliberately **not** a verdict input: MCP specifies no exit code for a server that saw its stdin close, so failing on a non-zero one would fail conforming servers.

| Outcome | Raised by | Verdict |
| --- | --- | --- |
| `shutdown_write_failed` | writing to a departed client during step 2 | **clean** — C3-1 measured it against agy; recorded, swallowed, sequence continues |
| `shutdown_child_killed` | step 3's bounded timer expired **and the `SIGKILL` was delivered** | **clean** — the spec makes forced termination the standard escalation and only **SHOULD**s a prompt exit, so this is worth recording and not worth failing on |
| `shutdown_read_failed` | a read error, not EOF, while draining the child in step 2 | anomaly — same argument as `read_failed`, and the one §4 has already caught in the wild: a swallowed `OSError` that presents as a clean end of stream |
| `shutdown_reap_failed` | step 5 could not reap the child, even after `SIGKILL` | anomaly — the terminator's central promise is exactly this, so it cannot be the part that is allowed to fail quietly |
| `shutdown_group_kill_failed` | step 4's group teardown errored (`ESRCH` is success — the group is gone, which is the goal) | anomaly — a surviving grandchild is a live credential the run no longer accounts for (§10.5 step 4) |
| `shutdown_anomaly` | an exception escaping any teardown step, carrying the exception and the exact completion fact it escaped | anomaly — the catch-all that keeps an unforeseen teardown fault from being an *unrecorded* one; it is not where racing triggers go |

**The drain is bounded, and the bound is the catch-all's first real customer.** The child's stdout can be held open by something the group signal does not reach — a helper the server put in a *different* process group — so the drain cannot wait for EOF indefinitely, and a proxy that did would hang instead of producing a verdict. It is `shutdown_anomaly` on `drain_ended` rather than a new outcome because the diagnosis is exactly "something happened here that this design did not anticipate": an unaccounted-for process holding a pipe from a credential-bearing server is precisely what a clean verdict must not certify, and naming it would suggest the proxy knows what that process is. Note this is the one outcome that can legitimately appear *alongside* `shutdown_child_killed` — step 3 escalated because stdout never reached EOF, which is true and clean, and the drain's failure is a separate entry on the same axis rather than a merger of the two.

**An outcome that names an act is written only where the act happened.** `shutdown_child_killed` says *this instance delivered a `SIGKILL` to the child's group*, and step 3's escalation used to write it whether or not delivery succeeded. The ending that exposed it is the one where the policy is deliberately to signal *nothing*: with the guardian gone there is no pin, `_deliver` refuses, and the log nevertheless recorded a kill beside the two failures proving nothing was signalled (review, PR #103). Step 4 had read that same return value since it was written; step 3 discarded it. The escalation now ends on the refusal rather than trying the next order — the only process that could signal is gone, so `SIGKILL` would fail exactly as `SIGTERM` did — and it raises `_EscalationUndelivered` rather than a `TimeoutError`, because no bound expired and the exception's name is what lands in the archived record as `shutdown_anomaly`'s payload.

**One reason is recorded at the start rather than at the end.** `fault_point_configured` names the fault-injection point the wire driver needs (§10.9) and is **always an anomaly**. What is anomalous is the *configuration*, not the firing: a fault that was armed and failed to fire would otherwise leave a clean trigger and clean outcomes satisfying the formula exactly, and the run would pass while pretending to have been tested (review, PR #101). The verdict is a conjunction over every reason the instance recorded, in the start record as much as the terminator, so no consumer needs a special case for this and none may omit one.

**The latch decides which trigger stopped forwarding, not which triggers count.** Two pumps and a signal handler can all reach the end at once, so the latch is a compare-and-set — but the runners-up are appended to the same list and classified the same way, so `client_eof` then `signal_term`, or `SIGTERM` then `SIGINT`, stays clean. A child that exits during step 3 is not a trigger at all: that is the step working, recorded as `child_status`. Note that §10.4's rules still apply to what the drain forwards — the shutdown is not a licence to pump bytes unfiltered — so a malformed or off-list frame arriving on the way out is a genuine second trigger, and an anomalous one.

**The completion facts — what actually ran.** Every step of §10.5's sequence that makes a promise records whether it kept it, and the terminator carries all of them. Each is one of `done`, `not_applicable` **with the trigger that makes it so**, `failed` **with the outcome that says how**, or missing — and missing is an anomaly, because a step that recorded nothing is indistinguishable from a step that never ran.

| Step | Fact | `not_applicable` when | typed `failed` pairing |
| --- | --- | --- | --- |
| 1 | `intake_closed` — no client traffic accepted after this point | never | — |
| 2 | `child_stdin_closed` | `spawn_failed` — there is no child | — |
| 2 | `drain_ended` — the drain reached EOF | `spawn_failed` | `shutdown_read_failed` |
| 3, 5 | `child_reaped` — with `child_status` alongside it as data | `spawn_failed` | `shutdown_reap_failed` |
| 4 | `group_terminated` — the group is gone, `ESRCH` included | `spawn_failed` | `shutdown_group_kill_failed` |

**Every fact may also pair with `shutdown_anomaly`, and the two dashes above are why that is not optional.** An exception can escape any step, including the two whose failures have no typed outcome, so `failed` on *any* fact is legal when the outcome list carries a `shutdown_anomaly` for it. The typed pairing is preferred wherever the column names one; `shutdown_anomaly` is what keeps an unforeseen failure writeable rather than forcing the writer to omit a fact and produce a malformed record. Step 6 is the one step with no fact and therefore no pairing: an exception there means no terminator, which the absence rule already covers.

**The pairing key is the completion fact, never the step.** A step number is coarser than the thing it identifies — step 2 owns both `child_stdin_closed` and `drain_ended` — so a `shutdown_anomaly(step=2)` would license `failed` on either of them, or on both, having arisen from one operation (review, PR #101). `shutdown_anomaly` therefore carries the **exact fact key** it escaped, and the validator pins the sibling case explicitly in both directions: an anomaly keyed to `child_stdin_closed` must not license `drain_ended: failed`, and the reverse. A pairing key one level coarser than what it pairs is not a weaker check, it is a check that passes for the wrong reason.

**Suppression pairs with *firing*, which is not the same fact as *arming*.** The fault point contributes two separate things, and collapsing them destroys the case they exist for (review, PR #101). `fault_point_configured` is the start-record reason, names the facts the hook is armed on, and is **always anomalous on its own** — that is the clause which stops an armed-but-silent hook from producing a passing run. `fault_point_fired(fact)` is written when the hook actually suppresses that fact, and is **evidence rather than a verdict input**: the instance is already anomalous from the arming, so firing adds nothing to the verdict and everything to the record. Only the fired record may pair with a completion fact, bidirectionally — `failed(fault_point_fired)` requires the matching fired record, and a fired record requires that fact to read `failed` — and a fired record is legal only for a fact the configuration listed. Arming alone therefore licenses nothing: a hook that never fires leaves ordinary `done` or `not_applicable` completions everywhere and a record that is anomalous **solely** because the start record says it was armed.

**`child_status` is required exactly when `child_reaped` says `done`, forbidden otherwise, and must be an integer.** Only a process that reaped a child can hold its exit status, so a `done` without one claims a reap while lacking the single piece of evidence a reaper necessarily has, and a status attached to `failed` or `not_applicable` is a status for a child that was never reaped — invented, since there was nowhere to get it. Tying the two structurally is what turns the earlier observation that fabricating a status is *a lie rather than an omission* into something the reader enforces instead of merely notes.

The type is part of that rule rather than a detail below it. Checking only that the field is *present* accepts `null` — a record asserting the evidence exists while carrying none of it — and accepts `true`, which slips past the obvious type check as well, because `isinstance(True, int)` holds (review, PR #102). Presence-not-content is the same defect as absence-not-emptiness, one level down, and it arrives the same way: a boolean standing in for a value nobody looked at.

**`failed` exists because the two axes describe the same events and must be able to agree.** Without it there is no structurally valid record of a teardown that ran and did not work: `shutdown_reap_failed` could not be said of `child_reaped`, `shutdown_group_kill_failed` could not be said of `group_terminated`, and the only remaining spelling — omitting the fact — is the one the validator calls malformed (review, PR #101). So failure is **present, valid and anomalous**, and the pairing is closed in both directions: a `failed` fact requires its cause in the record, and that cause requires the paired fact to say `failed`.

**The cause is declared by the fact, there is exactly one, and it exists only under `failed`.** A `failed` fact names which of three things ended the step — its typed outcome, a `shutdown_anomaly` keyed to it, or `fault_point_fired` — and the reader checks that the record actually carries what was named. The union is closed in both directions: a `done` or `not_applicable` step carrying a cause is a record disagreeing with itself, and reading the field only under `failed` does not tolerate that so much as leave it *unread*, which is worse — nothing reports it. **That rule quantifies over every tagged union here, not just the facts**: `anomaly` is legal only on a `protocol_anomaly` trigger, and `fact`/`exception` only on a `shutdown_anomaly` outcome, because those are the tags that read them. A field nothing consults is the thing being rejected, wherever it sits. And the reader never erases a present value into absence — a non-conforming optional field is a shape problem, since `null` and "not there" are the same value in Python and only one of them is legal (review, PR #102). The fault point's suppression targets are checked the same way, against the completion-fact set: a target outside it is a malformed configuration, and the instance being anomalous anyway (the hook was armed) is exactly what would have hidden it. Inferring the cause instead, by asking whether *some* pairing is available, lets one record hold two incompatible accounts of one step: a `group_terminated` carrying both `shutdown_group_kill_failed` and a fault-point firing says the kill was attempted and failed *and* that it never ran, and an inferring validator reports no problem at all (review, PR #102). Suppression and a runtime failure are therefore mutually exclusive by construction rather than by convention.

`not_applicable` and `failed` are explicit values carrying their justification, checked against the trigger and the outcome list respectively, rather than a blank the verdict is asked to interpret. A blank means three different things — "did not apply", "tried and failed", and "did not happen" — and the whole point of this half is that those must not be the same value. The one step with no fact is step 6: writing the terminator is what the terminator's existence attests, and its absence is covered by the absence rule below.

**One structural validator, and the reader owns it.** Before anything above is classified, the record's *shape* is checked: a non-empty trigger list, and a completion-fact set whose **names are exactly the closed set — no name missing and no name extra** — each carrying a value from its own closed set, with `not_applicable` only where the trigger licenses it and `failed` only where the outcome list carries its paired outcome — and, in the other direction, no such outcome without the paired fact saying `failed`. **Both directions of the key set matter, and only one of them is obvious.** A missing fact is the case everyone writes; an *unrecognized* one is how a fact added later goes unchecked, because a validator that iterates the names it knows accepts a record carrying a fifth it has never heard of. A record that fails is `malformed_record` — an anomaly whose subject is the proxy rather than the run. The proxy may assert the same shape before writing, but that assertion is not the check: a proxy broken enough to write an empty trigger list is precisely the wrong process to ask whether it did, and the rule that a claim and the thing it claims about must not have the same author applies here first.

**Which means the reader's input is arbitrary decoded JSON, and it must be total over that.** Not "a record the proxy promised to write" — the writer is the thing under suspicion, so `triggers` may be an object, `state` may be an array, `fault_point.suppresses` may be a number. Every such shape becomes a problem code; none of them raises. A traceback out of `verify_post_run` is not a failed cell, it is an *absent* verdict, which is the one outcome §10.5 exists to make impossible, arriving through the code written to guarantee it (review, PR #102). Two consequences worth stating because both were wrong first: **missing, null and empty are three different records**, since `raw.get(k) or []` turns an axis the writer forgot into an axis with nothing on it, and an axis with nothing on it is legal. And **a fault point is anomalous by being present**, not by suppressing anything — an arm-only hook suppresses nothing by design, so reading its empty list as "no fault point" passes exactly the run that case exists to reject.

**Totality is lost at membership tests, and the parser is what keeps it.** `[] in FROZENSET` raises `TypeError: unhashable type`, so every field the validator looks up in a closed set must already have been narrowed to a string — which the parser does, reporting each non-conforming value as its own code rather than erasing it. Two fields are deliberately carried **raw**, because for them "present but wrong" is a different verdict from "absent": `child_status` and the guardian injection. `child_status` was safe by accident — `is_json_int` is an `isinstance` check and therefore total over any value — while the guardian's predicate was a set lookup, and `"guardian": []` crashed the reader instead of producing a verdict (review, PR #103). **The rule a raw field owes is that its predicate is total**, and §10.9 drives an unhashable value through *every* membership-tested position rather than through the one that broke, so the next raw field cannot be added without meeting it.

**A tag that promises a payload must carry it.** `protocol_anomaly` says the connection was torn down for a protocol reason, so it carries *which* — checked against `mcp_proxy.ANOMALY_KINDS`, imported rather than re-derived, since a copy can disagree with the original silently. `shutdown_anomaly` carries both the fact it escaped and the exception. Without those, a record can be structurally valid while withholding the one thing the audit log exists to carry, which is the same defect as a verdict with no reason, one level down. §10.9 pins the validator on each way to be malformed *and* on the one legal record that looks malformed — the `spawn_failed` shape, where every child-and-group fact is legitimately `not_applicable` — because a validator only ever shown invalid input can pass by rejecting everything.

**A completion fact is the proxy's own claim, so one case checks the consequence from outside — and only the part of it that is observable.** Whether the reap happened is *not* observable from another process: a proxy that exited without one leaves a child that init adopts and reaps, and the two are indistinguishable after the fact (review, PR #101). The claim is therefore narrowed to the property that actually matters and to the width of the mechanism that delivers it — **nothing in the child's process group is still alive**, which is what §10.6 says the boundary is and no more (review, PR #103) — and the evidence is monotone rather than a point-in-time probe, so no synchronization with the proxy's exit is needed and none is specified. §10.9 gives the mechanism. `child_reaped` and its `child_status` stay in the record as a claim rather than a proof; the reaper is now the guardian and the proxy records what it reported, which does not weaken the rule that ties them together, because there is nowhere else a status could have come from — the fact and the number arrive in one report or not at all. Fabricating one is still a lie rather than an omission, and that raises the cost of the deception without making the reap externally verifiable, which this design does not claim.

Four rules make the enumerations load-bearing rather than decorative:

- **No default-clean branch.** `is_clean` is total, and an unrecognized reason on either axis classifies as an anomaly. Adding a reason without classifying it must fail the cell, not pass it — the failure has to be the loud one, or the enumeration decays into documentation.
- **Phase is part of the reason, not a flag a caller applies.** `client_write_failed` and `shutdown_write_failed` are two *reasons*; likewise `read_failed` and `shutdown_read_failed`, and `child_exit` versus the ordinary reap of step 3. The paragraph this replaces stated the same rule as a condition — "the distinction is the shutdown having already begun, not the errno" — and a condition evaluated at each call site is the thing that drifts. Splitting the axes is what makes the pairing visible: a live-phase reason with no shutdown-phase counterpart is now a gap you can see, which is how `shutdown_read_failed` was found missing.
- **The reason is recorded, not just the verdict.** The terminator carries the trigger list, the outcome list and the completion facts, so the audit log says *why* an instance ended cleanly and not merely *that* it did. A verdict with no reason cannot be checked against C3-1's table when a CLI changes its shutdown behaviour underneath us — which C3-1 already caught happening once.
- **Totality is necessary and not sufficient.** Both enumerations can be closed, total and fully driven while the three failures that matter most slip through, because none of them has a reason to enumerate: an ending where the process that would name one is already gone, a step that never ran to raise one, and a record so empty that every check over it is vacuously satisfied. Those are the absence rule below, the completion facts above, and the structural validator. **Every time this section has been wrong, it has been wrong about something that produces no record** — three rounds running — which is the argument for spending the effort on the clauses that check for silence rather than on lengthening the tables.

**What is detected by absence.** The rule is one line — **a start record with no well-formed terminator is an anomaly** — and it covers four endings that no enumeration can reach: an uncatchable `SIGKILL` to the proxy; a crash after the start record (uncaught exception, OOM kill); a teardown that died before reaching step 6; and a **truncated** final record, where the reader must treat a partial line as absent rather than repair it into a terminator. This is sound only because no observed CLI destroys the process without warning (C3-1), and it is why the audit log is flushed on every write rather than at exit: a kill arriving between records must not erase the evidence of what came before it.

`tools/verify_mcp_proxy.py` (§10.9) drives every trigger and every outcome against the real program, asserts that `is_clean` is total over both and that every consumer handles every verdict, and drives the absence cases too — the ones with no living process to ask are checked by running the reader over synthetic logs, and the ones about steps that never ran are checked from outside the proxy. A reason nobody can produce on demand is a reason nobody has tested; an ending with no reason at all, and a step that ran no code to report itself, are the ones most likely to be tested by assumption.

The handler itself must not do that work. Re-entrant buffered JSON and file I/O from a signal handler can interleave with a write already in progress and corrupt the very record the verdict depends on. The handler sets a flag or writes a byte to a self-pipe; the control path notices, runs the sequence above, and exits. Note the probe shim takes the shortcut this paragraph forbids — it has no child to reap and its handler writes with a single `os.write()` to an `O_APPEND` fd — so it is a witness to the shutdown *paths*, not a template for handling them. Its single-slot `reason` is sound for the same reason: with no child and no teardown steps it has no second axis to lose.

### 10.6 What the guarantee is, and is not

- **Containment lasts exactly as long as the pin does.** The guardian holds the child unreaped, which is what makes the group's id provably the one this instance created; if the guardian dies while the server is running, nothing portable can re-establish that, and the proxy therefore **refuses to signal** and records `guardian_lost` with both group facts failed (§10.5). The server survives, the cell fails, and the audit says so. This is a real limit and not a bug to be fixed with a better guess — a pgid that cannot be shown to be ours is a pgid that may be someone else's.
- **The containment boundary is a PROCESS GROUP, and that is the whole of it.** Step 4 terminates the child's process group, and the guardian terminates that same group if the proxy dies first — so a server that spawns helpers, the case §10.5 step 4 was written for, is covered. A descendant that calls `setsid()` **leaves that group and survives a clean run unreported**, and no signal either mechanism sends can reach it. This is stated rather than implied because the earlier wording — "nothing from this instance is still alive" — claimed more than a process group can deliver (review, PR #103); every claim about the teardown, in this document and in the checks that drive it, is now phrased at the width of that mechanism rather than at the width of the wish. There is no portable containment stronger than this on both supported platforms; PID namespaces and cgroups are Linux-only. What bounds the exposure is the threat model: step 4 exists for a **sloppy** server that leaves helpers running, and a server that deliberately detaches to keep a credential already *has* that credential in its environment and needs no process to keep it. §10.9 drives the escape as a **measured** case, so the boundary is a checked fact rather than a sentence, and widening containment later fails that case rather than silently outdating it.
- **Hard prevention, both directions.** An off-list tool is removed from what the model is shown, and an off-list `tools/call` never reaches the server. No enumeration, no complement, no drift window — this is a real boundary against a server the scenario author does not control, which is precisely what §6-C2 says `tools:` on claude is *not*.
- **`tools:` gates the server's MCP tool surface — `tools/list` and `tools/call` — and nothing else.** It does not promise that no tool definition can reach a model by any route. **Sampling** is the concrete counterexample: a server may put its *own* `tools` array in a `sampling/createMessage` request, and those definitions are scoped to the sampling request — they "don't need to correspond to registered tools". Legacy carries it as a server-originated request; modern carries it inside `InputRequiredResult.inputRequests`. Sampling is deprecated as of `2026-07-28` but stays specified for at least twelve months, which is inside this harness's horizon.
  The proxy does not implement sampling, but it **detects and refuses** a tool-bearing sampling request as an anomaly. Exposure is conditional — a server MUST NOT send one unless the client declared the `sampling.tools` capability — but the check is nearly free, and a tool definition the model can act on that never appeared in any `tools/list` is precisely the silent wrongness §10.5 exists to prevent.
  C3-0 measured the exposure rather than leaving it hypothetical: **copilot is the only one of the four that declares a `sampling` capability at all**, and it declares plain `sampling`, not `sampling.tools` — so today no shipped CLI may conformantly be sent a tool-bearing sampling request. That is a reason the check is cheap to keep, not a reason to drop it: it costs nothing on three adapters, and the one adapter in range is one capability string away from being in scope.
- **Tool definitions are checked at their *defined locations*, per implemented version — not by scanning for tool-shaped objects.** For `2026-07-28` those locations are exactly two: `tools/list` → `result.tools`, and sampling → `params.tools` inside `InputRequiredResult.inputRequests` (legacy: on the server-originated `sampling/createMessage` request). Both are filtered or refused; nothing else is inspected for tool shape. **"Per version" is a constraint in both directions**: `inputRequests` is a defined location only under `2026-07-28`, so reading it on a legacy response — where `Result` is open-ended and the key may mean anything — refuses conforming traffic just as surely as missing it forwards non-conforming traffic. It is deliberately *not* additionally gated on `resultType: "input_required"`, though: a modern server that put definitions under the wrong label would slip past, and a mislabelled definition is still a definition.
  An earlier draft of this section stated a universal rule — "a tool definition on *any* channel other than `tools/list` is an anomaly" — and specified enforcement on two methods. **That was a claim broader than its mechanism**, the same defect this document has already caught four times in the isolation guards, and it is unsound in both directions:
  - *False positives.* The schema gives `Result` an index signature (`[key: string]: unknown`), and capabilities carry an `extensions` map of arbitrary per-extension settings objects. A legitimate extension may contain a `name` + `inputSchema` shaped object that defines nothing model-callable. A structural scan fails those runs for no reason. (The narrower version of this trap is real too: a `DiscoverResult` legitimately carries `"capabilities": {"tools": {}}` — a capability *flag*, not a definition.)
  - *False negatives.* A future revision that conveys tool definitions in some other shape evades the scan entirely, so the universal-sounding rule would have bought nothing at the moment it mattered.
- **What actually closes the future-channel hole is the version gate, not the scan.** The proxy implements named protocol versions and treats any other version as an anomaly (§10.2). A revision that adds a new tool-bearing channel therefore *fails closed on arrival*, because it is an unimplemented version — not because a heuristic recognized its payload. Recording the new version in the audit log is **not** sufficient on its own: a version that gets forwarded under the broad heading of "modern" is forwarded whether or not it was written down.
- **Other channels pass through.** A server can still serve data through `resources/read`, `prompts/get`, or any future method, and the proxy forwards those verbatim. `tools:` is a **tool allowlist, not a capability sandbox**, and neither the schema docs nor the error messages may imply otherwise — the same rule §6-C3 already sets for C2.
- **It does not make a hostile server safe to run.** It makes the *tool surface* the scenario declared the tool surface the model got.

### 10.7 Telemetry

The audit log is a capability no CLI provides uniformly: wire-level, per call, with the server, the tool, whether it was allowed or refused, and when. Each instance additionally records the **eras and protocol versions it observed** (§10.2) — plural, and *observed* rather than "negotiated", because modern declares its version per request and a client may legitimately speak more than one era on one connection. A recorder that kept only the first would hide precisely the mixed-era client worth knowing about. This doubles as the standing answer to probe C3-0 as CLIs migrate, rather than a one-off measurement that silently expires.

Recording is *evidence, not control*: the thing that keeps an unimplemented version from being forwarded is the §10.2 gate, applied to every request including the first. A design that logged the version while still passing the traffic would have documentation of its own failure. **It is not, today, recorded per cell like any other artifact — this sentence said it was, and that was never built.** The log is written into the per-cell MCP scratch dir, read there by `verify_post_run`, and purged with the dir; nothing copies it into `artifacts/`, so the scrubbing pass never sees it either. Two consequences worth separating. The **secrecy** rule is unaffected: `mcp_proxy_io` keeps argv, the environment, the config and anomaly detail out of the log on the standing rule that a secret must never go where the scrubber has to catch it, which does not depend on where the file ends up. The **telemetry** claim below is the one that is currently aspirational — evidence deleted at the end of the cell is evidence for one exit-status decision and nothing else — so making it real is a piece of work (archive it, scrub it, decide its retention) and not a description of the present. It is stronger evidence than parsing a transcript for tool names, and it is the natural substrate for the portable `used_mcp_tool` assertion (§7) — which currently has to reconcile four naming conventions across four adapters, none of them the wire.

### 10.8 What stays refused

- `tools:` on a **remote** server — no bridge yet, so the allowlist could not be enforced; refusing is unchanged behaviour.
- `tools:` on an adapter that cannot inject at all — unchanged; the server would not be there either way.

### 10.9 Testing

The proxy is a program with a defined wire protocol on both sides, so it is testable without any agent CLI: **`tools/verify_mcp_proxy.py`** drives it with a scripted client over pipes and a fixture server, and asserts the filtered list, the refused call, verbatim pass-through of a non-tool method, the notification rule, and a recorded anomaly plus failing verdict for each malformed case — including the envelope cases (batch array, response with no `id`, both-`result`-and-`error`) that a "no `id` means notification" reading would wave through. It also drives **every trigger and every cleanup outcome in §10.5.1**, each on demand, because a reason nobody can produce is a reason nobody has tested — and it asserts the two axes stay independent, by driving one anomalous trigger through a *clean* teardown and one clean trigger through an anomalous one, which is the pair a single-slot reason cannot tell apart.

**The endings with no reason need their own cases, and half of them are checked against the reader rather than the program.** `SIGKILL` to the proxy and a teardown aborted before step 6 are driven live and assert start-present/terminator-absent/verdict-anomalous; a crash after the start record and a **truncated** final line are driven as synthetic audit logs through `verify_post_run`, asserting it treats a partial line as an absent terminator rather than repairing it — and, since the same reader owns it, that a clean terminator for a *different* instance id never satisfies an unterminated one (§10.5).

**The clean path needs a positive case, driven from outside the proxy.** Every anomalous case above asks whether the proxy noticed something; none asks whether it *did* anything, and a teardown that skipped step 4 entirely raises nothing to notice (§10.5.1). So one case has the fixture server spawn a credential-bearing helper into its own process group and runs an ordinary clean shutdown. It is the only check that can tell a proxy which tears the group down from one that merely claims to, and its absence would be invisible: every other assertion passes just as well against a proxy whose step 4 is a no-op.

The evidence is a **pipe, not a probe** — one per lifetime the driver needs to observe, which turns out to be two. The driver creates each pipe, passes the write end down to be inherited to a chosen depth, holds the read end, and never writes. Reading EOF proves every process holding that descriptor is gone; anything short of EOF within a bounded wait fails the case. This is deliberately not `kill(pid, 0)` polling: a probe is a point-in-time question that races the proxy's own exit and can be answered by a recycled PID, whereas EOF is monotone — once true it stays true, and before it is true something is demonstrably alive. That monotonicity is what removes the need to hold the proxy open after the terminator, which would otherwise need a pause the fault-point machinery cannot supply, since arming it makes the instance anomalous by construction (§10.5.1) and this case must come out clean.

**EOF is only evidence if the descriptor ever got there, and that premise is per channel.** A broken `pass_fds`, or a holder that closes its writer while starting up, hands the driver an immediate EOF and a passing case with nothing torn down — the same "nothing happened" success this section keeps finding, this time in the instrument rather than in what it measures. So the requirement is stated once, as a rule over **every** liveness channel here rather than as a fix to whichever one was last found wanting:

> A channel is evidence only with a **two-sided proof**: its intended holder announces itself through it, the driver confirms **no premature EOF**, and a **control keeps that holder alive on purpose and requires the channel stays open**. Only then does EOF mean the holder is gone.

Writing it as a rule is not tidiness. The child channel below was added to fix a defect in the helper channel and was introduced carrying the *same* unverified premise — never passed to the child, EOF immediately, accepted as proof the child exited (review, PR #101). That is `CLAUDE.md`'s first rule failing on the same page it was being applied on, and the quantifier is the fix.

**There are two channels, scoped one level apart.** The **helper channel** runs driver → proxy → child → helper and proves the *group* is gone; the **child channel** runs driver → proxy → child and is not passed on to the helper, so it proves the *direct child* is gone. The second exists because "wait for the child to exit" is not something the driver can otherwise observe: it did not spawn that child, so it cannot wait for it; the spawn record supplies identity, not death; a pid liveness probe is a point-in-time question with a recycling hazard; and the terminator's `child_reaped` is the claim these cases exist to test, so leaning on it would be circular. The proxy's own exit needs none of this — the driver spawned it and waits for it directly.

**Each channel's holder announces itself with a nonce-bound readiness record**, then holds its writer open for the rest of its life and writes nothing further. The nonce is generated by the driver per case and echoed back rather than chosen by the announcer, so a process left over from an earlier case cannot answer for this one — the same reason instance ids exist in the audit log. The helper reports its own process group id; the child reports its pid and process group id. Those are there because the control has to terminate that group, and the only non-guessing source for a group id is a process inside it: discovery from outside would be the driver deciding for itself which processes belonged to the run, which is how a cleanup ends up reaching further than what it created (§4). The driver refuses to signal its own group or an ancestor's, for the same reason.

**Three reports of the same identity now exist, so they are cross-checked before any of them is acted on.** The child's own record, the proxy's spawn record, and the helper's record must agree on the group, and the child must satisfy `pid == pgid`, since `start_new_session=True` makes it its own group leader — a launch decision that exists precisely so step 4 has a group to signal (§10.5). The child's record is the independent one: the spawn record is the proxy's account of what it did, and this case is about not taking the proxy's word for anything. Disagreement fails the case rather than being reconciled, and only a vouched-for group is ever signalled. Without this the control can be satisfied by the wrong group entirely — a mis-grouped helper announces itself, survives, is cleaned up successfully, and the child's actual process group, the only thing step 4 is meant to terminate, was never under test at all.

**Announcing proves a process once held its descriptor; it does not prove it is who still holds it.** Every process on the inheritance path gets a copy, so a holder that announces and then closes its writer is invisible: the ancestors keep the pipe open, the pre-shutdown check sees no EOF, and after they exit the EOF arrives with the holder still running. The topology is therefore explicit, and every stage closes its copy as soon as it has handed it on — **the driver closes both writers once the proxy is spawned, the proxy closes its copies once the child is spawned, and the fixture parent closes its helper-channel copy once the helper is spawned** while never passing on the child channel at all. The driver's own closes are not bookkeeping: hold one and its EOF can never arrive, so the positive case would hang rather than pass. With the handoff done each channel has a **sole writer**, and that is what makes an observation about a channel an observation about a process.

**One control covers both channels, and where it observes is what makes it mean anything.** Non-EOF proves only that *someone* still holds a writer, so taken while an ancestor is alive it proves nothing about the intended holder — and two defects then cancel: a helper that closes its writer early and survives, plus a proxy that retains its copy until exit, gives a positive case passing on the proxy's exit and a control passing on the proxy's copy, with the survivor invisible to both. So the control suppresses **steps 3, 4 and 5 together**, leaving both the child and its group alive on purpose, and the order is fixed:

> both records → no premature EOF on either channel → suppress steps 3–5 → run the shutdown → wait for the terminator and for the proxy to exit → require **both channels still open** → kill the cross-checked group → require **both channels reach EOF**.

**Step 5 has to be in that list, not just 3 and 4.** A child deliberately left alive cannot be reaped, so a control that suppressed only the killing would either hang in step 5 or reach the terminator by way of the reap giving up — a slow path, and one that reports `shutdown_reap_failed` for a reap that was never really attempted. Suppressing the three together keeps the terminator reachable and keeps the record *true*: the fault point is armed on `child_reaped` and `group_terminated`, a `fault_point_fired` record is written for each as it suppresses them, both facts read `failed(fault_point_fired)` as the pairing rule requires (§10.5.1), and `child_status` is absent because nothing reaped anything. Naming the facts rather than the step numbers is what makes that configuration checkable — steps 3 and 5 produce one fact between them, so a step-keyed fault could not say which. The terminator therefore stays required in this case rather than being waived for an instrument-only run, and that is worth having — it makes the control an end-to-end demonstration that processes surviving and the record saying so are the same event.

That middle observation is the whole case. By then the proxy is gone and no ancestor holds either writer, so two channels still open can only be the child holding one and the helper holding the other — which is simultaneously the ordering requirement, the proof that each descriptor reached its intended holder, and the proof that the child channel really is scoped one level shallower than the helper's. The closing EOF is not ceremony either: it separates a real non-EOF from a stuck reader, so the control cannot pass by never observing anything at all. Then the driver kills that group, because a test for leaked credential-bearing processes must not be the thing that leaks one.

One further property makes the cases discriminating rather than decorative, and it is a requirement on the fixture that the control is what enforces: **the helper must survive everything except a group signal** — it must not exit on its own, must not die when its stdin closes, and must outlive the bounded wait — or a proxy that skipped step 4 would pass on the helper's good manners.

**Two more fixture requirements, both found by the cases failing for reasons that had nothing to do with the proxy.** They are recorded because each is invisible until it bites, and each makes the instrument agree with something it should not have been coupled to at all:

- **The helper must not inherit the proxy's stderr.** The child's stderr *is* the proxy's, which is a descriptor the driver holds — so a helper that inherited it keeps that channel open, and the driver's read of it blocks until the helper exits. A liveness case whose instrument deadlocks on the very process it is meant to observe surviving proves nothing at all. (The driver's own fix is the same shape from the other side: the proxy's stderr goes to a *file*, because anything in the group can hold a pipe.)
- **The control's child must stay alive with its stdout closed.** A fixture that exits when its stdin closes EOFs the child channel by itself, and the case is then observing the fixture's manners rather than the suppressed steps — the same substitution this section warns about one level up. Closing stdout while remaining alive is what lets the drain settle cleanly, so the only anomalies in the control's record are the injected ones. (What kept the child's liveness from being read as the helper's used to be a rule about distinct tokens; with a channel per depth it is now structural, which is the better form of the same guarantee.) What the cases then assert is the observable property, **no process from the instance is still alive**, not the unobservable one: the terminator's `child_reaped` remains the proxy's own claim and is checked for consistency, never confirmed from outside (§10.5.1).

**The structural validator is driven on records, not on runs.** The verdict's other two clauses are universally quantified and therefore vacuously true of a record with nothing in it (§10.5.1), so the validator is pinned on synthetic terminators through the same reader: an **empty trigger list**; each completion fact **missing**, one case per fact rather than one case for the set, since a validator that checks all but one passes a single spot-check; `not_applicable` on a record whose trigger is not `spawn_failed`; **`failed` without its paired outcome, and that outcome without a `failed` fact** — both directions, since a validator that checks one of them lets a proxy record the failure on whichever axis it finds convenient and stay silent on the other; a `failed` fact paired to a `shutdown_anomaly` **keyed to a different fact**, which is the form that lets one catch-all excuse a failure anywhere in the record — including the **within-step** pair that a step-keyed check cannot see at all, an anomaly for `child_stdin_closed` licensing `drain_ended: failed` and the reverse; `failed(fault_point_fired)` with **no matching fired record**, a fired record whose fact does **not** read `failed`, and a fired record for a fact the configuration **never listed** — the three ways arming and firing can be made to stand in for one another; `child_status` **missing under `done`** and `child_status` **present under `failed` or `not_applicable`**, the two halves of the rule that a reap and its evidence travel together; an unrecognized completion **state**; an unrecognized completion-fact **name**, which is what a validator iterating only the names it already knows will accept — and therefore how a fact added later quietly stops being checked; and — the case that keeps the validator honest — a **valid `spawn_failed` record**, whose legitimately inapplicable facts are exactly what a lazily-written validator rejects along with the malformed ones. Without that last case, "rejects everything" scores full marks.

**The guardian and the group's limit are both driven.** Two cases end an instance whose server ignores `SIGTERM` and lingers — one by `SIGKILL`ing the proxy before its teardown, one by letting the teardown run — and both require the child's liveness channel to reach EOF, which is the same monotone evidence the teardown cases use pointed at the one ending that has no teardown to observe. A third drives a helper that calls `setsid()` and asserts what actually happens: the run comes out **clean**, `group_terminated` says `done`, and the helper is **still alive**. Asserting the limit rather than the wish is deliberate — a documented boundary nothing checks is a boundary that outdates itself quietly, and this one fails loudly if containment is ever widened.

**"Fail closed" is a claim about paths, so the paths are producible on demand.** A `ASE_MCP_GUARDIAN` knob breaks the guardian at each point it can fail, each of them a sentence from the review made reachable: its program is **missing** so `Popen` raises; it is **silent**, exiting before it reports ready; it is an **imposter**, reporting a pid that is not its own; it is **late**, exiting once the child exists. The first three must end `spawn_failed` with **no spawn record and no server having run at all**, and the last must latch `guardian_lost`. What makes "no server ran" more than an absence is a **positive control**: the same wiring, with a working guardian, is driven first and asserted to produce the announcement — because a channel nothing was ever passed to reports exactly the silence a channel whose holder never started does (§4).

Like the fault point, **the guardian injection is recorded in the start record**, in the same map as the suppression targets. While it was an env var the proxy read and never wrote down, an injected guardian failure was indistinguishable in the audit from a real one (review, PR #103) — a fault point with no provenance, which is the one property `fault_point_configured` exists to supply. Being in that map also means it arms the fault point on its own: a run with a broken guardian and no suppression list is the arm-only case one axis over, and it cannot produce a passing instance.

**"No server ran" needs two witnesses, because the obvious one is a race.** The end-to-end witness is the review's own: a marker file created by a `/usr/bin/touch` child, which survives the child and so records an execution that was killed a millisecond later. But a regression leaves that child alive only for as long as it takes the proxy to reject a report and the guardian to sweep, so the marker appears about **one time in twenty** — corroboration, not proof, and its sensitivity is written down rather than assumed. The deterministic witness is the **guardian's own account of how far it got**: under an injection it names each phase it reaches on stderr, and the pair of runs is matched — the imposter stops at `authenticated` because a rejected guardian is never told the command, while the accepted `late` injection reaches `launched`. The subject of that claim is the *proxy's* behaviour and its author is the guardian, so they are not the same process; the positive half is what stops "the string was absent" from being satisfied by a mechanism that never worked at all.

**A teardown that ran and failed is cleaned up, and that is checked from both sides.** Two cases fail step 4 through the fault point's `fail` mode — which records the step's own typed outcome and fires nothing — and require the survivors to be gone anyway. They differ in *which* sweep does it, because the two are not interchangeable: with only step 4 failed the reap order is still sent, the child exits on its own, and the survivor is a **helper** that only the sweep inside the release order can reach, since releasing the pin is the moment nothing can act any more; with steps 4 and 5 both failed no order is sent at all and the survivor is the **child**, reached by the sweep on the lifeline's EOF. Their mirror is the retention control, where a fault point *fired* and the survivors are kept on purpose. Between them the rule is pinned in both directions, which is why `fail` and `suppress` are different modes.

**A dead diagnostic channel is driven too.** One case closes the read end of the proxy's stderr before it starts, lets the child announce itself, and then `SIGKILL`s the proxy: the guardian's sweep must still happen, which it does because the signal precedes the message and the message cannot raise. A second points the same broken stderr at the proxy's own pump, where a malformed line is printed before it is classified — a raising `print` there would be caught by the pump's catch-all and recorded as `read_failed`, a protocol fault logged as a pipe fault, which is the worst of the three possible outcomes because the log then names the wrong thing.

**Every case that deliberately leaves a process running cleans it up in `finally`, from an identity that process reported.** Nonce-bound, cross-checked, and never discovered: the driver refuses its own group and its parent's, for the reason §4 records. Cleanup written inline after the assertions is cleanup the exact failure or mutation under test is most likely to skip — the stuck-drain case leaked its escaped helper for a full ceiling that way (review, PR #103). And an announcement is a **past** fact, so the licence to act on it is a **present** one: by cleanup time the proxy and its guardian are gone and nothing holds the pgid against reuse, so the driver signals only while the announcer's liveness channel is **not at EOF**. That is the same pin the proxy's rule uses, obtained the only way a non-parent can obtain it — the channel's sole writer is the announcer, a live announcer means its group exists, and an existing group's id names that group and no other. It is idempotent besides, since one group produces two announcements.

**The totality checks over both enumerations run last in the file, not at the end of their own sections.** They quantify over every run there is, and while they sat mid-file they were answered by the runs above them and blind to every run below — which the first reason added afterwards, `guardian_lost`, would have walked straight past.

**The fault point is itself under test.** Reaching the live absence cases needs one inside the proxy, and it is safe only under three constraints: it is read once at startup from an env var the driver sets; **its configuration is recorded in the start record as `fault_point_configured`**, naming the exact completion facts it is armed on (§10.5.1), and always anomalous on its own; and one case pins that last clause in isolation.

**It has three modes, and the second and third are what "each on demand" turned out to cost.** Suppression alone reaches the control case and nothing else. Three cleanup outcomes cannot be arranged from outside the proxy *at all*: a read error on a pipe the proxy itself created, a child that survives a group `SIGKILL`, and a `killpg` that fails for a reason other than the group being gone. So:

- **suppress** — the step does not run; the fact reads `failed(fault_point_fired)` and the firing is recorded. This is the control's mode.
- **fail** — the step does not run and the record carries the step's **own typed outcome**, with *no* firing. That distinction is load-bearing rather than cosmetic: §10.5.1 requires exactly one cause, and a record holding both would say the step was attempted and failed *and* that it never ran, which is the contradiction the declared-cause rule exists to reject. It is refused at startup for the two facts that have no typed outcome, because inventing a `shutdown_anomaly` there would fabricate an exception that never happened.
- **abort** — the process exits at that point, writing no terminator. This is §10.9's "teardown that died before reaching step 6", made deterministic instead of raced against a signal.

None of the three can make a run pass: the instance is anomalous from the **arming**, before any of them does anything.

**And this is where the coverage claim stops, stated rather than implied.** The `fail` mode drives the *record* for those three outcomes — that the pairing holds, that the cause is declared, that the verdict is anomalous — and **not** the code path that would produce them in the wild. A read error inside the drain loop, and a `wait()` that times out after a group `SIGKILL`, remain unexecuted. That is the same class of limit as `child_reaped` not being externally verifiable, and it is written down for the same reason: an untested path that nobody has said is untested reads as a tested one.

That case arms the hook in **arm-only** mode — configured, recorded, and wired to suppress nothing, which is its entire purpose. The run is then ordinary: a clean trigger, an empty outcome list, every completion fact `done`, and **no `fault_point_fired` record anywhere**. The assertion is that the verdict is nonetheless anomalous, and that is a genuine regression test precisely because the case would go green if `fault_point_configured` were dropped from the conjunction — nothing else in the record is anomalous, so no other clause can be covering for it. Without it, arming a fault that silently never fires produces a clean trigger, clean outcomes, a passing verdict, and a test that certified the untested case. An earlier attempt at this case armed the hook on a fact the scenario never reached, which does not pin the clause at all: the only trigger licensing `not_applicable` is `spawn_failed`, itself anomalous, so the case stayed red with the clause deleted (review, PR #101).

**The module is split by testability, and the split has two pure halves.** `tools/mutate_mcp.py` proves arms by running a suite, so anything reachable only by driving the real program over real pipes carries no mutation coverage. Everything that could be *silently* wrong therefore lives in pure functions an arm can call and a mutation can break: `agentskill_evals/mcp_proxy.py` decides what may be forwarded, and `agentskill_evals/mcp_audit.py` holds this section's record types, the structural validator and `verdict()`. The I/O half keeps only reads, writes, spawning and shutdown sequencing, which a wire-level driver can observe.

The audit half is written **before** the code that produces the records, because every defect the review of §10.5.1 found was a shape — a failed step with no legal value, a catch-all unreachable from most steps, a pairing key coarser than the thing it keyed, arming standing in for firing. Prose held all four without complaining; a validator and its arms reject them in seconds. That is also why `fixtures/` and `tools/` are now mutation targets in their own right, proven by `verify_mcp_fixtures.py` rather than by the selftest: this section's driver adds a large number of named assertions to a file where, until now, nothing proved that any assertion could fail.

**`mutate_mcp.py` therefore runs three suites, and the third arrival forced a split that was wrong from the start.** The class of a mutation — `M` production, `I` the selftest itself, `F` an instrument — was being read off *which suite proves it*, which happened to agree while there were two. It stops agreeing here: `mcp_proxy_io.py` is production proven by a driver, and `proxy_target_server.py` is an instrument proven by the same one. The class now comes from the file's own path and the suite from a named list, because "what does this perturb?" and "who would notice?" are two questions and only one of them determines which total a mutation belongs in. The named list is unavoidable: both of the third suite's files sit in directories the other two suites own.

**`mutate_mcp.py` is now also a mutation TARGET, and the argument admitting it is the one §9's probe reader already made.** A verifier cannot be mutated — the mutated program and the program judging the mutation would be the same one — and that had been read as covering the runner too. It stopped being true once `verify_mcp_fixtures.py` began driving the runner's suite-readers (§E17): that is a different program, executed from the mutated copy while the runner doing the judging keeps running from the original tree, which is the whole content of the separation the rule protects. Reopening it was not tidiness. The suite record grew a third field for the arm-names-a-real-check guard, `run()` was not updated with it, and the runner could not start **either** verifier suite for a full push — because the only thing that had ever executed those readers was the 63-minute run itself. An instrument exercised only by its slowest path has its breakage discovered late by construction. The line is not the file: what §E17 drives is admissible, and the runner's own scoring — `_classify`, the caught/missed accounting, the anchor guards — is not, since a mutation there would be judged by the code it perturbs. The same reasoning puts the opt-in live probe's startup path under §E18, for the mirror-image reason: nothing routine runs it, which is exactly how a fix landed in the verifier and not in the copy meant to be re-run.

The line is drawn at **`decide()`**, which takes one wire line plus the connection's state and returns an *action* — forward, forward-this-filtered-message-instead, answer-the-sender, or fail. Not at the predicates. The first cut exported predicates and formatters and left the combining to the I/O half, which put the load-bearing step — "may this be forwarded?" — back on the side no mutation can reach: an arm calling `refusal_for()` proved a refusal was well worded and proved nothing about whether an off-list call is ever refused, and would have passed against a proxy that forwarded every one (review, PR #100). It is the same defect as M117 and M125, and the same test applies — *state what a broken implementation would produce, and check the assertion rejects it*.

Three arms deserve naming because each pins a rule that a plausible implementation gets wrong:

- **Era by metadata, not by method.** A connection whose *first* message is an ordinary `tools/list` carrying modern `_meta` must classify as modern and proceed. An implementation that waits for `server/discover` or `initialize` to decide would stall here — and `server/discover` is optional for clients, so this is a conforming client, not an exotic one.
- **The version gate fails closed.** A request declaring a version the proxy does not implement raises an anomaly, even though it is well-formed, modern, and would parse fine. This is the arm that stands in for every future revision, so it is the one that must not be quietly relaxed to a warning.
- **Capabilities are not definitions.** A `DiscoverResult` whose `capabilities` contains `"tools": {}` passes clean and unmodified. It is the regression test against reintroducing a structural scan: that shape is what an over-broad check trips on, and it appears in *every* modern handshake, so getting it wrong takes down every gated cell rather than an edge case.

`fixtures/echo_mcp_server.py` provides the server side, but it is **legacy-only** — it answers `initialize` and knows nothing of `server/discover` or per-request `_meta`. C3-0 settled the open question: agy speaks `2026-07-28`, so the fixture needs **both** modes, not one. Dual-era fallback is a distinct code path with its own failure modes (notably the timeout branch), and it is now on the critical path rather than a contingency.

`fixtures/probe_era_mcp_server.py` is the working model for that: it already serves both eras and carries a `PROBE_MCP_MODE` switch that forces the legacy-refusal path on demand. It is a measuring instrument rather than a test double, so it is not the fixture — but the era handling can be lifted rather than rediscovered.

Live verification against all four CLIs comes after the offline arms, and the C3-1 finding gives it a specific target: codex and copilot exercise the `SIGTERM` terminator path that claude and agy never will, so a proxy validated only against claude would have a completely untested shutdown path on half the fleet.

**A second live target, now measured: probe C3-2** (§9). §10.2's era rule REFUSES a request pipelined behind an unanswered `initialize`, and the measurement says no shipped CLI is refused by it — three legacy CLIs wait, and agy has no handshake to pipeline behind. `tools/probe_mcp_pipelining.py` re-runs it; three of the four cost one cheap model call each, and claude is free because `claude mcp list` health-checks stdio servers with a full handshake. The instrument has its own regression in `verify_mcp_fixtures.py` (E13), checked in **both** directions — an instrument that reports pipelining for everything is as useless as one that reports it for nothing, and the second is the plausible failure, being what a buffered read path produces. The probe that *reads* the instrument has its own (E14), because it is a different program: E13's checks all stayed green over a classifier that would have reported a CLI which died before handshaking as "modern `n/a`", and the classification — not the log — is what a design decision gets justified by (review, third round on PR #100). `classify`, `unmeasured` and `summary` are functions rather than an `elif` chain inside `main()` for exactly that reason.

**Every reason a run might be untrustworthy lives in `classify`**, including the shim's own health. A broken instrument is the row that *looks* answered — the reader can die after an era and a pipelining record are already logged — so when `reader_failed` was threaded into the exit status alone, the tool printed "No CLI pipelined, across the whole fleet … costs the fleet nothing" and then exited 1 (review, tenth round on PR #100). That is the fleet-wide-claim-from-an-incomplete-run defect again, arriving through the one door the earlier fix did not cover, because `unmeasured` had been taught two ways of being unanswered and this was a third. `INSTRUMENT_FAILED` is now a classification like any other, checked first, and the summary names the cause rather than only the absence.

### 10.10 The transport bridge — stdio in, HTTP/SSE out (design)

The last piece between this harness and §8's motivating pattern. The scope note in §10 has always excluded it, and #107 gave that exclusion a check of its own; this section says what lifting it costs.

**Scope: `transport: http` only. `sse` + `tools:` stays refused, by name.** The schema admits both remote transports and the adapter writes both today (§9 probe #1 confirmed each live), so "the bridge lands and remote servers work" would silently claim a binding this section does not specify. **Streamable HTTP and the deprecated `2024-11-05` HTTP+SSE pair are different state machines, not one with an option**: there, a GET opens the receiving stream, its first `endpoint` event supplies a *second* URL to POST to, POSTs are answered `202` with the actual replies arriving back on the original stream, and correlation therefore spans two connections. `fixtures/http_mcp_server.py` implements that pair — it is measurable, not hypothetical — and none of it appears in anything below. Specifying one back half and shipping two is the error #107 was about, arriving before the code rather than after it.

The refusal has a place to live because #107 built one: `Adapter.tool_filter_for` answers per server and returns a reason, so `sse` + `tools:` gets a message naming its transport, exactly as `url:` + `tools:` does today. That it costs one branch rather than a new mechanism is the return on that round.

**What does not change is most of it, and that is the design's one piece of luck.** The decision layer operates on *messages*, not on pipes: `decide()` takes a line, a direction, an allowlist and the protocol state, and knows nothing about where the line came from. So §10.4's interception rules, §10.2's era gate and version allowlist, the direction-scoped correlation maps, §10.6's defined-locations rule and the whole anomaly set are transport-independent and are reused verbatim. The CLI still speaks stdio to the proxy, so nothing in the adapter's config shape moves either — `claude._write_proxy_config` changes only in what it stops refusing. **The bridge is a new back half for one existing program, not a second proxy.** Any design in which the two transports grow separate decision layers is wrong on arrival, for the reason §4 gives about duplicated rules: two copies of the allowlist logic can disagree, and the one that disagrees silently is the one carrying the credential.

**"Verbatim" is a claim about `decide()`, and it needs a decoder underneath it that stdio did not.** `decide()` takes a *line*, and a POST here may be answered `text/event-stream` — a framing layer with its own rules, carrying zero or more JSON-RPC messages, comment and priming events with no `data` at all, and reconnect metadata. So there is a stage between the socket and the decision layer that has no stdio counterpart, and it has its own anomaly boundary. Leaving it unstated would be claiming reuse for a program that does not exist yet:

- **Only a COMPLETE event's `data` payload reaches `decide()`.** An event still being assembled when the stream ends is not a short message, it is an unfinished one, and the stdio half already has this exact rule for a partial line at EOF: not a message, and terminal.
- **Every JSON-RPC message on the stream goes through `decide()`, not just the first.** A stream may carry several, and the plausible defect is an implementation that treats the stream as "the response" and forwards whatever follows it — which is unfiltered traffic reaching the client through a door the allowlist never saw.
- **A `data` payload that is not parseable JSON is the anomaly it already is**, reached through the decoder rather than around it.
- **A comment or an empty priming event is framing, not a message**, and is dropped without reaching `decide()`. Note that the same bytes mean opposite things on the two transports — a blank line is terminal on stdio and is the *event separator* here — which is the specific reason the framing rule cannot be shared even though everything above it is.
- **Resumability is unsupported, and it fails BY NAME rather than by silence.** `id:` on an event is inert while nothing reconnects, and `retry:` is inert for the same reason; what is not inert is a stream that closes before the response to the request that opened it. That is precisely the point at which a resumable client would reconnect with `Last-Event-ID`, and this one cannot — so it is the **`stream_lost`** trigger (below), never a generic read failure, because the two would be indistinguishable in the log at exactly the moment the difference matters.

§10.9's driver covers the empty priming event, a stream carrying more than one message, and a premature closure, for the usual reason: an arrangement nobody can produce is an arrangement nobody has tested.

**What does change is the ending model, and it changes structurally rather than by degree.** §10.5's six steps and §10.5.1's five completion facts are stated over a **child process**: close its stdin, drain its stdout, escalate `SIGTERM`→`SIGKILL`, terminate its process group, reap it. Four of the five facts name that child. A remote connection has no pid, no process group, and nothing to reap.

**But it does not follow that a remote instance leaves nothing behind, and the thing it leaves is the one that matters.** Three candidates, in ascending order of how long they outlive the proxy:

- **Sockets.** Local, closed by process exit, reclaimed by the OS. Not interesting.
- **An open SSE stream.** A GET this instance opened and the server is still writing to. Closed by closing the socket, so it dies with the proxy — but it must be closed *deliberately*, because a stream still delivering messages while the teardown believes it has stopped forwarding is §10.5's "never degrades" rule broken on the way out.
- **A session.** The Streamable HTTP binding identifies one with `Mcp-Session-Id`, and it is **server-side state this instance created, holding whatever the credential bought, outliving every connection to it.** Nothing local reclaims it. This is the remote analogue of the surviving credential-bearing process that §10.5 step 4 exists for, and it is *worse* in one specific way: an orphaned process is at least visible to `ps` on a machine someone controls, while an orphaned session is visible only to the server.

So the teardown's job is unchanged in principle — leave nothing from this instance alive — and entirely changed in mechanism.

**The completion facts are per transport, and the key set stays closed in both directions.** The tempting shortcut is one `FACTS` tuple with the stdio half recorded `not_applicable` on a remote run. That is wrong, and the existing code says why: `not_applicable` is licensed by `_NOT_APPLICABLE_LICENSED_BY`, which maps a fact to the **triggers** that permit a blank, because "the licence means the step never applied, and only the event that ended the instance before the step could apply can say that". A licence keyed on transport would merge two different reasons a step did not run — *the instance ended too early* and *this kind of connection has no such step* — and telling those apart is the entire content of §10.5.1's two axes. So: `FACTS_STDIO` as it stands, plus `FACTS_REMOTE`, with the **transport carried as a required field of the start record** and the validator selecting its closed key set from it. A record naming a transport the reader does not know is an anomaly, exactly as an unrecognized fact is — the direction that is easy to forget, and the one §10.5.1 already closes for facts.

`FACTS_REMOTE`, in step order:

| fact | what it asserts | its typed failure |
| --- | --- | --- |
| `intake_closed` | shared with stdio, unchanged — step 1 is the same on both | none (`shutdown_anomaly`) |
| `requests_settled` | every in-flight HTTP request either completed or was abandoned deliberately | `shutdown_request_failed` |
| `streams_closed` | every stream **still open when the teardown began** was closed by it, and the record says how many there were | `shutdown_stream_failed` |
| `session_released` | the session was terminated — or the server issued none, or it is unknown whether one exists | `shutdown_session_failed` |

**`streams_closed` is quantified over what was still open, and it carries the count.** Two earlier spellings were both wrong, in opposite directions. "Every stream this instance opened" is false of the ordinary clean path: a POST answered `text/event-stream` closes after its correlated response, which the binding recommends, so most streams are already gone before a teardown starts and were never the teardown's to close. "Closed **by the teardown**" — the repair for that — made it false in the other direction, since it says of a stream that closed normally an hour earlier that the teardown closed it.

What the teardown is actually responsible for is **the set still live when it begins**, which may be empty. That makes the fact universally quantified over a possibly-empty collection, which §4 names as its own trap: `done` would be satisfied by a teardown that enumerated nothing, and by one whose enumeration was broken, identically. So the record carries **what was open and what happened to each**, and `done` over zero streams is a recorded zero rather than a vacuous truth — the same shape as `child_reaped` carrying the child's exit status instead of a bare state.

**`requests_settled` and `streams_closed` are two steps, not a partition of objects, and one POST can be in both.** A POST answered `text/event-stream` is an unsettled *request* until its correlated response arrives on that stream, and an open *stream* until the stream ends — so at a teardown that catches it mid-answer, both steps have work to do about the same connection. Reading them as a partition is how one of them ends up skipping the case the other appears to cover.

**And that dissolves one of the two licensing questions: after the connect record exists, `streams_closed` is never blank.** Closing whatever is open is a step that always runs, over a set that is sometimes empty, so an empty set is `done(count=0)` and not a blank. `session_released` is genuinely different — there is no release step at all when the server issued no session — and the distinction generalizes: **a step that runs over a set is always applicable; a step that exists only if some thing exists is not.** So the *capability* source of a licence — the server declining to offer something — covers `session_released` and nothing else on this transport, and a `405` to the standalone GET licenses no blank anywhere.

**"After the connect record exists" is doing real work in that sentence, and an earlier draft dropped it and stated a universal.** The other licence source is untouched and still applies: an instance that ended *before* there was a back half at all has no step to have run, which is exactly what `spawn_failed` licenses on the stdio side and what `connect_failed` licenses here. Saying "never `not_applicable`" flatly contradicted that, and the contradiction is the very error this section is otherwise about — **two different reasons for a blank merged into one claim**: *the phase was never entered* and *the capability was never offered* are not the same fact, and only the first is an ending. `requests_settled` sits on the same rule for the same reason, which is why it stays blank under `connect_failed` and applicable, possibly over nothing, after.

**`session_released` is where the honesty has to go, and it needs a fact recorded at connect time rather than an inference at teardown.** The binding makes `Mcp-Session-Id` optional — the fixture's own scope note records this, and says a server keeping no session state is conformant without it — so "there was no session to release" is a legitimate `not_applicable`. It may not be inferred from the absence of a session id at teardown, because that is also what losing track of one looks like. The **connect record** is the remote analogue of the spawn record and carries the same weight: as the spawn record carries pid, pgid and guardian pid — facts the start record cannot hold, since it precedes the spawn — the connect record carries the negotiated protocol version and a **tagged session disposition** (below).

**And it carries no resolved URL, which is a correction rather than an omission.** Two drafts put "the resolved endpoint" in these records, on the assumption that a URL is addressing rather than secret. `${VAR}` is honoured in `url` — `interpolated_refs` lists it beside `env` and `headers` for exactly this reason — so `https://host/mcp?token=${TOKEN}` resolves to a URL that *is* a credential. **"Endpoint only, never the headers" was the wrong axis**: the question is not which field, it is whether the field's value space is under this harness's control, and for `url` it is not. Nor is scrubbing an answer — §4 already records that the redaction set omits values shorter than `MIN_REDACTABLE_LEN` and that a short credential is still a credential, so "it would be scrubbed" is precisely the reasoning that rule exists to refuse.

The rule does **not** rest on the log being archived, and an earlier draft justified it that way — see §10.7, where the same overstatement lives. `mcp_proxy_io` already states the standing rule without reference to archival: "the one thing this program must never do is put a secret somewhere the scrubber has to catch it", which is why argv, the environment, the config and anomaly detail text are all kept out. A file written to disk, read back by the harness, and quotable into a failure message that *does* reach `result.json` is enough for the rule to bite.

The identity these records carry is therefore the **declared server name**, which the start record already holds and which the schema forbids interpolating into — `[A-Za-z0-9_-]+`, no `${` anywhere. It is safe *by construction* rather than by inspection, and that is the property to select on: no subset of a resolved URL has it, since a secret can be placed in the query, the path, the userinfo or a subdomain. Whoever needs the endpoint reads the scenario, where it is written with the variable unresolved. A `not_applicable` on `session_released` is then licensed by a recorded positive fact rather than by silence, which is the rule §4 states for every universally quantified check — with one further case where *no record exists at all* and the guardian protocol supplies the positive fact instead, set out in the cross-product below. `session_released` is the one fact both licence sources reach; everything else takes exactly one.

**That makes the licence machinery two-sourced on this transport, and it is worth naming rather than discovering.** `_NOT_APPLICABLE_LICENSED_BY` maps a fact to the **triggers** that permit a blank, because for stdio there is only one way a step can fail to apply: the instance ended before it could. Remote adds a second, genuinely different way — **the arrangement never existed at all**, because the server declined to offer it. A server that issues no session is conformant, and that is not an ending. So a remote `not_applicable` is licensed by a trigger *or* by a **capability fact recorded in the connect record**, and by nothing else. Both sources are positive statements written before the teardown; what stays forbidden in both directions is a blank justified by silence.

**And the endings BEFORE that record needs a trigger of their own, or the grammar has no legal shape for them.** DNS, TLS, a refused connection, a non-2xx initialization, a version outside the allowlist, a guardian that dies before reporting — all of these happen after the start record and before any connect record exists, and the fact set above has no way to say so. `spawn_failed` is the stdio answer to exactly this, and the remote one is **`connect_failed`**, with the same three properties that make `spawn_failed` an ordinary ending rather than a hole:

- **Its complement is exact, and it is NOT the stdio one.** `spawn_failed` ⟺ no spawn record, because a failed spawn produces nothing worth recording — no pid, no pgid. A failed *connect* is different in the one way that matters: **it can already have produced a session.** So the connect record is written whenever the guardian reports at all, carrying the negotiated version, a **session disposition**, and whether the connection is `usable` — and no resolved URL, for the reason just given; and `connect_failed` ⟺ that record says `usable: false`, **or** there is no connect record because the guardian never reported. Forcing the stdio parallel here was the error — the asymmetry is real, and the design owns it rather than flattening it.
- **It licenses `requests_settled` and `streams_closed` unconditionally, and `session_released` only on one of its two branches.** An earlier draft blanked all three, which is false in the case that matters most: an initialization that succeeded and was then refused for an **unsupported negotiated version** is a `connect_failed` in which the guardian is holding a live session id, and blanking the release there says "there was nothing to release" about a session this run created. But the correction overshot in turn — see the cross-product below, whose first row an unconditional "never" leaves with no legal fact at all. `intake_closed` stays unlicensed on both transports: there is no ending in which the proxy did not have an intake to close, so a blank there is never justified.
- **`session_released` is decided by the EVIDENCE, and the evidence is a TAGGED value rather than a string with reserved words.** The guardian reports `{"state": "none" | "known" | "indeterminate", "id": …}`, with `id` **required when `state` is `known` and forbidden otherwise** — malformed in either direction, like every other pairing here. Sentinels were the first spelling and they are unsound: a session id is visible ASCII and may therefore literally *be* `"none"` or `"indeterminate"`, so a live session would decode as *no session* and its release would be skipped. This repo has already solved this exact problem once — `_MISSING` exists in `mcp_audit` because `child_status: null` is "a record claiming the evidence exists while carrying none of it" — and the rule generalizes past absence: **a value drawn from an open domain cannot carry its own status in-band.**
- **The audit log gets the STATE and not the id, and the id travels the REPORT pipe.** The topology already exists and has three parts, each one-way: the setup-and-launch order pipe the guardian reads, the **lifeline** carrying one-byte orders out — whose EOF is what fires the sweep — and the **report** pipe carrying the guardian's JSON answers back, whose EOF is how the proxy learns the guardian died. A disposition is an answer, so it rides the report pipe like every other answer; calling it the order pipe pointed it up a channel that only runs the other way and would have broken guardian-loss detection to boot. **The guardian retains the id** — it is the process that must send the `DELETE` if the proxy dies first — and reports it so the proxy can hold it *in memory* for **every request it makes after initialization**, which is the transport's requirement and not merely a teardown detail (see the outbound obligations below). What is persisted is `{"state": …}` alone, and an `id` in the record is malformed: the reader's question is whether a session existed, which `state` answers completely, while the id is a capability handle for a session someone is still holding open.
- **The cross-product is closed explicitly, because the trigger alone does not determine the fact.** Every state the evidence can be in gets a row, and the first two are not covered by the disposition table at all, since no connect record exists to hold one:

  | evidence | `session_released` |
  | --- | --- |
  | **no `connect_attempt` record** — no order to initialize was ever issued, so nothing can have been minted | **`not_applicable`**, licensed |
  | `connect_attempt` with **no connect record** — an order went out and no disposition came back | **`unknown`** |
  | `{"state": "none"}` — the initialization completed and carried no id | **`not_applicable`**, licensed by that recorded fact — the capability source, as the no-session case always was |
  | `{"state": "known", "id": …}` | the release **runs**, whatever else failed, landing `done`/`failed` by the `DELETE` table |
  | `{"state": "indeterminate"}` — sent, no usable answer | **`unknown`** |

  **That first row needs POSITIVE PRE-REQUEST EVIDENCE, and an earlier draft tried to infer it from a terminator.** The inference was that a terminator proves the proxy lived long enough to write a connect record, so its absence means the guardian never completed phase one and was never ordered to initialize. **Phase one is the guardian's identity report, and it happens *before* the launch order** — while the connect record cannot be written until the initialization *result* supplies the version and the disposition. Between those two points a guardian can authenticate, receive the order, mint a session and die, leaving a live proxy that writes a terminator with no connect record. The row would have said `not_applicable` about a session that exists. **A terminator proves the proxy survived; it proves nothing about what the guardian was told to do.**

  So the boundary moves earlier, exactly as §10.5 already moved the instance boundary to *before* the spawn attempt so that `spawn_failed` could be an ordinary ending with a record instead of a silence: the proxy writes and **flushes** a bare `connect_attempt` marker — the envelope and nothing else — **before the launch order goes down the pipe**. Its presence is what distinguishes "never ordered" from "ordered, outcome unknown", and it is the same argument `AuditSink`'s flush-on-every-write already rests on: a kill arriving between two records must not erase the evidence of what came before it. `_LINE_ORDER` gains it ahead of the connect record.

  Two consequences. The `unknown` biconditional widens: `session_released` is `unknown` **iff** the connect record says `indeterminate` **or** a `connect_attempt` exists with no connect record — one state, two ways to be in it, both recorded. And the licence for this fact is a predicate over the trigger **and the records**, not a lookup on the trigger, so `_NOT_APPLICABLE_LICENSED_BY` cannot express it as a plain map on this transport — the same shape as the disposition table itself.
- **`unknown` is a fourth fact state, and it belongs to ONE fact.** Adding it to `STATES` globally would structurally admit `intake_closed: unknown` and `streams_closed: unknown`, which are not states anything can be in — the closed-key-set discipline applied to values instead of keys. So the permitted states become **per fact**, `unknown` is legal only for `session_released` on the remote transport, and the relation is bidirectional in the widened form above: `session_released` is `unknown` **iff** the connect record reads `indeterminate` or a `connect_attempt` stands without one. `causes_for` gives it no cause, because there is no failure to name. It is anomalous: a possibly-live credential-bearing session that nothing can address is exactly what a clean cell must not certify. And it is the lost-response residue this section acknowledged in prose for three rounds while the grammar had no shape for it — a paragraph admitting a gap the record cannot express is its own defect.
- **It is an anomaly, like `spawn_failed`** — a gated server that was never reached is a gated run that did not happen, and §10.5's rule that an absent audit fails the cell is the same argument one layer in.

**`requests_settled` is `not_applicable` under it, and that is a consequence of the guardian owning the mint rather than a special case.** The initialization is the *guardian's* request, so at `connect_failed` the proxy has never had one in flight — there is nothing to settle, and the guardian's own report covers whether a session was minted. Had the proxy performed the initialization, this fact would have needed a fourth state for "a request was outstanding and its disposition is unknown", which is the tell that the ordering was wrong.

**A server that declines to terminate the session is the case this design has to take a position on.** The premise the bridge is built on is that a client asks for termination and a server may refuse — in which case the session persists on the server's own schedule, and the run cannot claim it left nothing behind. **The position: a retained session is not clean.** `shutdown_session_retained` is a cleanup outcome and it is anomalous, so the cell fails and the audit says why. The cost is named rather than hidden: a conformant server that simply does not offer client-driven termination makes every gated run against it fail, and the failure is a property of the server rather than of the scenario. The alternative — record it and call it clean — is available, and it is the right answer only if measurement shows real servers commonly refuse. **That is a question about the actual motivating server, so it is a probe, not a preference: C3-4 (§9).** Deciding it by reasoning would be choosing between "fails every run against a common server shape" and "certifies a live credential-bearing session as cleaned up", with no evidence about which case is real — and this document's standing rule is that a quantity worth deciding on is worth measuring.

**The guardian generalizes; it does not disappear.** §10.6 states its purpose as pinning the pgid so the group's identity is provable, which reads like a stdio mechanism. The *principle* underneath is transport-independent: **if the proxy dies without running its teardown, something else must release what this instance created.** For stdio that is `killpg` against a pinned group. For remote it is the session termination. And the asymmetry runs the other way from what "a remote connection has nothing to reap" suggests — a `SIGKILL`ed stdio proxy leaves a process the guardian can still sweep and the OS will eventually reparent, while a `SIGKILL`ed remote proxy leaves a session **nothing reclaims**. The guardian is more load-bearing here, not less.

What it holds changes: an unreaped pid becomes an endpoint, headers and a session id — which means **the guardian now holds a credential**, where before it held only a number. §10.3's rule that the launch order travels down a **pipe** rather than argv or the environment was written for the interpolated `env` of a stdio server and applies here with exactly the same force and for exactly the same reason: argv is world-readable via `ps` and is archived verbatim into `result.json`. The guardian's readiness protocol, its `imposter` check and its mandatory status are unchanged — a bridge that stood the guardian down because "there is no process group" would be removing the mechanism precisely where the leak is least recoverable.

**And the guardian must own the request that MINTS the session, not receive its id afterwards.** An earlier draft of this section had the proxy perform the initialization, learn the `Mcp-Session-Id` from the response, and hand it over. That leaves a window with the shape of the exact leak the guardian exists to close: the proxy is killed after the server created the session and before the handoff, and the only process still running has nothing to terminate. The window is not narrow in the way that matters — it spans a network round trip — and it is worst precisely under the failure the guardian is for.

**The stdio half already had this right, and the prose got it wrong rather than the code.** `Instance` says so in as many words: *"The child is the GUARDIAN's process, not this one's: what the proxy holds of it is two descriptors and two numbers, and everything else about it is asked for by order."* The proxy spawns the guardian and nothing else; the declared server is `Popen`ed inside `Guardian`, from a command that arrives *after* the proxy has accepted that guardian — "a guardian the proxy has not accepted has nothing to run". The invariant is **whatever can create a thing that outlives this instance is created by the process whose job is to outlive the proxy**, and the bridge restates it rather than inventing one: the guardian receives endpoint, headers and proposed version down the order pipe, performs the initialization itself, and reports readiness up the **report** pipe *together with* the session disposition — the two directions being different channels, which is why naming them matters. Only then does the proxy write the connect record, from what the guardian reported — the same shape as the spawn record, which is written only once the guardian has reported ready and carries facts the start record could not hold.

**One residue survives that ordering, and it is a property of networks rather than of this design.** If the initialization response is lost in transit, a session may exist on the server that no process here ever learned the id of. Nothing releases it, and no amount of ordering fixes it, because the fact never arrived. What the design owes is to not claim otherwise — and to give the residue a *place in the grammar* rather than only a paragraph, which an earlier draft did not: the connect record says `{"state": "indeterminate"}`, the instance ends `connect_failed`, and the terminator records `session_released: unknown` (below). So the log names the residue instead of being silent about it. §10.6's rule then applies — the guarantee is phrased at the width of the mechanism, so "nothing this instance created is still alive" becomes "nothing this instance *learned of* is still alive", with the server's own session expiry as the only backstop. Its duration is one of C3-4's questions for that reason.

**The case that proves it is a kill placed inside the window.** §10.9's driver kills the proxy between the initialization response and the first byte forwarded to the client, and the fixture — not the proxy's own account — witnesses the termination arriving. Without a case placed exactly there, every arrangement above passes equally, including the one this paragraph exists to reject.

**New anomalies, all of them client-side obligations.** The proxy is an HTTP *client* here, so the transport MUSTs it must satisfy are the mirror of the ones `fixtures/http_mcp_server.py` enforces as a server:

- `MCP-Protocol-Version` on every post-handshake Streamable HTTP request. Not a nicety — the fixture answers 400 without it, and probe #1 measured claude sending it on every message except the `initialize` that precedes the negotiation the header reports. The bridge must do what the fleet already does.
- **`Mcp-Session-Id` on every HTTP request after initialization, where the server issued one** — every POST, the standalone GET, and the `DELETE` alike. **Initialization itself omits it**, and necessarily: the id is what the initialization response *assigns*, so there is nothing to send until it exists, and the exemption is the same one the protocol-version header takes for the same structural reason.

  **This is the requirement an earlier draft came closest to losing**, because it described the retained id as being held "for the ordinary teardown" — which named its last use as though it were its only one. A conforming stateful server rejects an ordinary POST that omits it, so a bridge built from that sentence would attach the header on `DELETE`, work perfectly against a sessionless server like today's fixture, and fail against the first real one. The guardian holds the same id for its emergency release, so there is exactly one value with two holders and no second source.
- **`Accept: application/json, text/event-stream` on every POST** — both, because either is a legal answer and a client that advertised one would be refusing an answer the server is entitled to give.

  **This one comes with a witness problem, and the witness is the part to fix.** `Channel.rpc` in `verify_mcp_fixtures.py` sets that header itself, on every request it makes. Any check driven through a helper of that shape observes the header whatever the bridge did, so the bridge could omit it entirely and every green check would stay green — a claim and the thing it claims about with the same author, which §4 already names as its own defect family. The fixture's receipts already record **every header as received**, so the observation channel exists; what is missing is the obligation and an assertion that reads it. So: the check reads `accept` off the receipts written by the *fixture*, the driver's own client stops supplying it for the bridge's cases, and a negative control — a request that really does omit it — proves the assertion can fail.
- **A status is read against the operation that provoked it, never as a bare number.** An earlier draft said "non-2xx is an anomaly, no retry", which is the same defect §10.5.1 is built to prevent — one slot asked to carry facts from different phases of a lifecycle. Two statuses in the binding this bridge serves are *lifecycle signals with defined meanings*, and a blanket rule erases both: `404` to a session-bearing request is how a server says that session is gone, and `405` to a `DELETE` is how it says client-driven termination is not supported. Flattening them into "a request failed" loses the only information either carries.
  The session release therefore has its own small table, and it is not the same table as an ordinary request's:

  | `DELETE` answered | `session_released` |
  | --- | --- |
  | 2xx | **done** — the server says it terminated it |
  | `404` | **done** — the server may end a session whenever it likes and owes `404` to anything carrying that id afterwards, so this *is* the evidence the session is gone. A `DELETE` racing an expiry is the ordinary way to see it. |
  | `405` | **failed**, cause `shutdown_session_retained` — client-driven termination is not supported and the session persists |
  | anything else | **failed**, cause `shutdown_session_failed` |

  **The same status therefore means opposite things on the two operations, and that asymmetry is the point of reading it against the operation.** On the release, `404` is "already done". On an ordinary session-bearing request it is "the state this run depended on vanished underneath it" — **an anomaly that ends the instance**, and a *priced* refusal rather than an oversight (see "what stays refused"). A rule that merged them would have to pick one, and either pick is wrong half the time.
  - Every other non-2xx is an anomaly, and **no status is retried.** Retrying is degradation with a friendly name: a request the proxy re-sends is a request whose disposition the audit can no longer state.
- A POST answered with something that is neither `application/json` nor `text/event-stream` is an anomaly. `202` with no body is the correct answer to a notification-only POST and must not be read as an empty response to a request.
- A response carrying an `Mcp-Session-Id` that differs from the established one is an anomaly — a session change mid-connection is either a server bug or a different server.
- **A redirect is refused.** Following one would send the bearer token to a host the scenario did not name, and "the credential goes only where the config says" is not a property to leave to a library's default.
- **`https` is required unless the host is loopback.** The fixture binds loopback-only and the harness's own tests reach it over plaintext; every other destination gets a credential over TLS or gets refused. This is the one rule here with no stdio counterpart, because stdio had no network to leak onto.

**All three outbound headers are checked the same way, and the check is per METHOD rather than per run.** The receipts carry the HTTP verb beside the headers, so the assertion is that `Mcp-Session-Id` is absent on the initialization and present on **every** later request across `POST`, `GET` and `DELETE` — not that it appeared somewhere. That distinction has already cost this repo once: probe #1's version-header check "dropped the header-less requests and required only that one remained, under which a client sending the header once and omitting it thereafter passed while the paragraph went on claiming otherwise". Each header also gets an omitted-header negative control, for the reason the `Accept` case needed one.

**The standalone GET stream is in the first cut, and it needs a lifecycle of its own.** `streams_closed` named it from the start while nothing else in this section said when it opens, what it may be answered with, or what a closure means — so the rule for a POST's stream would have been applied to it by default, under which a server closing the channel mid-cell reads as *successful cleanup* and the proxy continues, quietly deaf to everything the server says afterwards.

**It is not optional for this bridge, whatever the binding permits a client.** The proxy presents **stdio** to the CLI, and stdio is symmetric: a server may send notifications at any time, and under legacy it may send requests. A bridge that never opened the GET would convert a bidirectional channel into a half-duplex one *without the CLI being able to tell* — which is degradation with no error, the one outcome §10.5 exists to make impossible. Concretely it is not hypothetical either: §10.4 already turns on `notifications/tools/list_changed` prompting re-enumeration, and C3-0 found agy opening a `subscriptions/listen`.

- **Opened by the PROXY, not the guardian, immediately after the connect record is written.** The guardian owns what *mints* — the GET creates nothing, it carries a session that already exists — so the ownership rule from above stays as narrow as it should be. Immediately, because a notification arriving before the stream exists is lost, and the only honest thing to do about that window is make it as small as the design can.
- **`Accept: text/event-stream` — this one header only**, which is *not* the POST's pair. A stream is the only thing a GET can be answered with, and copying the POST's `Accept` here would advertise willingness to receive a thing that would be a protocol error. Plus the session id where one exists, and `MCP-Protocol-Version`. All of it observed off the fixture's receipts, per the witness rule above.
- **`405` is a conformant answer and is not an anomaly** — it is the server saying it offers no *standalone* channel. **That is all it says, and an earlier draft read far more into it.** A POST may still be answered `text/event-stream`, and such a stream may carry notifications and, under legacy, server-originated requests — so `405` here does **not** mean no server-initiated message can arrive, does not mean the filtered advertisement cannot be invalidated mid-cell, and licenses nothing about `streams_closed`, which is never blank anyway. The mistake is worth keeping in view because of what it would have produced: a bridge that concluded "no stream, therefore no server traffic to inspect" and stopped routing POST stream events through `decide()` would launder exactly the traffic §10.6 exists to catch, while its audit log recorded a clean run.
- **The GET's result is its OWN record, because an append-only log cannot amend one.** The stream is opened after the connect record is written, so its outcome is a fact observed strictly later; putting it *in* the connect record — as the first draft did — describes a file that cannot be produced. It gets a **stream record**, mandatory, between the connect record and any forwarded traffic, carrying one of `open`, `unavailable` (the `405`), or `failed` (anything else). It is subject to the same closed-world and absence checks as the spawn record: **no client traffic is forwarded before it is written**, which is what makes its absence mean something rather than being a gap in the evidence, and `_LINE_ORDER` gains a member between spawn and event. A connect record with no stream record after it and no terminator is the ordinary absence case — the proxy died in between — and the existing rule already fails it.
- **`failed` needs a trigger of its own, and neither existing one fits.** It happens *after* the connect record, so it is not `connect_failed`; no stream ever opened, so it is not `stream_lost`; and every instance must latch a terminal reason or the terminator is malformed. So: **`stream_open_failed`**, related to its record in both directions — it **appears in the trigger list** iff the stream record reads `failed`, and the record reads `failed` iff it appears. A terminator carrying one without the other is malformed rather than interpreted, which is the same discipline `spawn_failed` and the spawn record already keep.

  **The relation is over MEMBERSHIP, not over being the latch, and an earlier draft got that wrong.** §10.5.1 is explicit that the latch decides which trigger stopped forwarding and not which triggers count — "two pumps and a signal handler can all reach the end at once" — so a `SIGTERM` or a client EOF may latch while the GET is failing microseconds later. The stream record correctly reads `failed`; `stream_open_failed` is then a runner-up. Requiring it to be the latch would make a legal, ordinary race into a malformed record, which is the same defect as any other rule that reads a *list* as though it were a *slot*.
- **It licenses nothing, and that is the difference from `connect_failed`.** A failed GET is an ending, not a phase that never happened: the connection exists, the session exists, and everything downstream of it still applies — so `session_released` **must still run**, `requests_settled` applies over whatever was outstanding, and `streams_closed` is `done(count=0)`. An ending that skipped the session release because the *stream* failed would leak the session on the strength of an unrelated failure, which is the shape of leak this whole section keeps circling.
- **A 2xx whose content type is not `text/event-stream` is an anomaly.** We asked for a stream; anything else is a server we cannot read.
- **Every event on it goes through `decide()`, in the server→client direction**, using the same decoder as a POST's stream. This is the channel where that matters most: under legacy a server may originate requests, so §10.6's tool-bearing-sampling check has its most likely real arrival point here, and a GET stream that bypassed the decision layer would be a route by which tool definitions reach the model without passing the allowlist — precisely the hole §10.6 is built around.
- **A closure the proxy did not initiate, while the instance is live, ENDS the instance.** The trigger is **`stream_lost`**, and it is the *same* trigger the decoder rules above reach for when a POST's response stream ends early — one reason, with the record naming which stream, because "the server's half of a stream went away before it was finished" is one fact whether the stream was correlated to a request or standing open for notifications. Its stdio counterpart is exact: `child_exit` is already an anomaly because "a child that dies mid-request must not read as a quiet end of stream", and a server dropping this stream is the same event with a socket instead of a pipe. Without resumability there is no way to recover the gap and no way to bound it, so continuing would mean forwarding an unknown number of *absences*. The classification is therefore by **phase**, not by the closure itself: closed by the teardown ⇒ `streams_closed=done`; closed under the proxy while the instance is live ⇒ trigger, anomaly, instance over. That is the same phase distinction §10.5 already draws between an unexpected child exit and an ordinary EOF during the drain.

**The same race asks a question of `connect_failed`'s licence that slice 1 has to answer, and it is not a remote question.** `not_applicable` is licensed by the **latch** today — "only the event that ended the instance before the step could apply can say that", the argument being that a later trigger arrives during teardown, by which time the step has had its chance. That argument is sound for triggers that can *only* arrive during a teardown, and `connect_failed` is not one: it can only arrive before the back half exists. So a `SIGTERM` latching while the connection is failing leaves `connect_failed` as a runner-up, holding no licence, over facts whose phase genuinely never happened.

**The licence stays keyed on the LATCH, and the bridge is built so that keeps being sound.** An earlier revision of this section said the opposite — that `spawn_failed` could be a runner-up behind a signal, making the shipped latch check a false anomaly reachable today, and that the reader should therefore be loosened to membership. **That was wrong about the stdio half, and reading the path rather than reasoning about it is what showed it.**

The invariant is that `spawn_failed` is always **first**, and an earlier draft of this paragraph claimed something stronger and false: that the signal is never latched at all. The handler is `lambda _sig, _frame: None`, all it does is let `set_wakeup_fd` write a byte, and that byte is read only by `_on_signal` — but `run()` calls `_on_signal(wake_r)` a second time, **after the teardown and outside the `if self._spawn():` branch**, precisely so a signal landing mid-teardown is not silently dropped. So a signal arriving while a spawn is failing *is* recorded, as a runner-up, and `[spawn_failed, signal_term]` is an ordinary trigger list.

What cannot happen is a signal getting there first: `_spawn()` latches `SPAWN_FAILED` before any code path can read that pipe. **`spawn_failed` is structurally the latch, not structurally alone** — and the latch is exactly what `_NOT_APPLICABLE_LICENSED_BY` reads, so the narrower invariant is the whole of what the licence needs.

So there is no shipped defect and no reason to weaken the check. **The property is structural, and the bridge inherits it by construction**: connect-phase failure must latch before anything drains the wakeup pipe, which the `if self._connect(): … self._pump(…)` shape gives for free — a signal may still be recorded behind `connect_failed`, and must be, but it cannot precede it. Keeping the invariant and constraining the new code is the better trade than relaxing a rule to tolerate a state that cannot occur; a looser licence would accept a blank in some future arrangement where the phase *had* run.

**What is genuinely missing is an arm.** The property is guaranteed by control flow and explained in prose, and nothing tests it, so a refactor that moved the spawn inside the loop would break it silently and no check would notice. Two are needed, and they are different questions — which is not a stylistic point: the reader arm alone passes whatever the writer emits, and that is exactly how the post-teardown drain escaped the first draft of this section (review, PR #109).

The **reader** arm drives both orderings: `[signal_term, spawn_failed]` with blanks must be REFUSED, and `[spawn_failed, signal_term]` with the same blanks must be ACCEPTED — the second being what the writer really produces, so an arm that pinned only the first would be silent about the case that occurs. The **writer** arm delivers a signal during a failing spawn and asserts `spawn_failed` is still first *and* that the signal is present behind it; an arm demanding a one-entry list would forbid the behaviour the post-teardown drain exists for. That needed a window, since every establishment failure returns in microseconds — hence `mute`, a guardian that stays alive and says nothing so the readiness wait ends on its deadline rather than on EOF, in the same test-only category as the fault point.

§10.9's driver covers four, and only one of them can fail against a teardown that closes nothing:

- **the positive control: streams held open until the teardown, closed by it, counted.** Every other case here ends with `count=0` or with an anomalous closure the proxy did not perform, so **a bridge that always recorded zero and never deliberately closed anything would pass all of them** — §4's rule that an assertion satisfied by nothing being recorded is satisfied equally by the code never running. So one case holds a standalone GET stream *and* a POST stream open until teardown begins, and asserts the recorded identities and a **non-zero** count before the terminator is accepted, with the closures **witnessed by the fixture** rather than read from the proxy's account of itself.

  **And that is still not enough, for the reason §4 already gives about the process-group case.** A proxy that records the right identities, closes nothing, writes its terminator and exits **closes every socket on the way out**, and the fixture sees the same EOF it would have seen from a real teardown. This is the C3-3 lesson in its third instance — there, "a proxy that exits without reaping leaves a child that init adopts and reaps, and afterwards the two are identical" — and §4's remedy is the one to apply rather than a new one: prefer evidence that cannot race the proxy's exit, and check the discriminating power of the witness itself.

  Sockets admit no monotone equivalent of the inherited pipe that solved it for processes: a closed socket and a dead peer are indistinguishable *after* the fact, which is the whole difficulty. So the window is constrained instead, in two parts, and both are needed:

  - **The observation is taken while the proxy is demonstrably alive.** A test-only gate holds the proxy after `streams_closed` completes and before it may write the terminator or exit; the driver confirms its own child is still running, reads the fixture's record of the closes, and only then releases it. That the gate is test-only puts it in the same category as the fault point (§10.9) — a knob that exists so a state can be produced on purpose — and it is subject to the same rule: armed, it must never be able to produce a *passing* run that skipped anything.
  - **A negative control proves the fixture can say "still open".** The same case with the close suppressed at the fault point, asserting the fixture reports the stream live while the proxy is alive. Without it, "the fixture reported closed" might be what the fixture reports regardless — the premise §4 requires an observation channel to establish before its silence, or its speech, is worth anything.

- a fixture answering `405`, asserting the run stays clean, the stream record says `unavailable`, and `streams_closed` reads `done` over a recorded **zero**;
- a live stream the fixture closes mid-cell, asserting the instance ends anomalously and — the assertion that matters — that `streams_closed` does **not** read `done`;
- **`405` to the GET *and* a POST answered `text/event-stream` carrying a server-initiated message.** This is the laundering case: the arrangement in which a bridge that treated the standalone `405` as "no server traffic exists" would forward an unfiltered server→client message and record a clean instance while doing it. Neither case above can fail against that bridge, which is the whole reason this one exists.

**What stays refused after the bridge lands.** §10.8's list grows these rather than shrinking to nothing, and the first two are *priced* refusals — legal client behaviour this design declines on purpose — rather than gaps nothing has reached yet.

- **`transport: sse` with `tools:`** — a second state machine, not an option on this one (scope, above). Refused by name at `tool_filter_for`.
- **Session restart after a `404` to an ordinary request** — the release's `404` is a *completed* cleanup, not this case. The binding lets a client whose session has expired initialize a new one and carry on. This bridge ends the instance instead. **The price is a real one and belongs in the open**: a server that expires sessions on a short timer will fail long runs, and the failure is a property of the server rather than of the scenario. The argument for paying it is that the tool list the model was shown was filtered from an advertisement served by the session that just vanished, so continuing means grading a run against a server that has forgotten the state the run depended on — §10.5's never-degrade rule reaching one layer further out than it was written for. **How short that timer is on a real server is measurable, so it is a C3-4 question rather than an assumption**, and if the answer makes this expensive, the alternative is a *recorded* restart — a new connect record under the same instance — not a silent one.
- Modern `2026-07-28` over HTTP, which the fixture explicitly does not serve and which only agy speaks. Note the direction of the surprise here: **modern removed protocol-level sessions**, so the session machinery above is *legacy* machinery, and a modern back half is a different design rather than a wider one.
- Stream resumability and `Last-Event-ID`.
- Any authentication flow other than the declared `headers:` — no OAuth, no token refresh.

**Build order, and each slice verifiable before the next.**

0. **Pin the latch property, before any of this — it is an arm, not a fix.** `mcp_audit` licenses `not_applicable` off the **latch**, and that is correct and stays: a failed spawn returns before the pump loop is entered, so a signal is never latched alongside it (above). What is missing is anything that would notice if that stopped being true. Add the **reader** arm — trigger list `[signal_term, spawn_failed]` with blanks must be refused — and the **writer** arm for a signal delivered during a failing spawn, which needs a test-only knob holding the proxy inside guardian establishment. It is step zero because every slice below inherits the property, and because the bridge is required to preserve it by construction rather than to be checked for it afterwards.
1. **The ending model** — `FACTS_REMOTE`, `connect_failed`, `stream_open_failed`, the `connect_attempt` and connect records with the tagged session disposition, the `unknown` fact state, the new outcomes and their pairings in `mcp_audit.py`, with arms and mutations. The arm that matters most is the one for a guardian that dies **after** the order and **before** its disposition report, since that is the window the first draft's terminator inference was blind to. Synthetic records only; no bridge, no server, nothing on a socket. This is how `mcp_audit.py` was built the first time — written before the code that produces it.
2. **A session arm and a server→client stream arm for `fixtures/http_mcp_server.py`.** The fixture implements no sessions and advertises none, deliberately: *"what is not conformant is issuing one and ignoring it."* Everything downstream of `session_released` needs a server that mints, honours and can be made to refuse — so this is a prerequisite rather than a detail, and it is harness work rather than a dependency on anyone. On demand it must also answer `405` to `DELETE`, `404` to a session-bearing request, `405` to the standalone `GET`, open a real stream and **close it mid-cell**, emit an empty priming event, **hold a stream open past its correlated response until the client closes it** — which is what the non-zero-count control needs and what nothing else in the fixture does — and, for the laundering case, **answer a POST with an SSE stream carrying a server-initiated message**, independently of whether the standalone GET was refused. It must also record each close it observes, since the count assertion is only worth anything read from the server's side. Every one of those is a case above rather than a hypothetical, and the last is the one that has to be arrangeable *in combination* with the `405`.
3. **The HTTP client half**, driven by `verify_mcp_proxy.py` the way the stdio half is: over a real socket, with the audit log read back. Two parts of it are easy to leave for later and must not be: the **SSE decoder** with its own anomaly boundary, and the **outbound header assertions** read off the fixture's receipts — which means the driver's client stops supplying `Accept` for these cases, since a helper that sets a header cannot witness whether the program under test sets it.
4. **The guardian's session release**, whose control is the one that matters — the `SIGKILL` placed *inside* the minting window, with the fixture witnessing the termination rather than the proxy's account of it.
5. **The adapter flip**, and it is narrower than the earlier draft claimed: `tool_filter_for` stops returning `unbuilt` for a remote `http` server, and keeps returning it for `sse`. That the last slice is a branch rather than a rewrite is the return on #107, which put the refusal in the two places that have to change.

Slices 1–4 need no MCP server that this repo does not already own or is not about to write. **C3-4 is the only piece gated on outside access**, and its hard deadline is slice 5: before that, an unmeasured verdict rule cannot affect a run, because no gated remote run can happen.

Two dependencies worth restating as risks rather than facts, because they are the ones most likely to move:

- **Sampling's clock is running.** It is deprecated, not removed, and the ≥12-month floor puts removal no earlier than mid-2027. The §10.6 anomaly check should outlive it harmlessly, but the *justification* for it expires.
- **The era split is a moving target, not a constant.** C3-0's answer is true on the day it is measured. §10.7 records era and version per run precisely so the design does not quietly rot back into an assumption once the probe is a year old.
